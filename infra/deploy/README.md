# The demo server

Everything needed to run the COOP ERP **demo** (demo data only, about 80 testers) on one Ubuntu 24.04 server with Docker Compose. Not a production deployment: that is doc 35's, which is not written yet.

Pick the size, then follow its guide from start to end. Each guide is complete on its own.

| Size | Server | Guide | What it carries |
|---|---|---|---|
| small | 2 vCPU / 4 GB RAM (+ 2 GB swap) | [SETUP-2vCPU-4GB.md](SETUP-2vCPU-4GB.md) | the demo, with slow moments when many testers sign in or print at once |
| medium | 4 vCPU / 8 GB RAM (+ 1 GB swap) | [SETUP-4vCPU-8GB.md](SETUP-4vCPU-8GB.md) | about 80 testers comfortably |

Both guides use DigitalOcean as the example and say how to do the same at another provider (Contabo, for instance). Nothing in the files depends on the provider.

## How it fits together

One address, served by Caddy, the only container with open ports (80 and 443):

```
https://<address>/            the back office (the web image: Caddy with the built web client)
https://<address>/api/...     the backend (web and worker roles in one container)
https://<address>/auth/...    Keycloak: the coop realm's sign-in pages only (the admin console by SSH tunnel)
https://<address>/mail/...    Mailpit, which catches every mail the demo sends (own password)
```

Behind them, inside the server only: PostgreSQL 16 (the application's database and Keycloak's), PgBouncer, RabbitMQ and MinIO.

The address is one of three kinds, chosen when `bootstrap.sh` runs:

- **The server's IP as an sslip.io name** (the default): `https://203-0-113-5.sslip.io` for the IP 203.0.113.5. sslip.io answers every such name with the IP inside it, so there is no DNS work, and Caddy gets a real Let's Encrypt certificate for it.
- **The bare IP with Caddy's own certificate** (`--tls internal`): `https://203.0.113.5`, for when sslip.io or Let's Encrypt cannot be reached. Browsers warn once.
- **Your own domain** (`--domain demo.example.com`): an A record pointing at the server, and a Let's Encrypt certificate.

Plain `http://<ip>` is not offered: the sign-in needs a secure page (the browser's crypto functions behind PKCE exist only there), and Keycloak refuses a sign-in over plain HTTP from outside.

## The files

| File | What it is |
|---|---|
| `compose.yml` | the services, shared by both sizes: images from GHCR, health checks, restart policy, capped logs, named volumes, secrets from `.env` |
| `resources-small.yml`, `resources-medium.yml` | the memory of every service and the JVM and PostgreSQL tuning for each size; the numbers are explained at the top of each |
| `Caddyfile` | the front door: TLS, the paths above, and `/config.js`, the web client's addresses written from `.env` when Caddy starts |
| `.env.example` | every variable of `.env`, explained, with placeholders; the real `.env` is generated by `bootstrap.sh` |
| `bootstrap.sh` | prepares a fresh server (Docker, swap, firewall), writes `.env`, renders the realm, starts everything |
| `deploy.sh` | updates the server to the clone's commit (files and images alike), after a backup, and checks it from outside; run from the clone only |
| `demo-data.sh` | loads the demo (`--reset` wipes it first, after asking; `--repair-users` puts every demo user back to `DEMO_PASSWORD`, no data touched) |
| `backup.sh` | dumps both databases and mirrors the uploaded files to `/opt/coop-erp/backups`, optionally to an S3-compatible bucket |
| `restore.sh` | restores one backup into fresh databases, with its uploaded files and the version that made it |
| `objects.sh` | copies the uploaded files into a backup and back (run inside the MinIO client container by `backup.sh` and `restore.sh`) |
| `lib.sh` | what the scripts share |
| `postgres/02-keycloak.sh` | Keycloak's database user and database (beside `infra/compose/postgres/init/01-roles.sh`) |
| `compose.local-test.yml` | for trying the package on a laptop beside the development stack; never on a server |

The scripts copy what the server needs (these files but `bootstrap.sh` and `deploy.sh`, the role script, the Keycloak theme, the development realm it renders from, and the seed SQL) into `/opt/coop-erp`, and work there. `bootstrap.sh` and `deploy.sh` run from the clone only.

## Decisions taken here

- **The Keycloak realm is rendered from `infra/compose/realm-dev.json`**, not kept as a second copy, so a user added to the development realm reaches the demo server too. The rendering replaces the web client's addresses, every user's password (with `DEMO_PASSWORD`), the backend client's secret, requires HTTPS from outside, and switches the web client's password grant off. `lib.sh` refuses a result that still holds a development value.
- **Step-up without a second factor is kept, as a demo-only setting**: the demo realm has no OTP, so `COOP_ERP_MFA_PASSWORD_REAUTH_COUNTS=true` lets a fresh password sign-in count as the step-up, as on a laptop. With a public issuer the backend refuses to start on that flag unless `COOP_ERP_MFA_PASSWORD_REAUTH_PUBLIC_ACK=demo-data-only` is set too, which only `compose.yml` here does (wave 2, D-5). A real environment removes both and gives the realm a second factor.
- **The till application floor is not raised above a version that has shipped** (`sync.app_version_floor`) until the self-updating launcher of CR-30-1 exists: a till below the floor after its grace still uploads its sales (facts are always accepted, CR-32-1 item 1), but it receives no snapshot or change log (426) and sells on its last snapshot until someone updates it by hand.
- **Wave 2 (6 October 2026, `docs/progress/deviations/2026-10-06-wave2-deploy-kit.md`)**: the server runs explicit commit SHAs of main, chosen by the operator (D-1); backups include the uploaded files and are restored by `restore.sh` into fresh databases (D-2); Keycloak's public surface is the coop realm and the theme files, the console is reached by SSH tunnel, brute-force protection is on (D-3); the demo users are shared, without self-service, and repaired by `demo-data.sh --repair-users` (D-4); security headers, `no-new-privileges` everywhere and `cap_drop: [ALL]` but on postgres and rabbitmq; the backend uses its own MinIO user, not the root key. Before real data: point-in-time recovery, encrypted dumps, named Keycloak admins with OTP, one account per person, read-only root file systems, a maintained MinIO image (doc 35).
- **The till history runs from a small `demo-tools` image** (the till simulator of the backend's test sources and its class path, `infra/demo-tools`), published by CI, so the server needs no JDK or Gradle. It signs in with the password grant, which `demo-data.sh` switches on for the run and off again.
- **The web image is Caddy itself** with the built bundle in `/srv` (`infra/web-image`), and the web client reads its addresses from `/config.js` at page load (`web/src/shell/runtimeConfig.ts`), so one published image serves any address.
- **Keycloak serves under `/auth`** rather than on a subdomain: an IP or sslip.io address has no subdomains, and one origin needs one certificate and no CORS.
- **Keycloak keeps its data in PostgreSQL** (its own database), so users made in the back office survive a restart; the realm file is imported only into an empty Keycloak.
- **HTTP/3 is off**: it would need UDP 443 opened as well, and without it browsers stall trying.
- **CPU is not split between services**; memory is capped per service.
