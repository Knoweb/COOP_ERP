# Production go-live: the task list

What stands between the system as merged on 7 October 2026 and a production that handles real money records, real people's data and a fleet of tills. Written for the architect, the DevOps engineer, the till and backend leads, the Federation's business owners and the people who will run the assurance (load, security, certification). It is a list of tasks with evidence, not a schedule: there are no dates in it, only gates and dependencies.

Sources, so every figure and gate here can be checked: the NFR specification (doc 06, `docs/requirements/txt/06_NFR_Specification.txt`), the technical foundations (doc 14, sections 5 to 9), the solution architecture (doc 17, sections 12 to 15), the open-items register (doc 10, `docs/DECISIONS_PENDING.md`), the update design (doc 31), the sync contract (doc 32), the wave 2 review (`docs/reviews/wave2-summary.md`, `wave2-fix-plan.md`) and the repository itself. Where a document is cited, the task says "per doc n".

## 1. How to read this list

**Gates.** Each task blocks the earliest gate it is tagged with.

| Tag | Gate | Meaning |
|---|---|---|
| **P** | Pilot gate | About 400 shops, real data, real (recorded, never moved) money. Doc 14 DR-1 and doc 17 name this as the latest moment for the hosting decision. |
| **L** | Production go-live | Rollout beyond the pilot, in waves, on the update rings of doc 31. |
| **S** | Scale readiness | Evidence that the system reaches the three-year envelope (10,000 shops, about 15,000 tills, about 3 million receipts a day) and the five-year one (12,000 shops). Needed before the wave sizes grow, not before the pilot. |
| **C** | Certification audit | The independent penetration test must be finished and its findings closed before the certification audit (NFR-SEC-040; open items P-12 and P-13). |

**Fields.** Every task has an ID `GL-<area>-<nn>`, what to do, the **evidence** that proves it is done (a report, a test run, a signed document: never "someone says so"), what it **needs** first, and an owner role in square brackets: [Arch] the architect (Chamin), [DevOps], [BE] backend, [Till], [Web], [QA], [Fed] the Federation's business owners, [Legal], [Ext] an external party.

**Status marks.** *Exists* means something real is already in the repository and the task extends or proves it. *New* means nothing exists yet. *Decide* means the task is a decision, to be recorded as an ADR or a deviation file and not left in a conversation.

**Rules that apply to every task.** Evidence is kept in the repository (a Markdown report under `docs/assurance/` or the document's own folder) or, where it contains secrets or personal data, in the named secure store with a pointer in the repository. A test that cannot be repeated is not evidence. A task that changes behaviour goes through the normal pull request, review and CI path of `AGENTS.md`.

## 2. The targets we are held to

These come from the baseline, and every load, resilience and security task below is judged against them. Where a figure is "planning", the task that measures it replaces it with a measured one.

| Area | Target | Source |
|---|---|---|
| Capacity | 10,000 shops (about 15,000 tills), 2.5 to 3 million transactions a day (three-year basis); 12,000 shops (five-year envelope) | NFR-PRF-010; doc 14 section 6 |
| Headroom | 2x current load unchanged; 3x with one database instance upgrade | NFR-PRF-020 |
| Reconnection burst | Hundreds of shops flushing queued offline events at once, without loss, via queued, deduplicated ingestion | NFR-PRF-030 |
| Snapshot freshness | Catalogue and price sync to tills at most a 15-minute poll interval | NFR-PRF-040 |
| Recovery | RTO 4 to 8 hours; RPO 15 minutes or less | NFR-AVL-010 |
| Offline trading | A till sells, prints legally numbered receipts, receives goods and refunds on the same till through a 1 to 2 day central outage | NFR-AVL-020, NFR-AVL-050 |
| No downtime window | 24x7 trading; rolling deploys; no scheduled central downtime | NFR-AVL-040 |
| Security baseline | OWASP ASVS Level 2; NIST-aligned credentials; TOTP MFA for financial and admin functions; no card data ever; independent penetration test before certification | NFR-SEC-010 to 040 |
| Privacy | PDPA (No. 9 of 2022) compliance, minimal PII, a named responsible officer | NFR-CMP-010 |
| Tax | Standard VAT invoicing only; numbering, invoice content and archival reviewed in writing by the tax advisor | NFR-CMP-020, NFR-CMP-030 |
| Updates | Signed, integrity-verified packages; ring deployment; resumable; automatic rollback on a failed health check; a version floor with a grace period | NFR-UPD-010 to 030 |
| Auditability | Documents immutable once issued; an audit trail with the catalogue of doc 07; the audit log hash-chained (phase 2) | NFR-AUD-010 to 030; NFR-SEC-050 |

The planning workload behind them (doc 14 section 6; the text extract of that table interleaves its columns, so confirm against the PDF before using a number): about 3,000,000 receipts a day at the horizon, about 5 lines per receipt, about 100 receipts a second on average over a 9-hour trading day and about 300 at peak, about 8 events per receipt reaching central, a steady ingest near 1,000 events a second at peak, a reconnection backlog of about 6 million receipts with a catch-up target within 4 hours at about 3,500 events a second, about 2.5 KB a receipt (about 7.5 GB a day, about 2.7 TB a year before compression), a catalogue snapshot under 20 MB a shop and about 2,000 back-office users at peak across 876 entities. The pilot is about 400 shops, which is 4 percent of the horizon.

## 3. Where we are

Done and merged: the nine modules of the demo path; the kernel; the till desktop trial; wave 1 and wave 2 reviews with all 17 fix pull requests merged (#262 to #285); the deploy kit for a one-server demo with backup and restore scripts, a restore drill and a hardened Caddy and Keycloak front; CI with unit, three integration shards, scaffolder proof, stack smoke, coverage merge, gitleaks over the whole history, a weekly Trivy scan, SBOM (CycloneDX), SHA-pinned actions; Prometheus metrics and health probes in the backend.

Not production: the deploy kit is a one-server demo shape (2 vCPU / 4 GB or 4 vCPU / 8 GB). Doc 17 section 12 asks for at least two web/API and two worker instances behind a load balancer, a PostgreSQL primary with a streaming replica and WAL archiving, a broker, object storage and a self-hosted identity provider, in four environments. None of that exists yet. No load test has been run at any scale. No penetration test, threat model or ASVS traceability exists. Docs 34 to 40 (assurance plan, deployment, observability, rollout, support and others) are not yet written.

## 7. Performance and load testing (PRF)

The architecture's own verification for the capacity targets is "spike 5 at the 15,000-till envelope" and a burst simulation of two days of events from thousands of tills (doc 17 section 13). The kernel has a till simulator (`TillSimulator`, doc 32 section 11 conformance); the load harness builds on it.

## 17. Order of work

This is dependency order, not a schedule.

1. **Decisions first** (section 4): hosting and its residency check, support hours, the certification scope and quotes, retention, the terminal and update path. Most later tasks cannot be sized without them.
2. **Foundations in parallel**: the infrastructure code and environments (INF), the load harness, data generator and workload model (PRF-01 to 03), the security engineering baseline (SEC-01 to 04), the application gaps that block the pilot (APP-01 to 05), and the till spikes (DEV-01 to 03).
3. **First measurements**: the pilot-scale baseline and burst (PRF-04, PRF-06, PRF-08), the restore and PITR drills (REL-01 to 03), the rollover test (REL-06), the offline soak (REL-07). Their findings feed fixes; fix pull requests follow the usual process.
4. **Security assurance**: ASVS matrix and threat model complete, authorisation and tenant-isolation campaigns (SEC-05 to 07), wave 3 review (CRT-08), then the penetration test and its retest (CRT-05, CRT-06). The audit (CRT-10) follows, not precedes.
5. **Pilot gate review** (ROL-02): every task tagged P done or accepted by name.
6. **Pilot run with hypercare**, then production waves; the scale tests (PRF-05, PRF-07, PRF-09 to 13) and the failure tests (REL-04, REL-05, PRF-13) run during the pilot against staging, and gate the first large wave (tag L and S).

## 19. What this list does not decide

It does not choose the hosting provider, the certification body, the accounting system, the terminal model or the load tool; each has its decision task above. It does not set the numeric pass targets for latency and throughput beyond those in the baseline: those come from the measured baseline (GL-PRF-04) and are then fixed in doc 34. It does not replace the open-items register: every register item still open before the pilot appears here only where it needs work, and the register remains the source of the decider and the date.
