- **M1-12 society register screens (24 Sep, branch `feat/m1-12-society-register`).** The first M1 screens, in a `party` web module (`web/src/modules/m1party`): the **society register** (`/party/societies`: status and district go to the server, which filters and pages; the search box narrows what is loaded by code or name as one types; a row leads to the card), the **register form** (`/party/societies/new`: posts `RegisterEntity`, field errors under the fields and the problem title under the form, both as the server translated them; lands on the new card), the **bulk upload** (`/party/societies/bulk`: the CSV of M1-11 goes up as a multipart part, and the `ValidationReport` is a table, one row per line, problems named by field with words from the module catalogue) and the **society card** (`/party/societies/:id`: code, name in the user's language, status chip, facts; Activate for ONBOARDING, Suspend for ACTIVE, Reinstate for SUSPENDED, each only with the permission; Activate is shown disabled WITH the reason while the responsible officer or the VAT number is missing, 21A section 8; Suspend and Reinstate take a reason first). **Three shell components stop being stubs:** `DocumentHeader` (code, title, subtitle, chip, label/value facts with an em dash for "not set", and children for the bar), `ApprovalBar` (a disabled action carries its reason, tied to the button for a screen reader; one primary action) and `ReasonCapture` (code from the codes the screen offers, optional text, confirm or cancel; a dialog where the action was, not a browser modal), with their rules in `shell.css` (tokens only) and the form words `shell.reason.*` in three languages. **The stack:** the dev realm gets `fed-officer` (policy class OWN on the Federation entity, role fed-admin): `fed-admin` holds FEDERATION_VIEW, which sees every entity but may not register, activate or suspend one (21A section 6, the guard `FederationCaller`), so the register needed a user acting for the Federation itself; that is a Keycloak import and needs `make reset`. And a party dev seed (`seed/m1party/entities.dev.sql`) inserts the Federation and the MPCS every other seed and the realm already assume, so a fresh stack has a Federation for the guard to find and one ACTIVE society to show. Proof: 122 web tests (the three components; the actions of the card for every status and permission; every status and bulk problem code has words in three languages), lint, typecheck, `check-permissions`; the Playwright flow `register-society.spec.ts` registers a society as fed-officer, sees the card with Activate disabled and its reason, finds it in the register, is refused the same code again with the server's words, and sees fed-admin refused by the guard. This is part 1 of M1-12 (four of the nine screens of 21A section 8). Not in it: appointing the responsible officer from the card (the `PUT responsible-officer` needs a user of the entity, M1-07), and the screens of relationships, locations, devices, users and roles, which follow their handlers.
