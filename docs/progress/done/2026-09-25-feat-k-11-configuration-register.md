- **K-11 configuration register (25 Sep, branch `feat/k-11-configuration-register`, on top of K-12).** The register of doc 19 section 8 as 19A section 11 restates it. **Schema** (`kernel/V0052`, lane C): `config_item` (reference data: type, schema, descriptions in three languages, default, the finest scope allowed, the change permission, sensitive, till_visible, owning module) and `config_value` (append-only; a unique expression index where 19A wrote a primary key with `coalesce()`, which PostgreSQL does not take). The value policies widen the template's `own_read` on purpose: a caller reads the federation-wide rows (nobody's), its entity's rows and, at a location, that location's rows and the entity-wide ones, because a read is a resolution. **Register** (`seed/kernel/config-items.yaml`, upserted on every start as the migrator, items never values): the business time zone, the day-close cut-off, `m1.bulk.max_rows`, `trade.federation_direct.enabled`, `security.policy.mfa_enabled` (sensitive), `till.idle_lock` (till-visible); the doc 07 section 4 register is not in the repository's design texts, so the items are the ones the code and the module seeds name today, and the file is the one place to grow. A module's `seed/<module>/config.yaml` still goes through `ConfigSeeder.addDefaults`: a registered key gets its default, an unknown key becomes a plain ENTITY-scoped string item of that module. **Resolver** (`JdbcConfigRegistry` replaces the 17A stub behind `ConfigRegistry`): location, then entity, then federation, then the default; typed getters (`getDuration` added); a Caffeine cache per instance, emptied for a key by the change on the same instance, by `config.changed.v1` on the others (`ConfigCacheInvalidator`, where the consumer runtime runs), and by a thirty-second expiry everywhere. **Setter** (`ConfigRegistry.set`): the item must exist; the value must parse in the item's type and pass its schema (minimum, maximum, enum, pattern, max_length: a small validator, no JSON Schema library until an item needs one); the scope must be one the item allows; a federation-wide value is the Federation's alone (the system entity of K-12); a sensitive item needs a second factor fresher than ten minutes (`mfa.required`; K-02 refines the freshness); then the append-only row, `CONFIG_CHANGED` with before and after, the event. **Waiting on others, said out loud:** the item's `change_permission` is checked when K-03b gives the kernel a permission resolver (the calling handler carries the permission until then); the change-log fan-out for till-visible keys needs K-08's change log (the event carries the flag). **Proof** (`ConfigRegistryPostgresIntegrationTest`): the register is seeded and the default answers; the most specific scope wins and another entity is untouched; a change is appended, audited, published and seen at once; a value outside the schema, of the wrong type or of an unknown key is refused with nothing recorded; the scope must be one the item allows and the entity the caller's own; a sensitive item needs a fresh second factor; a module default updates a registered item and registers an unknown one; the M1 tests (bulk registration reads `m1.bulk.max_rows` from the register now) still pass.
