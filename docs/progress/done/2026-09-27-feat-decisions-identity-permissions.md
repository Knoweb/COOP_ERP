- **Identity and permission decisions (27 Sep, branch `feat/decisions-identity-permissions`).** Six open items decided on the architect's delegation, 27 September 2026, recorded in `docs/change-requests/CR-19A-9.md` (items 1 to 4) and `CR-19A-10.md` (item 5), both accepted; item 6 under Deviations. (1) **An EXTERNAL principal's permissions come from its roles, like everybody's** (doc 19 section 3; 21A section 7): the Federation assigns the EXTERNAL user the Regulator or Auditor template (class EXTERNAL_TIMEBOXED; `AssignRoleHandler` now permits that class for the Federation to a user of kind EXTERNAL, and to nobody else), the grant of M1-09 says in which entities and until when, and `JdbcPermissionResolver` resolves the two together: the union of the user's EXTERNAL_TIMEBOXED-class roles while a current grant exists, nothing once it ends. A regulator may name a granted entity as its active scope (`ScopeFilter.holds`), and need not. Rejected: exempting the read-only classes from every read check (the regulator template's permissions would mean nothing, and any GET would be open to any external user within its RLS). (2) **The web shell reads the resolved permission set from `GET /v1/session`**, a kernel slice (`openapi/session.yaml`, generated into `kernel.session.web.generated`, `SessionController`): user, home entity, class, scopes held, active scope, granted entities, permissions resolved for the active scope; `x-permission: authenticated`, the one value that is not a catalogue code (any signed-in principal; refused on a mutating operation and on a handler by `tools/check-permissions.mjs`); the one operation a caller holding several scopes may call without naming one. The shell's temporary role map is gone: `PermissionsContext` reads the operation once per token (and again when the step-up replay invalidates every query), `permissions.ts` answers from it, `Session` no longer carries `roles`. Rejected: a token claim (fixed for the token's lifetime; doc 19 section 2.2 keeps permissions out of the token). (3) **The kernel enforces the x-permission of every GET** (`SliceOperations` reads every slice at start; `ReadPermissionInterceptor` looks the request's path template up and asks `PermissionGate.requireRead` in a transaction carrying the caller's scope, under the same enforcement switch as a command, no second factor); the four hand-written checks of #120 and #130 (`ViewPermission` and the users, devices and grants controllers) are removed with their two tests. `PermissionGate.require` (a command) now refuses every class but OWN explicitly, because a read code and a command code may be one string (`gov.external.grant`); FEDERATION_VIEW resolves to every read of every slice ("SELECT on everything, no writes", doc 18 section 3.7). (4) **Scopes resolved at request time from M1's tables** (#105) confirmed; the provider mapper endpoint of 19A section 2 is not built (a provider extension AGENTS.md forbids; a claim cannot be revoked at once). (5) **`kernel.api.SyncStatus`** (#109, #114) confirmed as a kernel contract, CR-19A-10. (6) **`m1.relationship.credit_limit_mfa_max_age` stays ENTITY-scoped, PT1M to PT12H, sensitive**, the same scope and bound as `security.mfa.freshness` (Deviations). **Seed**: `users.dev.sql` gives the cashier a reads-only development role (`*.view`, `*.read`, including `hello.greeting.read`, now seeded too) and takes the every-permission row away from a stack seeded earlier, so that the e2e "cashier is told why there is no form" holds against the server's set as it did against the map; fed-admin (FEDERATION_VIEW) sees every read and no form without any row.
