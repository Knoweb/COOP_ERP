- **Review fixes for K-03a and K-05 (24 Sep, branch `fix/k05-relay-user-and-consumer-paths`).** #86 and #87 put the command interceptor and the event backbone on `main` in one day; the reviews found the failure paths, and the ones that matter are fixed here. **Database users are applied on every `make up`, not only at creation:** #87 added the login user `coop_relay` to the role script, which ran only when the volume was created, so every existing database lacked it and the worker could not start. The script is idempotent now (`make roles`, run by `make up` before the backend starts), so a new user or membership reaches an existing database without `make reset`; proven on a database that had no `coop_relay`. A migration cannot do this on PostgreSQL 16: the migrator may create a role but not add it to a group it did not create (measured), and a password never enters git; `AGENTS.md` says so. **Consumers no longer redeliver for ever:** a body that cannot be read or a consumer/type pair nobody registered is refused without requeue and logged, instead of coming straight back; the replayer sends a consumer only the types it subscribes to. **The event payload check is a word list** (name, phone, mobile, email, address, nic, passport, password, pin, otp, token, secret, dob and so on), matched as whole words of the field name, with a unit test of what it refuses and what it lets through; the old heuristic let `customerName` and `mobile` in and refused `technicianId`. **A mutating request without a user is refused** (`scope.required`): until K-02 reads the token, the dev stub gave a request with no `X-Dev-User` a fresh random user, so a retry never matched and the command ran twice. **The non-HTTP bypass is logged:** a command from a sync batch, a job or a consumer has no idempotency check yet (K-08 and K-12 give those callers their keys); the interceptor says so at WARN instead of silently. The RabbitMQ health indicator is on in the worker role only, so a web-only instance is not DOWN for a broker it never uses. Left for the author of the two tickets, from the reviews: retries in place so a failed event keeps its order, backoff and a metric when the broker is down, the relay `UPDATE` by primary key (carry `received_at`), `@Profile("worker")` instead of `@ConditionalOnBean` on the relay components, a two-instance test with a real broker (19A names it), a concurrency and a rollback test for the idempotency claim, the three idempotency config keys declared in `application.yml`, a DEFAULT partition for `idempotency_key`, inbox RLS scoped, and the literal relay password default removed.
