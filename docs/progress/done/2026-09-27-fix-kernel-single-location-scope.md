- **Shell fix: a user scoped to one place works in the web client (27 Sep, branch `fix/kernel-single-location-scope`; found by the M4-11 phase 1 e2e).** The web client sent `X-Scope-Entity` (the token's entity) and never a location. A user whose only scope is one location (the demo's `fed-stores` at FW01, `d101-stores` at W01, `m101-shop` at S01) holds no entity-wide scope, so every request, `GET /v1/session` first, was `scope.invalid` (the kernel refuses a shop user entity-wide on purpose, `TokenAuthenticationPostgresIntegrationTest`) and the shell showed "your permissions could not be read". Now the session read, when refused with `scope.invalid`, is asked again with no scope (`SCOPE_UNNAMED`, a mark the client middleware strips), and the server takes the one scope the user holds; `PermissionsContext` keeps the answer's `activeScope`, and `ScopeProvider` narrows the active scope to its location, which the client then sends as `X-Scope-Location` on every request. Proof: `client.test.ts` (an unnamed request carries no scope and no mark), `scope.test.tsx` (the scope narrowed to the one place), the phase 1 e2e (#171) with `fed-stores` and `d101-stores`.
