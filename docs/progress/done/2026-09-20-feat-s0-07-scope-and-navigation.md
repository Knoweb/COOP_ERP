- **S0-07 web shell, step 3 of 5: scope banner, module definitions, navigation (20 Sep, branch `feat/s0-07-scope-and-navigation`).** `shell/scope`: `ScopeProvider` and `useScope()` give the active scope of the signed-in user (entity, location, policy class, whether it can show data at all), worked out from `useSession()` by the plain function `scopesOf`. The token has no `scopes` claim, so a user has exactly one scope and there is no scope switcher; the state is already a list (`available`), and the switcher of doc 30 section 3 comes with the scope assignments of M1 and the claim mapping of K-02. `ScopeBanner` is real and on every page: "who is acting for which entity, all locations, access class", the class always in words because colour is never the only signal; a user with no entity or class NONE gets a warning with `role="alert"` ("you have no scope; you will see no data"), not an empty strip. No entity names before M1, so the banner shows the last eight characters of the entity id (UUIDv7 ids created together differ at the end, not at the start). **Module registration (17A section 7):** `shell/modules/ModuleDefinition.ts` is `{ id, routes, navItems, requiredPermissions }`; a module exports one from `module.tsx` (hello's `routes.tsx` was renamed) and is listed once in `web/src/modules/registry.ts`, which is where the two `new-module:` markers of the router moved to; `router.tsx` names no module any more. `requiredPermissions` means "at least one of": it filters the navigation and guards every route of the module, put on once by the shell (`shell/modules/assemble.tsx`) so a module cannot forget it; a stricter screen wraps itself in `RequirePermission`. A route the user may not open shows a translated "not allowed" screen inside the frame; an unknown address shows "page not found"; `/` shows a one-line start page; a user with no module at all reads that in the navigation. Nav labels are message ids, and a test fails for one that does not exist or leads to a route the module does not have. The hello page hides the form from a user without `hello.greeting.register` and says why (doc 30: disabled actions state why). **Temporary until 19A K-03, in one marked map** (`shell/auth/permissions.ts`): the three development roles get their permissions by hand (fed-admin everything, so a freshly scaffolded module is visible to one user without touching the shell; mpcs-admin read and register; cashier read only).
