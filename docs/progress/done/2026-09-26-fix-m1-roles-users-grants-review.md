- **Roles, users and grants, the review fixes (26 Sep, branch `fix/m1-roles-users-grants-review`).** The wave-1 findings on M1-07, M1-08 and M1-09 and the deep review of M1-09. **Holdings are counted entity-wide** (`m1security/V0013`, `security.user_permissions_at`, a narrow SECURITY DEFINER function like `role_assignment_count`): AssignRole's per-person ROLE-mode check no longer reads the user's assignments under a shop-scoped caller's own policy, which hid the half held at another shop. **The guards that count and then write run under a per-entity lock** (`m1party.internal.security.EntityLock`, `pg_advisory_xact_lock` on the entity id, taken before the facts are read): AssignRole, RevokeRole, SetSodPair, AmendRole and DeactivateUser; two revocations of the last two user managers at once now leave one (proved on two threads). **A template held outside the Federation** keeps `gov.user.manage` and takes no FEDERATION-scope code (`security.template_assignments_outside_federation`, `m1.role.template_held_outside_federation`): AmendRole on a template ran no guard on the people who hold it. **A DEACTIVATED user holds nothing** (`SecurityRecords.assignmentsAt`, `usersHoldingBoth`), so a departed holder of both halves no longer blocks raising a pair to ROLE; **only an ACTIVE user is a user manager** (`UserFacts`, `SecurityRecords.userManagerHoldings`): the resolver grants a PENDING or LOCKED user nothing, so one could not be the other manager who lets the last one go. **No limits is refused where the schema requires one** (`RoleRules.limitsProblem`). **`listRoles` loads every role's permissions in one query.** **A temporary password is NOTIFIED only when a send was accepted**: `kernel.api.Notifications.send` now answers a `Delivery` (the id and what was decided inside the caller's transaction: QUEUED when the row is logged for sending after commit, as #127 made every provider call, SUPPRESSED when a suppression applies, a repeat inside the hour included, FAILED when nothing could be sent), and `TemporaryPasswordDelivery` answers NOTIFIED when at least one resolved recipient's send is SENT or QUEUED, otherwise RETURNED, so a suppressed send never drops a password the provider already replaced. **A kind that loses the back office closes the login** (`UpdateUserHandler`: BACK_OFFICE or BOTH to TILL disables the login and ends the sessions, as DeactivateUser does; back to the back office enables it again through the new `IdentityProviderClient.enableUser`); 21A section 6 names no guard on the kind, so the change is allowed and the login follows it rather than refused. **`username_taken` compares the column as stored** (lower case, `CreateUserHandler`), so the unique index serves it (V0013). **The user, device and grant reads check their x-permission in the controller** when enforcement is on (`gov.user.view`, `sys.device.view`, `gov.external.grant`), the pattern of #120's `CatalogueController`. **Grants (deep M1-09):** `JdbcUserScopes.grantsOf` joins the grantee ACTIVE (deactivation ends a grant; the row stays in the register for the Federation to revoke) and keeps a cache entry no longer than the earliest `valid_until` in it; a token's `grants` claim is intersected with the records and never widens them, and only an EXTERNAL_TIMEBOXED caller has any; `ExternalGrantsIntegrationTest` asserts on `grantsOf`, the path a request takes, for the window, a revocation while cached, an ended grant and a deactivated grantee, and the never-called M1 query `activeGrantedEntities` is deleted with its `GranteeGrants` bean (the `grantee_read` policy of V0009 stays, unread: a merged migration is never edited); `ExternalGrantExpiryJob` logs `not_active` and `not_due` at debug; the M1-09 entry above and the module README no longer say the window is checked "at every resolution" by that query or that `party` has no `ext_view`. **Raised, not changed:** `CR-21A-3`, whether M1 may delete `role_permission` and `sod_pair` rows (V0010 granted it; 21A names `user_role` alone); decided 27 Sep 2026, the three deletes stay (option 1, branch `feat/decisions-m1-rules`), on the architect's delegation. **For the architect:** enforcing a GET's x-permission in the kernel on the generated interfaces rather than per controller;
