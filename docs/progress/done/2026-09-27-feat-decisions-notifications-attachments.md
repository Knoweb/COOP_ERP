- **Notification, attachment and business-date decisions (27 Sep, branch `feat/decisions-notifications-attachments`).** Seven open items of the K-06, K-09, K-10 and K-13 reviews (#97, #125, #127, #132, #137, #139) decided on the architect's delegation and raised as `docs/change-requests/CR-19A-8.md`, accepted; the reasons are in the change request and in Deviations. **Notifications (doc 19 section 7; 19A section 10)**: what a retry needs is sealed, never in clear: `PendingSeal` seals the recipient and the placeholders (M1's temporary password among them) with AES-256-GCM under `coop-erp.notification.pending-key` (base64 of 32 bytes, `COOP_ERP_NOTIFICATION_KEY`; no default outside development, as the idempotency secret; `pending-key-previous` for a key change), a fresh nonce per row and the notification id as associated data, so a value copied onto another row does not open; a row that does not open is failed as "nothing held for the retry". **Migration** `kernel/V0063__sealed_notifications_and_object_cleanup.sql` (lane C, the reserved number): `notification_pending` drops `recipient` and `arguments` and gains `sealed` and `key_id`; `document_attachment` gains `settled_at` (written by the verifier) and `object_deleted_at`; `object_upload` gains `object_deleted_at`; both transition triggers admit that mark as the one change of a settled row, once, on a FAILED row only. **Attachments (19A section 9, 12)**: the upload URL's validity is the register's `attachment.upload_url_minutes` (15; the read URL keeps `presign-minutes`), the verifier's schedule `coop-erp.attachment.verify-cron` (every five minutes); settle-after-expiry stays. A new K-12 job `attachment-cleanup` (nightly, `coop-erp.attachment.cleanup-cron`) deletes the file of a FAILED attachment or module object after `attachment.failed_retention_days` (30), at most `attachment.cleanup.batch_size` (500) of each per run, marks the row, audits `ATTACHMENT_OBJECT_DELETED` / `OBJECT_DELETED` (seeded); `ObjectStore.delete` (S3 `DeleteObject`, repeatable). A COMPLETE or VERIFIED object is never deleted by the kernel. **Confirmed without code**: NFC on every String (19A section 6), no provider adapter in the kernel (M9 builds the EMAIL adapter against Mailpit first), a document with no location takes the calendar date in the business time zone (Javadoc of `BusinessDate` and `IssuanceProtocol`; the order test now asserts it). **Moved**: the A4 renderer is K-06b before M3-10, not M4 (23A's label job prints through it). **Tickets** in `docs/PLAN_TO_M2.md`: 6.13 K-06b renderer, 6.14 settle evidence on "upload complete" (only if M5 needs it), 6.15 module objects nobody refers to. **Proof**: `PendingSealTest` (round trip, no plaintext in the ciphertext, a moved or changed value and an unknown key open nothing, the previous key opens, no key outside development); `NotificationsPostgresIntegrationTest` (the row carries no number and no password while QUEUED, a sealed value moved to another row is given up and reaches nobody, the sweep still sends from what is held); `AttachmentsPostgresIntegrationTest` (the clean-up keeps a failed file inside the retention, then deletes it once, audited, never the COMPLETE one; the mark is the only change and happens once; the upload URL lasts what the register says); `ObjectStoragePostgresIntegrationTest` (the same for a module object, never a VERIFIED one); `SchemaRulesIntegrationTest` (the ledger's UPDATE grant with the mark); `DocumentBasePostgresIntegrationTest` (an entity-level order's business date is its local issue date); the RLS matrix, the unit suite, `check-i18n`.
