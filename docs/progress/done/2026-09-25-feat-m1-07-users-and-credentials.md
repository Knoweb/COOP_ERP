- **M1-07 users and credentials (25 Sep, branch `feat/m1-07-users-and-credentials`, on top of K-02's second pull request).** The user commands of 21A sections 5 and 6 in `m1party/internal/user`, all `gov.user.manage` with MFA in an entity-wide OWN scope (a shop-scoped session is refused, `m1.user.entity_scope_required`), under `/v1/security/users` in the slice (`listUsers`, `getUser` with the new `gov.user.view`; `createUser`, `updateUser`, `resetCredential`, `deactivateUser`). **CreateUser**: home entity the caller's (ADR-18), kind, language, user name (lower case, unique in the federation through `security.username_taken`, a definer function that answers a boolean only), display name, `succeedsUserId` a deactivated user of the entity (doc 21 DR-5); the row PENDING, then the login through `IdentityProviderClient.createUser`, then the subject on `provider_subject`; `USER_CREATED`, `user.created.v1`. **UpdateUser**: name shown, language, kind among BACK_OFFICE, TILL and BOTH (never to or from EXTERNAL); a user who stops working a till loses the PIN; `USER_UPDATED`, `user.updated.v1`. **ResetCredential**: PASSWORD (the provider's one-time password), SECOND_FACTOR (TOTP reset) or PIN; a PENDING or LOCKED user becomes ACTIVE with a new password or PIN (`USER_ACTIVATED`, `user.activated.v1`, beside `USER_CREDENTIAL_RESET`, `user.credential_reset.v1`). The temporary password goes out through `Notifications.send` when M9 holds an ACTIVE rule under the key `user.temporary_password` whose role audience resolves; otherwise it is answered once (`delivery: RETURNED`, `Cache-Control: no-store`), `@JsonIgnore` on the result so the idempotency store never holds it, and a replay answers without it. **PIN policy** (doc 19 section 2.1 and DR-5; doc 21 section 7): digits only, 4 to 6 as the entity sets (`security.pin.length_min`/`length_max`, narrowed never widened), none of the last three (`security.pin.history_depth`), Argon2id through `PinHasher`, the history rotated in `pin_history`; `security.pin.lockout_attempts` (5) and `lockout_duration` (PT15M) are till-visible items for the till to enforce. The five items are typed in `seed/kernel/config-items.yaml` (module m1party, like `m1.bulk.max_rows`) with defaults in `seed/m1party/config.yaml`. **DeactivateUser**: in scope, not deactivated, a reason, not the last entity-wide holder of `gov.user.manage` (as ActivateEntity counts them), not the entity's responsible officer (doc 21 DR-1); status DEACTIVATED, the PIN cleared, assignments kept, the login disabled and its sessions ended; `USER_DEACTIVATED`, `user.deactivated.v1` with `userId`, which empties the kernel's permission and scope caches. **Row-level security** (`m1security/V0012`): a shop-scoped session reads the users with an assignment at its shop or an entity-wide one, not a sibling shop's; an entity-wide one all its entity's users. **Decisions**: the user events carry `appUserId` as well as `userId`, because the outbox skips `userId` when it looks for the aggregate id; activation happens when the platform issues the first credential, since there is no provider callback; `user.updated.v1` is new. **Two defects repaired on the way.** (1) `KeycloakAdminClient` read the target's home entity through `SystemScope.inScope` inside the caller's transaction, which left the connection in the federation viewer's scope; the handler's audit record was then refused (the reset answered 500 in the provider test with the old code). The read now runs in a transaction of its own. (2) A `SECURITY DEFINER` function with `SET row_security = off` fails on a `FORCE`d table ("query would be affected by row-level security policy"), so M1-03's `entity_has_user_manager` and `user_belongs_to_entity` could never have read a user (their tests stub them); V0012 admits the definer with read policies `TO app_seed` on `app_user` and `user_role` and removes the setting from both. **Not here**: "no open till session" before deactivation (waits for M6's query, as in M1-05); the provider's locale when the language changes (the wrapper has no update call); counting till PIN failures and `account.locked_out.v1` (till sync); the operator snapshot (M1-10). **For the architect**: the idempotency filter hashes the request body with plain SHA-256 and stores the hash, so a four-to-six-digit PIN in a reset request can be recovered from `kernel.idempotency_key.request_hash` by trying every PIN; a keyed hash (HMAC with a server secret) would close it, and it is a kernel change. **Proof**: `UsersAgainstTheProviderIntegrationTest` (the done criterion: through the HTTP API against the provider started with `infra/compose/realm-dev.json`, create, then reset, then deactivate, checked after each step as the realm administrator and by signing in: the one-time password is right and must be changed, then the account is disabled; four audit records and four events), `UsersPostgresIntegrationTest` (every guard with its message id and nothing committed; the audit states and events; the PIN hashed with Argon2id and absent from audit and events; the policy's digits, length, the entity's narrower length and the last three; LOCKED unlocked; the last user manager and the responsible officer; the shop-scoped reads and updates; the definer functions; over HTTP the password answered once, never in the idempotency store, and a PIN of the wrong shape refused before the handler without being echoed), `PinPolicyTest`, `TemporaryPasswordDeliveryTest`.
