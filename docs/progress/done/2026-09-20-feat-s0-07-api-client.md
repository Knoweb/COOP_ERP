- **S0-07 web shell, step 2 of 5: the API client (20 Sep, branch `feat/s0-07-api-client`).** `shell/api/client.ts` is the one way the web client talks to the API; a module never calls `fetch`. `useApiClient<paths>()` is `openapi-fetch` over the types `openapi-typescript` generates, so paths, parameters, bodies and responses are checked by the compiler against the slice: a changed slice is a compile error in the web client as it is in the controller. Every request gets the bearer token and `Accept-Language`; a mutating request without an `Idempotency-Key` is refused before it is sent, because a key made up inside the client would be new on every retry. `useIdempotencyKey()` holds the key of one user action: the same across retries, renewed when the server has answered, not after a network error. An error answer becomes a thrown `ApiProblem` with the stable `code`, the translated `title`, and `fieldErrors` for a form (the `errors` list of CR-17A-1); the hello form now shows them under each field. The shell takes the `Problem` type from `web/src/generated/common.ts`, which `make gen-clients` now writes from `common.yaml`, so the shell depends on no module. `helloApi.ts` lost its private fetch code and its hard-coded development scope: what a user sees now follows who signed in (the Federation administrator sees every entity, the MPCS users their own). **Temporary until 19A K-02, in one marked function:** the scope headers the 17A stub reads are derived from the token's claims. Not built: the step-up retry (needs K-02).
