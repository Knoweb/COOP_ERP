- **K-02 identity, first pull request (25 Sep, branch `feat/k-02-identity`, on top of K-03b).** 19A section 2, the token half. **Resource server** (`kernel.internal.security.SecurityConfig`): Spring Security's OAuth2 resource server verifies every bearer token against the provider's JWKS, its issuer and its times; the decoder is built from `coop-erp.security.oidc.issuer` and `.jwk-set-uri`, not from the issuer's discovery document, because inside compose the backend reaches the provider at another address (`keycloak:8080`) than the browser does (`localhost:8085`). A refused token is a 401 problem document `token.invalid` with `WWW-Authenticate` (`ProblemAuthenticationEntryPoint`); health and metrics need no token; no session, no CSRF. **`JwtClaimsMapper`** turns the claims of doc 19 section 1 into the `ScopeContext`: `sub` (a UUID: the platform issues the ids the provider carries), `dev`, `ent`, `scopes` ("entity" or "entity/location"; absent, the home entity alone, entity-wide), `cls` (absent or unknown, NONE), `grants`, `mfa_at` (epoch seconds), `lang` (then Accept-Language, then English); the active scope is the X-Scope-Entity and X-Scope-Location headers, validated by the scope filter against the token's scopes. **`TokenCurrentScope`** replaces `DevCurrentScope`; the scope filter now runs after Spring Security's chain. **The command interceptor** takes the user from the scope and no longer from a header: a command with no user is `scope.required`; a stale second factor is now 401 `mfa.required` with the provider's step-up address (`coop-erp.security.oidc.step-up-url`) in the problem's params, for the web shell's retry (17A section 7). **`PinHasher`** (`kernel.api`, `Argon2PinHasher`): Argon2id, 64 MB, three iterations, parallelism two, 16-byte salt, 32-byte hash, as a PHC string. **`IdentityProviderClient`** declared in `kernel.api` with CR-19A-1's signature; its implementation is the second pull request. **The dev realm** gives its four users fixed ids, so the token's `sub` is the platform's user id, and `seed/m1security/users.dev.sql` gives each a development role with every permission of the catalogue in its home entity; **compose now enforces permissions** (`COOP_ERP_ENFORCE_PERMISSIONS`, default true there, off elsewhere), and the smoke test registers as the seeded MPCS administrator. **Until the second pull request** a request without a token still names its user in the development headers (`coop-erp.security.dev-headers`, true by default, to be deleted with the headers on both sides, `DevScopeContextProvider` and `DevStubsGuard` with them); a request without either gets no user and no scope. **Not here**: the provider mapper endpoint that puts `scopes` and `roles` into the token from M1's assignments, `KeycloakAdminClient`, device authentication (`DeviceAuth`, `DeviceCredentials`), the web shell's step-up round trip, the deletion of the headers. **Proof**: `TokenAuthenticationPostgresIntegrationTest` (a provider of its own: a key pair, a JWKS on a local socket, tokens signed in the test, permissions enforced; a valid token runs the command as the token's user and another user is refused 403; the token wins over the development header; a token signed by another key, an expired one, one from another issuer and one that is not a JWT are 401 `token.invalid` as problem documents; without a token the development headers still name the user and without either the command is `scope.required`; health needs no token), `JwtClaimsMapperTest` (every claim of the table; the home entity as the only scope; the header's choice among several; unknown class NONE; the language order; the correlation header; a subject that is not a user id refused), `Argon2PinHasherTest`. `make e2e` (the browser signs in for real and the backend verifies the token) is the net for the local stack.
