- **Kernel change requests about the documents, not the code, decided (27 Sep, branch `docs/decisions-kernel-crs`).** On the architect's delegation: seven document/code CRs raised while preparing 19A (branch `chore/19a-kernel-prep`, #61) were checked one by one against the code that has since shipped and decided. **`CR-18-1`** (partitioned-table primary keys, no foreign key out of the kernel schema) — accepted: `kernel.audit_event`/`kernel.event_outbox` already carry `PRIMARY KEY (received_at, id)` and plain `uuid` scope columns; PostgreSQL and the layering rule leave no other buildable shape. **`CR-19A-1`** (most published `kernel.api` types named without signatures) — accepted: every type has a signature in the code, built and reviewed through K-02 onward; the re-issue of 19A takes them from there. **`CR-19A-2`** (idempotency table, no `DELETE`) — accepted: K-03a built `kernel.idempotency_key` day-partitioned, retention by `IdempotencyPartitionJob` dropping partitions with the migrator's rights, no `DELETE` grant anywhere. **`CR-19A-3`** (a sequence cannot give dense outbox numbering) — accepted: `OutboxWriter` uses a sequence for `central` (a total order, not density, is what a consumer needs), `DeviceEventWriter` keeps the till's own dense sequence; the `GapCheckJob` this implies does not exist yet, so it is added as a follow-up (`docs/PLAN_TO_M2.md` 6.10). **`CR-19A-4`** (the sync slice breaks three slice rules) — accepted as revised: `openapi/sync.yaml` needs no `x-auth: device` exemption because it already satisfies every rule as built (`/v1/sync/...` paths, a real `Idempotency-Key`, a device-marker `x-permission` value); confirmed by reading `tools/check-slices.mjs` and `tools/check-permissions.mjs` directly and adding a case to `tools/checks.test.mjs` rather than changing either tool. **`CR-19A-5`** (the relay role has no login path) — accepted: `coop_relay` (member of `app_relay` only) exists in `infra/compose/postgres/init/01-roles.sh`, created by the role script and never a migration, with its own data source. **ShedLock's naive-UTC columns**, versus 19A §12's `timestamptz` (#125, kernel V0057) — accepted: ShedLock's own PostgreSQL provider dictates the column type; the 19A DDL is what should move. Every decision is recorded on the change request itself (or, for ShedLock, on its existing PROGRESS Deviation) with the reasons; none of doc 18, 19A or 17A is re-issued by this pull request. **`docs/change-requests/README.md`** (new) lists every accepted-but-not-yet-reissued change request, grouped by document, so the next re-issue of 17A, 18, 19A, 21A or 28A picks all of them up in one pass. No Java or migration changed; `make reset` not needed. **Proof**: `node tools/check-slices.mjs`, `node tools/check-permissions.mjs`, `node --test tools/checks.test.mjs`.
