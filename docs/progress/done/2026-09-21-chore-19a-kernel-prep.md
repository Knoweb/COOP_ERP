- **Preparation for the 19A phase (21 Sep, branch `chore/19a-kernel-prep`).** Nothing here implements a kernel service; it is what has to exist before four lanes start K-01 to K-13 at once without colliding. Four things. **(1) The version catalogue** names the libraries the kernel tickets need, so no two lanes edit `libs.versions.toml` on the same day: the OAuth2 resource server starter (K-02), Caffeine (K-03, K-11), the AMQP starter (K-05), ICU4J 78.3 (K-06), the AWS SDK v2 `s3` client and its bill of materials 2.55.1 (K-09) and ShedLock 6.10.0 with its JDBC-template provider (K-12). Every version was checked against Maven Central. The four Spring Boot manages carry no version, as the catalogue header requires; ShedLock is the latest of the 6 line and not of the 7 line, because 7 is built against Spring Framework 7 (Spring Boot 4) and this repository is on Spring Framework 6.2, and `.github/dependabot.yml` now holds ShedLock majors for that reason, the only change the automation needed. The S3 client is the AWS SDK and not MinIO's own client: 19A §9 asks for a provider-neutral client with path-style addressing, which is what MinIO needs and what the same code gives anywhere else, and AGENTS.md forbids coupling to a vendor for exactly this. **Nothing was added to the application's dependencies.** The two starters must not be: the resource server brings Spring Security, whose default chain answers 401 to every endpoint, and AMQP brings a connection factory and a health indicator that turns `/actuator/health` DOWN where no broker runs. The other four are inert, and were still left out, because adding a dependency that nothing uses changes the bill of materials and the vulnerability scan and proves nothing. **(2) Three declarations in `kernel.api`**: the annotation `@EventConsumer` (K-05), `PermissionResolver.allows(...)` (K-03b) and `Sod.assertDistinct(...)` (K-03b), each with no implementation and no bean, so the context starts as before. Only what 19A writes out was declared; everything it names without a signature was left alone and listed for the architect, which is most of the service map: `IdentityProviderClient` and `DeviceCredentials`, `TextNormaliser` and `Formats`, `DocumentService`, `NumberingService`, `DocumentLinks`, `Attachments`, `SyncApi`, `NotificationDispatcher` and `NotificationChannel`, `SnapshotContributor` and `SnapshotChangeLog`, `@ScheduledJob`, and the `Resolved` and `Limits` types of `PermissionResolver`. Three differences between 19A and the code were found and none was fixed here: 19A §1's `ScopeContext` has no `activeScope` component and a `String lang` where the code has a `Locale`; 19A §6 has `Messages.t` return a `Text(value, fallback)` where the code returns a `String`; 19A's service map puts `BrokerAdapter` in `kernel.internal`, which is right, while AGENTS.md names it beside `IdentityProviderClient` as though both were published. **(3) Migration number ranges** per lane, in a new `db/migration/kernel/README.md`: V0010–V0029 security, V0030–V0049 ledgers and events, V0050–V0079 configuration, documents and jobs, V0080 and up language and sync. Only `V0001__baseline.sql` exists, so nothing collides. The README is safe in that folder: Flyway ignores files that do not match the migration naming, and `tools/check-schema-ownership.mjs` reads `.sql` files only; both were checked. **Measured, not assumed:** `FlywayConfig` runs with `outOfOrder = false` and `validateOnMigrate = true`, and a probe against PostgreSQL 16 showed that a V0010 merged after a V0030 has been applied does not run and is not skipped quietly — `migrate()` throws `FlywayValidateException: Detected resolved migration not applied to database: 0010`, and because `FlywayConfig.migrate()` is a `@PostConstruct` the application does not start. A fresh database is never affected, so the pipeline would stay green while developer machines stop working. The setting was not changed; it is in the pull request for the architect. **(4) `KernelRecorder` no longer names a stub.** It was tied to `LoggingAuditFacade` and `LoggingEventPublisher`, so K-04 and K-05 would have broken all twenty-eight integration tests at once. It is now a plain recorder, and the new `KernelRecording` (a `BeanPostProcessor` in the test support package) wraps whichever bean implements `AuditFacade` or `EventPublisher` and reports to it. The real service still runs first, with every refusal it makes; `@Primary` is gone, so a real implementation may carry it. Every assertion means what it meant.
