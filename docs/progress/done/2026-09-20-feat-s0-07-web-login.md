- **S0-07 web shell, step 1 of 5: login and session (20 Sep, branch `feat/s0-07-web-login`).** Before this the shell had a login configuration and nothing that ever started a login; the scope banner, the API client, the navigation and twelve components are one-line stubs, and only i18n and the hello page were real. The ticket is built in five pull requests (login; API client; scope banner, module definition and navigation; design tokens, fonts and the first three components; Playwright and the e2e stage). This one: `RequireLogin` around the whole application sends an anonymous visitor to the identity server (authorization code with PKCE, S256) and brings them back to the page they asked for; it never retries a failed login by itself. Tokens live in memory only (doc 30 section 3), renewed in the background; a reload is answered by the identity server's own session without a form. `useSession()` is the one way the client learns who is signed in (user, home entity, policy class, language, roles, from the access token's claims; anything missing falls to the safe side: no entity, class NONE, English). The language of the screen now follows the user's `lang` claim, then `?lang=`, then English. `UserMenu` shows the name and signs out. Decided by the architect for the whole ticket: react-router 6 to 7 and react-intl 6 to 12 now (both went in without a code change; `pnpm audit` reports no known vulnerability for the first time), Keycloak stays on 25 until the login exists and is tested, `openapi-fetch` inside the API client (step 2), the headless component library (open item E-03) waits for M1's first forms. Component tests arrive with this step: jsdom and Testing Library. **Temporary until 19A K-02, and said so in the code:** the backend does not validate the token yet and still reads the scope from the development headers, so from step 2 the client sends the bearer token and headers derived from the token's claims. Deferred with reasons: the scope switcher (the dev realm has no `scopes` claim; needs M1), the step-up dialog (needs a backend that issues the challenge). Verified: 15 web tests, lint, build; on the running stack an anonymous visit to `/hello` lands on the Keycloak sign-in page with `code_challenge_method=S256`; `make smoke`. Typing the development password into the form was left to a person, and to the Playwright test of step 5.
