- **Notifications, attachments and i18n, the review fixes (26 Sep, branch `fix/notifications-attachments-review`).** The review of K-10, K-09 and K-06 (#96, #97, wave 1 and the deep review of 26 September). **Notifications** (doc 19 section 7; 19A section 10). *Retries every instance can run*: what a retry needs and the log must not hold (the recipient, the placeholders) is held in `kernel.notification_pending` (`kernel/V0059`, lane C: it references `notification_log`) until the row is settled, then cleared (never deleted); the log keeps the hash alone (ADR-27). *Sends after the commit*: `NotificationService.deliver` queues and suppresses inside the handler's transaction and sends from its after-commit callback, so a slow or failing provider never rolls back a handler or the recipients sent before it; the dispatcher skips a recipient it cannot serve (no adapter for the rule's channel) and says so, instead of throwing into the consumer and having the event redelivered. *Each attempt is claimed* (`NotificationLog.claim`: a conditional UPDATE that counts the attempt and holds the row for the longest backoff) in a transaction of its own (`NotificationTransactions`, REQUIRES_NEW), the provider is called in none, and the outcome is written in another; a sweep that outlives its lock and the next sweep never send one row twice. *The retry re-checks* the kill switch, the quiet hours and the hourly de-duplication before it sends, as 19A says. *The hourly de-duplication* compares the dedup key (the event id) with the recipient and the template, as the `Notifications.send` Javadoc says; two deliveries twenty minutes apart are two alerts. The sweep takes at most `notification.retry.batch_size` rows (new register item). **Attachments** (19A section 9; doc 32 section 4). *Nothing settles while the pre-signed PUT is valid* (`upload_expires_at`, `kernel/V0058`): the verifier offers a PENDING row only after its window ended, so the bytes it hashed cannot be replaced with the same URL; *a settled row never changes* (trigger `document_attachment_transition`, PENDING to COMPLETE or FAILED only) and no new URL is issued for it (`attachment.not_pending`). *Presign is idempotent per attachment id*: asking again for a PENDING row of the same document renews the window and the URL (a till that lost its connection, doc 32 section 4); another document's row is `attachment.document_mismatch`. *Limits from the register*: `attachment.max_bytes` (a declared `content_length`, new optional field of the sync slice, is refused above it and signed into the URL; the verifier fails a stored object above it before reading it) and `attachment.content_types` (jpeg, png, webp, pdf; refused with `attachment.content_type_not_allowed`); `content_type` is stored, and a read URL of anything but an image carries `response-content-disposition=attachment`. *A counterparty is told* `attachment.document_not_owned` (`kernel.document_owned` before the insert) instead of a bare database error. The verifier reads at most `attachment.verify.batch_size` rows, settles each conditionally (nothing audited or published on zero rows), and its lock outlives its runtime by twenty minutes. *No default credentials*: `OBJECT_STORE_ACCESS_KEY` and `OBJECT_STORE_SECRET_KEY` have no default in `application.yml` (compose passes MinIO's); unset, the store logs an ERROR at start and every call fails with a clear message. **i18n** (doc 19 section 5; 19A section 6). Real plural and select forms in the si and ta fixtures, with the fallback mark through a plural proved; `tools/check-i18n.mjs` compares the named ICU arguments of the three texts (inside plural and select branches too) and scans `messages.text(` as well as `.t(` and `new ProblemException(`; `NfcConverter` normalises and no longer strips (`TextNormaliser.nfcOnly`; `nfc` keeps stripping for typed text at a handler); `CollationPostgresIntegrationTest` proves in PostgreSQL that the equivalent spellings are two values that sort adjacent and one value once normalised, and that the collations' `collversion` matches `pg_collation_actual_version`; `SearchSupport.comparator` is the ICU4J collator of the display language, sorting the test set as PostgreSQL does; `SearchSupport.orderByDisplayLanguage` puts the untranslated rows after the translated ones (`(x_si IS NULL), x_si COLLATE ..., x_en COLLATE ...`; the `coalesce` put Latin before Sinhala); `moneyWithCurrency` writes `Rs` in every language (doc 19 section 5.1); `IcuMessages` throws on an id no catalogue has when `coop-erp.i18n.strict-missing-ids` is on (the integration tests set it) and caches one `MessageFormat` per language and id, cloned per call. **Not here**: binding the notification consumer to the event types with active rules only (M9, which owns the rules, does not exist; the consumer stays on `#` with an early return per event, and the rebind on `notification_rule.changed.v1` is described in the pull request); a distinct "id shown" flag on `Messages.Text` (an api change for the architect); the retire and lifecycle of attachments (below). **Deviations**: the pending table, the converter's marker type and the settle delay, below. `make reset` is not needed (two plain new migrations). **Proof**: `NotificationsPostgresIntegrationTest` (a retry served from the table and cleared once sent; the kill switch re-checked; a claimed row left alone; a recipient without an adapter not stopping the others; the dedup key), `AttachmentsPostgresIntegrationTest` (no settle inside the window; the trigger; the renewed URL; the mismatch; the size and type limits; the download disposition), `S3ObjectStoreIntegrationTest` (a signed length refused; the disposition header), `CollationPostgresIntegrationTest`, `IcuMessagesTest`, `FormatsAndSearchTest`, `RlsMatrixIntegrationTest`, `tools/checks.test.mjs`, and the unit, sync, hello, config, schema and job suites.
