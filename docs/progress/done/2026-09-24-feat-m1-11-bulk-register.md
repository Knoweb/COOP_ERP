- **M1-11 BulkRegister (24 Sep, branch `feat/m1-11-bulk-register`).** `POST /v1/party/bulk-register` (21A section 5, multipart; section 8, the "Bulk upload" button of the society register) takes a CSV of entities and answers a `ValidationReport`. Every row is validated first (the shape rules of the slice, applied by `RowValidators` because a CSV row has no schema; a code repeated in the file; a code already in the register) and **when any row fails nothing is registered**: the report says which rows and why, with a `bulk.*` message id per problem, and the file is corrected and sent again. When every row passes, all are registered in one transaction, each with its audit record and its `entity.registered.v1`, through the same rules as a single registration: `EntityRegistrar` now holds the rules and the entity they produce, and both handlers write, audit and publish themselves, because the build's rules keep those in the `@CommandHandler` (and a handler never calls another: the kernel's interceptor claims the request's key around each). The row limit is the configuration item `m1.bulk.max_rows` (seed, 500). **Two things outside M1 had to change:** the kernel's `IdempotencyFilter` read the whole body for its hash and left nothing for the container's multipart parse ("Required part is not present"); for a `multipart/*` request it now hashes the parts and passes the request through. And `EntityRepository` and three accessors of `Entity` are public within `internal`, for the `bulk` package 21A section 3 names. Proof (`BulkRegisterIntegrationTest`, over HTTP as the Federation): a bad row registers nothing and is reported by line and column; a good file registers every row with an audit record and an event each; a code already registered is reported; a missing column and an empty file are refused; an MPCS cannot; forty societies register in a small fraction of the sixty seconds 21A section 11 allows. The screen is M1-12's; the generated web client carries the operation.
