- **M1-05 locations and till positions (25 Sep, branch `feat/m1-05-locations-and-positions`).** The location and position commands of 21A section 6 on the K-07 numbering service. **Commands** (`m1party/internal/location`, one `@CommandHandler` each, audit and event in the transaction): RegisterLocation (owner = the caller's entity, acting entity-wide; owner ACTIVE or ONBOARDING; code unique in the owner; PLANNED; the language defaults to the entity's), UpdateLocation (names, address, district, map position, language, trading hours, size band; code and type never change, the code being part of every document number), ConfirmLocationConnectivity (the gate of doc 21 section 3.3, once, the audit record says who), StartLocationOnboarding, ActivateLocation (connectivity met; for a SHOP a primary till and at least one operator, a TILL or BOTH user with an assignment at the shop), MarkLocationDormant (reason), ReactivateLocation (connectivity met), SetPrimaryTill (MFA; position of this location, ACTIVE; reason), RegisterTillPosition (SHOP only; number unused, retired ones included), RetireTillPosition (no device at it). **NumberingService hooks** (`SeriesHooks`, which types from the kernel's document type registry): a shop gets its LOCATION series (CNT, GRN, RPK, WOF, XFR, prefix `M905-S01-GRN`) on registration, a warehouse or an office none (their types number from the entity's series); a position gets its TILL_POSITION series (CPR, RCT, prefix `M905-S01-T1-RCT`) in the same transaction, which is the "done when" of the ticket; SetPrimaryTill moves the location series' counters to the device at the new primary till (`holderChange`, `series.holder_changed.v1` from the kernel) and moves nothing while no device is there; retiring a position closes its series. **Queries** (`PartyQueries`): getLocation, listLocations (status, type, cursor), listTillPositions (with the primary flag), all under row-level security only. **Schema** (`m1party/V0005`): V0001 already had both tables and their OWN and FEDERATION_VIEW policies; added are a composite key so a position's owner is its shop's owner, a composite key so the primary till is a position of the same location, and `ext_view` on both tables. **Slice**: thirteen operations under tag `Locations`; web client regenerated. **Events**: `location.registered/updated/onboarding/activated/dormant/primary_changed.v1`, `till_position.registered/retired.v1`, the location named `registeredLocationId`, `activatedLocationId` ... as the kernel's `LocationDayClosed` does, because the outbox reads `locationId` as the place of an event. Ten audit types, twenty message ids in three languages. **Decisions to note:** 21A section 3.3's `prt.location.register`, `.activate` and `.primary` are added to the catalogue next to `prt.location.manage`/`.view` (whose removal is `CR-21A-1` item 1's); update uses `.register`, and onboarding, dormant, reactivate and the connectivity gate use `.activate`, since doc 21's `prt.location.onboard` and `.dormant` are not in 21A's catalogue; UpdateLocation, ConfirmLocationConnectivity and `location.updated.v1` are not named by 21A or doc 21 section 5.3 and are added so that hours, language and the gate can be set at all; RetireTillPosition refuses the shop's primary till (the location series would be held at a position that no longer exists); the operator and primary-till gates apply to a SHOP only. The dev seed (`seed/m1party/locations.dev.sql`) adds shop S01 (PLANNED) and warehouse W01 (ACTIVE) to the development MPCS, and no positions: a position's series are in the kernel's schema, which an M1 seed may not write, so positions are registered through the API. **Not here:** "no open till session" for MarkDormant and RetireTillPosition (an M6 query; M6 does not exist), "device staged" for StartOnboarding (M1-06 and doc 31), device assignment and the counter transfer on it (M1-06), the location part of the till snapshot (K-08, M1-10), PARTY's ship-to names (a projection, with M4's drops), the permission and MFA checks themselves (K-03b). **Proof** (`LocationsPostgresIntegrationTest`, 19 cases as the application user, and `TradingHoursTest`): a shop is registered PLANNED with its five location series, audited and published; a warehouse gets no series; every guard of RegisterLocation, RegisterTillPosition, SetPrimaryTill and RetireTillPosition refuses with its message id and commits nothing; a position is registered with its two till series in the same transaction; the life cycle goes PLANNED, ONBOARDING, ACTIVE, DORMANT, ACTIVE only through its gates; naming the primary till moves the five counters to its device, or none when there is no device; retiring closes the series and the number is never reused; the database refuses a primary till of another location; a shop-scoped caller sees and changes its own shop only and still registers a till there; the Federation view reads every location and writes none; an external grant reads its entities' locations; over HTTP a shop and a till are registered, a malformed code is a 400 and a repeated till number a 422 with its code.
