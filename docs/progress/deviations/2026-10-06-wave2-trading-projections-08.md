- **M8's projections per shop and per event, sales by item, the dashboard cache, exposure and exports (branch `fix/m8-projections-per-shop-and-event`), where `2026-10-06-wave2-trading-projections.md` (1) to (7) and CR-28A-2 met code they did not foresee:** (1) **The location of a row the event does not place.** The consumer runs in the publishing session's scope, at its location (`EventConsumerDispatcher`, from the outbox), so "entity-wide" is not guaranteed: a row left NULL in a shop's scope would be refused by the new `own_write` and the event dead-lettered. `TradeProjection` takes the location the event names for its owner (GRN, discrepancy, claim, delivery note), else the location an earlier event of the same document on the owner's side named (a delivery note's dispatch follows its issue), else the publishing session's; orders, invoices and payments are published entity-wide (kernel V0061 keeps a shop session off those documents), so they stay NULL as decided. (2) **`credit_limit_fact` has owner, counterparty and location columns** beyond CR-28A-2's list, so the four-class template applies as written: the owner is the publisher, the other party reads it through `party_read`, and the location is NULL (a relationship is the entity's), which keeps limits out of a shop session. (3) **The exposure queue has no field for the step reached**: `ExceptionItem` and the OpenAPI slice are unchanged; the queue lists a pair once its ratio reaches the lowest step of `trading.exposure_warn_thresholds` (read in the caller's scope) and shows the ratio as the percentage, which tells the reader which steps it passed. (4) **A CSV export by a class that writes nothing is refused** (`m8.export.own_required`): the audit log and the outbox accept OWN scopes only (kernel V0053), so a FEDERATION_VIEW or EXTERNAL caller could not leave the `REPORT_EXPORTED` record decision (7) requires; no template of those classes holds `rpt.export.run`, so nobody loses an export today. (5) **`report.exported.v1`** is published with the audit record: the build requires every command handler to publish (`ArchitectureTests.handlersAuditAndPublishRule`); it carries the report, the period, the location and the row count, no row content. (6) **Old shop sale lines are numbered in the migration**: rows projected before V0007 have a `line_id` and no number, and `(receipt_id, line_no)` cannot be a key over nulls, so V0007 numbers them by `line_id` within the receipt, lifting the table's `FORCE ROW LEVEL SECURITY` for that one statement (the migrator owns the table but is not a superuser); quantities and totals are unchanged, the till's own numbers return with a rebuild (M8-05). (7) **The current limit is the pair's latest event**, by (occurred_at, event_id) per (seller, buyer), not by `effective_from`: an amendment is a new relationship row, and M4 recomputes its own warning on the same event.
