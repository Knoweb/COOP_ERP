- **A shop writes only at its own location (27 Sep, branch `fix/decisions-rls-followups`; `docs/PLAN_TO_M2.md` 6.12):** the template's `own_write` had no location line and `own_update`'s WITH CHECK none either, so a session scoped to shop A could insert a row at sibling shop B of its entity (an audit record, an event, a quarantined fact, a day-close row, a location) or move one there, and not read it back. **Decided 27 Sep 2026: the template's `own_write` and `own_update` WITH CHECK carry `own_read`'s location line, applied to every existing table with a location (kernel V0064 and V0083, m1party V0012), on the architect's delegation.** Options weighed: leave writes entity-wide and rely on the handlers (17A section 6.3 and 19A section 1 show `own_write` without the line; cheapest now, but a handler that takes the location from a request instead of the scope writes at a sibling, and the matrix could not tell); add the line table by table when a module asks (the leak stays the default for every new table); add it to the template and every table (chosen). Reasons: doc 18 section 3.7 gives OWN the rows "where owner = scope entity (and location when the assignment is location-scoped)" and M-05 says a shop sees nothing of a sibling shop, and a row a shop can write but not read is the same leak turned round; `kernel.document` already had it (V0061); the kernel writers take the location from the session's own scope (`AuditFacadeImpl`, `OutboxWriter`) or the device's shop (`DeviceEventWriter`, `EventApplier`), so nothing that works today changes; relaxing one table later is one `ALTER POLICY`, finding forged rows is not. An entity-wide session still writes anywhere in its entity. **One departure:** `kernel.numbering_series` admits `location_id IS NULL` on insert too, as it did on read and update (V0055, V0061): a shop creates the ENTITY series its document draws from (24B). **For the modules still to build** (nothing in the guides writes at another location from a shop session): M4's GRN is confirmed at the receiving location, and a discrepancy raised inside it carries that location (already noted above for `kernel.document`); M5's transfer is issued entity-wide (`inv.transfer.issue` ENTITY) and received at the destination as a new receipt document there (`shop.transfer.receive` LOCATION, 25A section 6.3), so the receive must not update the source-side transfer rows from the destination's session: either the transfer's state follows from `transfer.received.v1` in an entity-wide consumer, or the rows the destination writes carry the destination. M5's developer decides which when building the transfer, against `RlsMatrixIntegrationTest`.
