- **Extension rows after a document is issued (wave 2: RLS-09, RLS-11), decided on the architect's delegation (6 Oct, branch `docs/wave2-decisions`):** (1) **The rule**: an extension row of a document (a module's `doc_*` table keyed on `document_id`) is written before the document is issued or in the transaction that issues it, never later; the columns a handler specification writes after issue are named per table in the grant and keep their own `document_update` policy (`doc_order_line.cancelled_qty`; `doc_delivery` dispatch columns and `doc_delivery_drop` proof-of-delivery columns; `doc_invoice.settled_amount` and `credited_amount`, caches recomputed from links; the three `print_object_key`s). `trading.claim_photo` follows `kernel.document_attachment`: photographs may be added to an issued claim. Recorded in `RLS_POLICY_TEMPLATE.md` under "The rows of a document" and in the M4 README. (2) **The mechanism**: kernel V0086 adds `kernel.document_open_for_write(p_document_id uuid) RETURNS boolean`, SECURITY INVOKER, STABLE: the header is unissued, or its `xmin` equals the current transaction's id (`pg_current_xact_id()::xid`; fallback `d.xmin::text::bigint = txid_current() & 4294967295` if the cast is refused; the kernel test proves one of the two), so "issued in this transaction" is a fact the database knows without a session variable (which the template forbids) and without trusting a clock. m4trading V0010 adds the test to `document_write` WITH CHECK on the fourteen extension tables and to `document_update` on `doc_grn` and `doc_grn_line` (both written in the confirming transaction), plus a `BEFORE INSERT` trigger with the same test on `doc_grn_line` alone (its rows are money and stock, so the rule holds for every role, as V0055 did for `kernel.document_line`). `payment_allocation`, `cheque`, `cheque_outcome`, `invoice_dispute`, `claim_decision(_line)`, `discrepancy_settlement` and `claim_return` are the other party's own rows or insert-only facts about an issued document, not extension rows, and are out of scope. (3) The same migration recreates `party_read` on `trading.claim_return` with the owner-side location line of the template (CR-17A-3; `kernel.document` V0055 item 4). Rejected: the verifier's plain `document_unissued` test (it breaks nine handlers that issue and then write their row in one transaction, and for the GRN it is impossible: the synthetic batch number `S-<GRN number>-<line>` exists only after the number is drawn, CR-24A-1 item 4); reordering those handlers (large, and the kernel's protocol issues last for a reason, V0055 item 1); a session variable (template rule); comparing `issued_at` with the clock (Java clocks, fixed in tests). Caveat proved by the test: a savepoint gives a tuple the subtransaction's xid; Spring's default propagation opens none and `inOwnTransaction` opens a connection, not a savepoint.
