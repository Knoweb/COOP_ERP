- **The Federation is unknown to the database (26 Sep, branch `fix/m2-01-schema-review`):** 22A section 3's `shared_read ON catalogue.sku USING (status = 'SHARED')` trusts the status column, so an entity that set SHARED on its own row (nothing in SQL stops `own_update` from doing it) would publish it federation-wide; the review asks the policy to require the Federation as owner. The Federation is the entity `coop-erp.system.entity-id` names, a Spring property (`SystemScope`, `FederationCaller`, `M2SeedLoader`); no table, function or configuration row of the kernel carries it, so neither a policy nor a check trigger can ask for it, and a session variable is what the RLS template forbids. The handler guard of `FederationCaller` (#120) was the only defence. Decided 27 Sep 2026: `kernel.system_entity()` over the one-row table `kernel.system_identity`, written on every start from `coop-erp.system.entity-id` by `SystemEntityRecorder` as the migrator (kernel V0061), and `catalogue.sku`'s `shared_read`, `own_write` and `own_update` require the Federation as owner of a SHARED row (m2catalogue V0006); `FederationCaller` stays as the handler guard (branch `feat/decisions-rls-federation`), on the architect's delegation. Reasons: the property is already the one name the platform acts under, so the table is its copy and cannot disagree with the Java guards; a kernel function is callable from every module's policies without a sideways dependency (M2 may not read `party`); a missing row returns NULL and admits nothing; rejected: reading `party.federation_identity` (M1's table, visible only to the Federation's own scope, and a second source of truth), a configuration row (changeable through the API), a session variable (forbidden by the template). `party.federation_identity` stays under M1's `federation_*` policies until the follow-up in `docs/PLAN_TO_M2.md` folds it into the kernel function. **Folded 27 Sep 2026 (6.11, branch `fix/decisions-rls-followups`), on the architect's delegation:** M1's `federation_*` policies (m1party V0012) and the five m1security functions (V0016) ask `kernel.system_entity()`, and the table `party.federation_identity` and its trigger are dropped (m1party V0012); the name is kept as a view of `kernel.system_identity` granted to no role. Options weighed: keep the table beside the function (two copies that can disagree when the property names another entity than the FEDERATION row, the reason the decision above rejected reading it); drop the name outright (cleanest, but impossible: on a fresh database the whole m1party stream runs before m1security, whose V0010 creates a LANGUAGE sql function naming the table, which PostgreSQL resolves at creation, and rule R4 (`tools/check-schema-ownership.mjs`) keeps a drop of a party object out of m1security); keep the name as a view of the kernel's row with no grant (chosen: nothing reads it after m1security V0016, it cannot disagree with `kernel.system_entity()`, and it is dropped the day V0010 is squashed in a baseline). A departure from the plan's wording: the M1 tests that register their own Federation name it for the test through `PostgresIntegrationTest.theDatabaseNamesTheFederation` instead of setting `coop-erp.system.entity-id`, since a property of their own would start one more cached application context per class. M1's handler guard (`FederationCaller`, by the caller's `entity_type`) stays; in production the property and the FEDERATION row name the same entity, and if they ever did not, the policies refuse (fail closed).
