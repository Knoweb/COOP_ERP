- **Notification delivery (wave 2: TWK-21, TWK-22, M9-08, M9-09, M9-10, M9-11; the recipient hash is in `2026-10-06-wave2-keyed-hashes.md`), decided on the architect's delegation (6 Oct, branch `docs/wave2-decisions`), CR-19A-12:** (1) **Quiet hours defer; they never suppress** (TWK D-7 = M9 D6, one fix in the kernel). `NotificationSuppression` returns `Suppress(reason)` for the kill switch and the hourly duplicate, or `Defer(until)` = the window's end in the business zone (today or tomorrow); at queue time the hold is written, `next_attempt_at = until`, the row stays QUEUED and no after-commit attempt is registered; at retry time `NotificationLog.defer(id, until)` sets `attempts = attempts - 1, next_attempt_at = until` (a deferral is not an attempt) and the hold is kept. `MAX_AGE` (24 h from `created_at`) needs no exemption: a window is under 15 hours and the three backoffs add 21 minutes; a `ConfigValues` validator refuses a window longer than 15 hours, and an unparsable window is "no quiet hours" with a WARN, never a throw past the dispatcher. The window is read for the **recipient's entity** when the audience resolver knows it (`Recipient.entityId`, ROLE_AT_COUNTERPARTY gives the counterparty), else the event owner's: doc 19 section 7 says "per recipient", M1 keeps nothing per person, so the entity is the nearest owner of the setting; a distributor must not decide when a society's phones ring. The log screen shows a QUEUED row with a future `next_attempt_at` and `attempts = 0` as "deferred (quiet hours) until 07:00"; no new status. Doc 19 section 7 and doc 29 section 6.4 ("deferred to 07:00") govern; 19A section 10's test name "quiet-hours suppression" is wording, corrected at re-issue. Rejected: suppression (an evening bounced cheque would never reach the society); the sender's window; a per-rule "drop if deferred" flag (no v1 template needs it). (2) **Provider text never reaches the log or the audit** (TWK-21 = M9-10): `last_error` and `after.error` carry `failure.getClass().getSimpleName()` plus a category the channel adapter maps (`REJECTED`, `TIMEOUT`, `AUTH`, `UNKNOWN`), or a `ProblemException`'s message id, never `getMessage()`; the full text goes to the application log at DEBUG with the notification id; `SmsChannel` wraps as SMTP does and the `SmsGateway` javadoc says an exception message must carry neither recipient nor body; a unit test makes a gateway throw `+9477...` and asserts it is nowhere. (3) **SMTP** (M9-09, M9-11, M9 only, before the first relay that is not Mailpit): `Message-ID: <{notificationId}@{domain of coop-erp.integration.smtp.from}>` set before send so a retry is the same mail to Gmail-class clients; `coop-erp.integration.smtp.{username, password, security = NONE | STARTTLS | SSL}`, `starttls.required` and `ssl.checkserveridentity` on, the password from `COOP_ERP_SMTP_PASSWORD` only, and a start refused with `NONE` and a non-local host unless the issuer is a development one (the `PendingSeal` rule); the variables go into `infra/deploy/.env.example`.
