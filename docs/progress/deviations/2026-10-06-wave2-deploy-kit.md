- **The deployment kit (wave 2: DEPLOY-01 to DEPLOY-18, TWK-18's Caddy half, PR #247), decided on the architect's delegation (6 Oct, branch `docs/wave2-decisions`):** the kit serves a public demo on one small server (about 80 testers on about 20 role users) and later becomes the template for staging and go-live; each item below says which. (1) **D-1: the demo runs explicit commit SHAs of main, chosen by the operator.** `deploy.sh` runs from the clone only (`cd ~/COOP_ERP && git pull --ff-only && sudo ./infra/deploy/deploy.sh`; it fails when `REPO_DIR` is empty and is no longer copied into `/opt/coop-erp`), pins `IMAGE_TAG` to the clone's HEAD after `docker manifest inspect` finds all images in GHCR (else: "CI has not published this commit yet"), writes `IMAGE_TAG` and `PREVIOUS_IMAGE_TAG` into `.env` (so `demo-data.sh` loads the seeds of the image it runs), refuses a dirty clone (`--allow-dirty` for the laptop), backs up first (`--no-backup` to skip), and prunes registry images whose tag is neither of the two; one `pin_image_tag` in `lib.sh` serves `bootstrap.sh` and `deploy.sh`. Rollback is `restore.sh <stamp>`, `git checkout <previous>`, `deploy.sh`, in the guide; a bare tag rollback after a migration is wrong and the guide says so. Rejected: following the moving `main` tag; automatic deploy on every merge (#247's model: the demo would change under a class mid-session); release tags before doc 35 exists. (2) **D-2: uploaded objects are backed up with the databases.** `backup.sh` mirrors `attachments`, `images` and `packages` after both dumps (one current mirror, no `--remove`), locally and to S3; `audit-anchors` is left out for the demo and must go to an object-locked off-site bucket before real data (it is evidence); secrets reach the backup container by a 0600 `--env-file`, `.part` files are cleared, `LAST_OK`/`LAST_FAILED` markers are printed by `deploy.sh` and the smoke (a team without an MTA sees that; `MAILTO` goes); encryption (`age`, the private half kept with the `.env` copy off the server) before real data. **`restore.sh <stamp>`** checks both dumps and the stamp's recorded image tag (refusing an image older than the dump's: Flyway would start old code on a newer schema silently), asks for the word `restore`, backs up first, stops backend, Keycloak and PgBouncer, drops and recreates both databases with their owners, restores `--single-transaction --exit-on-error`, mirrors objects back, starts and smokes; the drill on `compose.local-test.yml` (bootstrap, demo data, backup, a table the dump does not hold, restore, the table gone, sign-in and an uploaded image still showing) is part of the fix and recorded in the PR. RPO 24 h is for the demo; F-14's 15 minutes needs PITR (F-01's managed PostgreSQL or pgBackRest) before real data. (3) **D-3: Keycloak's public surface is the coop realm and the theme files only.** Caddy proxies `/auth/realms/coop/*` (less `account*` and `clients-registrations/*`) and `/auth/resources/*` and answers 404 to every other `/auth/*`; Keycloak is published on `127.0.0.1:8081` with `KC_HOSTNAME_ADMIN=http://localhost:8081/auth`, the console reached through `ssh -L 8081:127.0.0.1:8081`; `bruteForceProtected=true` with temporary lockout on `coop` and `master`, applied by an idempotent `apply_realm_policy` (kcadm) on every deploy, since `render_realm` reaches only a fresh import. Rejected: a deny-list of two paths; basic auth in front of the console; an IP allowlist (operators on dynamic addresses). Before real data: a named admin per operator with OTP, the bootstrap admin removed. (4) **D-4: demo identity policy.** Shared role users with one `DEMO_PASSWORD` (`Demo-` plus 12 hex on a new server) remain, because the users are the storyline's characters bound to seeded scopes; no self-service (account console and `kc_action` application-initiated actions answered 404 by Caddy, `manage-account*` removed from the default roles, `CONFIGURE_TOTP` disabled); the forced password change for a new user stays (phase 4 of the demo needs `UPDATE_PASSWORD`); credential changes made through the application are accepted and repaired by `demo-data.sh --repair-users` (every realm user back to the password, required actions and OTP cleared, lockouts cleared, no data touched; one minute instead of `--reset`); the smoke fails when `directAccessGrantsEnabled` is left on outside a `demo-data.sh` run. Before real data the policy inverts: one account per person, self-service password change, OTP for admin and money roles (doc 10 E-05). Rejected: one user per tester; disabling `UPDATE_PASSWORD`; a dedicated confidential demo-tools client (five copied mappers and a widened `OIDC_ACCEPTED_CLIENTS`: more surface than it removes). (5) **D-5: a public issuer may run the #184 shortcut only with a second opt-in.** `coop-erp.security.mfa.password-reauth-public-issuer-ack` (env `COOP_ERP_MFA_PASSWORD_REAUTH_PUBLIC_ACK`) must equal the literal `demo-data-only`; the backend refuses to start when the flag is on, the issuer is not a development one and the ack is absent; only `infra/deploy/compose.yml` sets it; staging gets Keycloak OTP and the flag off; the "never fall back to `iat` for a non-web `azp`" narrowing is a separate kernel change (tills step up by PIN, E-05). Rejected: fatal without exception (the demo could show no step-up action); the log line (the template would carry it into a real environment). (6) **Hardening now**: HSTS, `nosniff`, `frame-ancestors 'self'` with `X-Frame-Options SAMEORIGIN`, `Referrer-Policy strict-origin-when-cross-origin`; `nosniff` on objects but no `sandbox` CSP until tried against an inline printed PDF in Chrome and Firefox (Chromium refuses PDFs in sandboxed documents; the content-type allowlist is the safer control); `path /actuator /actuator/*` private with the health exclusions (the management-port split goes with doc 35); `security_opt: no-new-privileges` everywhere and `cap_drop: [ALL]` on every service but postgres and rabbitmq (their entrypoints chown and gosu), caddy adding `NET_BIND_SERVICE`; the rendered realm file `chown 1000:0`, `chmod 600` (not `chmod 700 /opt/coop-erp`, which stops postgres and Keycloak starting). Before real data: a bucket-scoped MinIO user (`coop-erp-app`, Get/Put/List on three buckets, Put and retention only on `audit-anchors`, appended to an existing `.env` once), `read_only` roots, a maintained MinIO image (the `bitnamilegacy` repository gets no further updates). (7) **CI supply chain**: every action SHA-pinned (Dependabot's `github-actions` entry keeps them), `persist-credentials: false` on the publish job's checkout, base images digest-pinned (`caddy`, `eclipse-temurin` in three places including `jibBaseImage`, `debian:trixie-slim`) with Dependabot `docker` entries for the three image folders and `docker-compose` for `/infra/deploy`; the apt `chromium` version is not pinned (Debian drops superseded versions); the docker-only publish job and signed provenance go with doc 35's release workflow. (8) **The sign-in page** speaks three languages: every string a `${msg(...)}` with the custom and Keycloak keys in all three `messages_*.properties` (Keycloak ships no Sinhala bundle), a check that the three files hold the same keys, `<a href="${l.url}">` instead of inline handlers, Inter woff2 shipped under `resources/fonts/`; the temporary-password page is a known English gap unless the demo shows it. (9) **PR #247**: recommend close, not rework: its deploy workflow runs the laptop stack on a server as root with committed development passwords (would be high if merged), its tenant-isolation change ("distributor-managed MPCS", `ALTER POLICY` on four M1 tables) is a doc 21 design question that needs a CR and its own RLS review, and its CSS fix is a one-file PR; an automated deploy, if wanted later, is a `workflow_dispatch` job behind a GitHub environment with required reviewers, an SHA-pinned SSH action with a fingerprint, a non-root user, running the clone command of (1).
