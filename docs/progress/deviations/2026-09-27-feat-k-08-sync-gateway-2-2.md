- **No round-robin ingest queue, versus 19A section 8 "fairness by round-robin across devices in the ingest queue" (27 Sep, same branch):** ingestion is synchronous in the request and there is no queue to order. Fairness comes from one batch in flight per device (409), the per-device buckets and the per-instance slot limit with `retry_after`, which spreads a burst in turns of a batch per device. The buckets are per instance, as 19A says, so behind N instances a device's allowance is up to N times the configured one. **Decided 27 Sep 2026: confirmed as built (branch `feat/decisions-sync`), on the architect's delegation.** 19A section 8 itself writes "token buckets per device ... in memory per instance plus a global concurrency limit", and the round-robin it names presumes an ingest queue that synchronous ingestion (the part-1 decision) does not have. What bounds a device is the one batch in flight per device on any instance (409 through the cursor row), so N instances let a device send its batches faster, never at once. Shared counters would cost a write per batch on the hottest path for a limit nobody has measured; if the load test (spike 5, doc 32 DR-1) shows the N-fold allowance matters, the buckets move onto the cursor row the claim already locks, a change inside `SyncRateLimiter` and one migration.
