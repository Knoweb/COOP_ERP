- **Functions that answer across tenants (wave 2: RLS-03, RLS-06, RLS-07, RLS-12, RLS-13, RLS-14, RLS-16, M9-06, M7CR-15), decided on the architect's delegation (6 Oct, branch `docs/wave2-decisions`):** (1) **The pattern, recorded as the fifth case of `RLS_POLICY_TEMPLATE.md` and pinned by `SchemaRulesIntegrationTest`:** a SECURITY DEFINER function executable by `app_rw` tests `kernel.scope_class()` first and answers nothing to a class that has no business asking (today `= 'OWN'`; a job's class is named explicitly); takes the caller from `kernel.scope_entity()`, never as a parameter (parameters name the thing asked about, never the entity answered for); returns the smallest fact the guard needs, a boolean, a count or ids the caller already owns, so another tenant's ids never leave it; sets `search_path = pg_catalog, <schema>, pg_temp` (PostgreSQL's own hardening guidance for definer functions: an unlisted `pg_temp` is searched first and lets a session shadow a catalogue function); keeps `REVOKE ALL FROM PUBLIC; GRANT EXECUTE TO app_rw`, so who may call is the class test inside, not the grant (one role serves every class). The test asserts every `prosecdef` function's `proconfig` ends in `pg_temp` and every one granted to `app_rw` names `kernel.scope_class()` in its body; `01-roles.sh` adds `REVOKE TEMPORARY ON DATABASE coop_erp FROM PUBLIC` (nothing under `backend/app/src` creates a temporary table). (3) **One recorded exception to the layering rule, for SQL (RLS-07, D-4):** a module's migration may call a function another module created for it, read-only, never a table and never a write, and the function is listed in the creating module's README as part of its contract. `catalogue.batch_apply_correction` (m2catalogue V0008) refuses, before its two updates, a caller that is not OWN, nor the corrected batch's owner, nor the Federation (`kernel.system_entity()`), nor a lot holder by `inventory.entity_holds_lot_of(NEW.corrects_batch_id, kernel.scope_entity())`, with `ERRCODE insufficient_privilege`; no location test (a batch is global); the Java guard stays. Rejected: owner-or-Federation only (refuses the holder, doc 22 B-I8); a kernel function or an M5 hook in the catalogue schema (writes another module's schema or puts lots in the kernel); a holder projection in M2 (eventually consistent, flaky right after a GRN). (4) **The contact door (RLS-06, M9-06): M1 publishes the fact.** m1party V0015 adds `party.caller_trades_with(p_entity uuid) RETURNS boolean`, SECURITY DEFINER under the pattern: OWN class and an `entity_relationship` of status ACTIVE **or SUSPENDED** between the caller and `p_entity` in either direction (a suspended buyer still owes and must still be told; the directory `party_names_read` already shows each side its counterparties, so this is no oracle). m9integration V0006 rewrites `integration.notification_recipients` as `WHERE kernel.scope_class() = 'OWN' AND (p_entity = kernel.scope_entity() OR party.caller_trades_with(p_entity))`. This disagrees with the M9 fix review's D7 (a kernel `are_document_parties(a, b)` reading `kernel.document` as definer): the relationship is the business fact ("you may reach those you trade with"), M1 is below M9 in the layering so the call is the D-4 pattern and not a boundary breach, and a kernel helper that bypasses RLS on `kernel.document` for one module's need is a wider door than a boolean about the caller's own relationships.
