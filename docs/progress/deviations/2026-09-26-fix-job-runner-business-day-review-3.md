- **`kernel.shedlock` times without a time zone, versus the 19A section 12 DDL (26 Sep, branch `fix/job-runner-business-day-review`):** `lock_until` and `locked_at` are `timestamp` (naive UTC) from `kernel/V0057`, not `timestamptz`, because ShedLock's PostgreSQL statements write and compare `timezone('utc', CURRENT_TIMESTAMP)` and a `timestamptz` column reads that through the session's zone. The table is ShedLock's, read by nobody else; the run history (`kernel.job_run`) keeps `timestamptz`. **Decided 27 Sep 2026: accept (PR #141), on the architect's delegation.** ShedLock's own PostgreSQL provider dictates the column type it compares against; fighting it with `timestamptz` and a session time zone is what caused the bug this migration fixes (a lock read hours early or late depending on which session wrote it). The 19A DDL is the one that should move: a re-issue should show `lock_until`/`locked_at` as `timestamp` (naive UTC) with a note that ShedLock, not the kernel, owns this table's convention. Reversing this later, once more scheduled jobs depend on locks expiring at the right instant, would cost far more than fixing one document sentence now.
