- **What `Notifications.send` answers, versus 19A section 10 "returns the notification id" (27 Sep, branch `fix/m1-roles-users-grants-review`):** it answers a `Delivery`, the id and the outcome decided inside the caller's transaction. Since #127 the provider is called only after that transaction commits, so a direct send answers QUEUED (logged for sending), SUPPRESSED or FAILED, never SENT at call time. `TemporaryPasswordDelivery` therefore counts a QUEUED send to a resolved recipient as NOTIFIED. A queued send can still fail at the provider after commit: the retry sweep takes it, and if the password never arrives the user asks for another reset.
