- **Keyed hashes for the NIC and the notification recipient (wave 2: M7CR-01, M7CR-02, M7CR-15, RLS-01, M9-07, TWK-20), decided on the architect's delegation (6 Oct, branch `docs/wave2-decisions`):** (1) **One kernel facility, `kernel.api.KeyedHash`**: HMAC-SHA-256 (NIST SP 800-107 and FIPS 198-1) over a canonical input, keyed by a 32-byte key read from an application property supplied by the environment or a secret store, never a `ConfigRegistry` item (the item would live in the database the key protects), with the "no default outside a development issuer, else refuse to start" rule lifted out of `IdempotencyFilter` into the same helper so the three keys (idempotency, NIC, recipient) cannot drift. (2) **Two separate keys**, `coop-erp.customers.nic-pepper` (M7's) and `coop-erp.notification.recipient-hash-key` (the kernel's): one purpose per key (SP 800-57 key separation); they rotate for different reasons and a leak of one must not open the other. The notification key is not `pending-key`, which rotates daily and would break de-duplication and the unique `(rule_id, event_id, recipient_hash)`. (3) **A key id beside every keyed hash**: `customers.customer.nic_key_id smallint` (null = legacy plain SHA-256) and `kernel.notification_log.recipient_hash_key_id text` (null = replaced legacy row), so a second key can ever be introduced. (4) **NIC**: `nic_hash = HMAC(pepper, SHA-256("nic:" + canonical NIC))`, the canonical form being the 12-digit new form (old form `YYDDDSSSCV|X` → `19YYDDD0SSSC`; `nic_last4` from the canonical form); legacy rows are re-keyed as `HMAC(pepper, stored_sha256)` by a job that computes in Java and writes through `customers.rekey_nic(customer, old, new, key)` (SECURITY DEFINER, idempotent, the pepper never in SQL text); until the job reports zero legacy rows the lookup also tries the legacy candidate set (canonical, old form with V, with X, as typed) so no window needs care; a `RecaptureNic` command (`cus.account.manage`, fresh second factor, reason, audit `NIC_RECAPTURED` with `nicCaptured: true` only) is the way out of any unmatched legacy row and the ordinary rotation path; an emergency rotation chains the stored value under the new key in the same job. The cross-society duplicate check is `customers.nic_holders(p_hashes char(64)[])` returning `(own_customer_id, held_elsewhere)` under the cross-tenant pattern (`2026-10-06-wave2-cross-tenant-functions.md`); `m7.account.nic_held_elsewhere` names nobody. The four last characters stay (doc 10 L-06 stands): with the hash keyed they add nothing to an attacker without the key, and the reuse confirmation step relies on them. (5) **Notification recipient**: `HMAC(key, channel + ":" + recipient)`; the clear recipient of legacy rows exists nowhere (`notification_pending` is sealed and cleared), so they cannot be re-keyed; kernel migration V0085 replaces every legacy `recipient_hash` with `encode(gen_random_bytes(32), 'hex')` (rows stay unique; only the one-hour de-duplication of rows older than the deploy is lost, which is past anyway). This takes M9-07's randomisation over TWK-20's "age out": the log has no purge, so an unkeyed hash of a 10^8 phone space would otherwise sit at rest for good. A rotation is a maintenance-window act and may queue one duplicate for an event replayed across it; both keys live at once is not built. (6) **The log screen never shows a hash**: it shows the recipient's entity, the audience role and the channel (new nullable columns `recipient_entity_id`, `audience_role` on `notification_log`, filled from a widened `NotificationAudience.Recipient(channel, recipient, language, entityId, roleCode)`) plus an 8-character tag of the keyed hash so two numbers of one role can be told apart. Rejected: a per-row random salt for the NIC (breaks the equality lookup `nic_held`, and does nothing against a 7.3e5 candidate search once the last four are known); tokenisation or encryption of the NIC (stores something recoverable the system never needs to read back); fewer than four trailing characters (breaks the confirmation step with no gain once keyed); the plain SHA-256 prefix on the screen (reversible in minutes). Residual, recorded in both READMEs: the application host holds the key and can enumerate; that is the application, which must compare anyway.
