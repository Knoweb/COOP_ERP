- **Amendment, application, the receipt's print and the credit limit, decided on the architect's delegation (29 Sep, branch `feat/m4-amend-onaccount-receipt-creditlimit`):** (1) **A limit change does not break open orders**: 21A section 6.1 closes the relationship row and opens the next, and that stays; M4 judges an order by the seller and buyer's row in force today (M1 LookupRelationship), not by the row the order names, and AcceptOrder prices and compares the limit under it. The order keeps naming the row it was drafted under (history). (2) **An amendment is a new order, the next version**, not superseded lines: an issued order's lines are never edited and the kernel's SUPERSEDES link is for drafts only, so `doc_order.amends_order_id` names the version it replaces and the old one is CANCELLED (reason ORDER_AMENDED, `order.cancelled.v1` published too so M8 stays right). Built before the seller decides only; the lock-override path of 24A (amending an accepted order) is not built. Permission `ord.order.submit`, as CancelOrder (24A names no amend code). (3) **ApplyReceipt writes allocation rows of the receipt** (with `application_id`), no document and no journal: the receipt's posting already credited the buyer with the whole amount. It is reversed with the receipt (a bounce); no separate un-apply. (4) **The receipt prints as recorded**: money applied later shows on screen, not on that copy. (5) **The web cannot test `bil.creditlimit.change`** (no operation carries it, check-permissions): the agreement sheet offers the change to `prt.relationship.amend` holders and the server checks the limit permission and the second factor. (6) **No demo application of on-account money**: the history's invoices exist before the payments are replayed, so an overpayment would be taken by the next invoice at once; the flow is shown live instead.
