- **M1 administration guardrails (wave 2: M1A-01, M1A-03, M1A-05, M1A-06, M1A-07, M4MONEY-08's query), decided on the architect's delegation (6 Oct, branch `docs/wave2-decisions`), CR-21A-7:** (1) **Who may reset or disable whose credentials** (M1A-01, D8): `ResetCredential`, the `UpdateUser` kind change that closes the back office, and `DeactivateUser` are refused (`m1.user.target_outranks_caller`) when the target holds, at the entity, any permission whose catalogue entry has `requires_mfa = true` that the caller does not hold (user and role management, credit limit, approvals: the sensitive codes); nobody resets their own SECOND_FACTOR through the command (`m1.user.credential_self`); the temporary password may still be returned to the caller when no delivery rule exists, since the caller now outranks or equals the target. Rejected: the strict within-grantor rule (the seeded Entity Administrator lacks finance codes, so the society's administrator could not reset the cashier's password); protecting `gov.*` holders only (leaves credit-limit and approval holders exposed); notification-only delivery (shops without e-mail or SMS). **Raised, not decided here, for the architect**: a one-administrator society whose only user manager loses their second factor; ADR-18 says the Federation cannot repair in-app, so either activation requires a second holder or the helpdesk procedure (doc 38) says how. (2) **The last user manager** (M1A-03): `UpdateUser` takes `EntityLock` and refuses `m1.user.last_user_manager` when a kind change removes the login of the last holder; every "another user manager" count (`UserFacts.USER_MANAGERS` and the definer count RevokeRole and AmendRole use) counts only users whose kind has a login (BACK_OFFICE, BOTH), in m1security V0019 if the function does not already join `app_user.user_kind`. (3) **Segregation pairs** (M1A-05, D10): `gov.audit.review`/`gov.user.manage` stays INSTANCE and is enforced where its instance exists, at the exception acknowledgement of 28A (a reviewer may not acknowledge an exception whose actor is themselves), built with that ticket; the `gov.role.manage`/`gov.user.manage` pair, which is in neither doc 21 nor 21A and was added in M1-08, is removed (m1security V0019 deletes it by id, the seed too); its protection is the code guardrails doc 21 names. Rejected: ROLE mode (the Entity Administrator template holds both codes; a small society has one administrator). (4) **A credit limit is gated where it is set** (M1A-06): `PermissionResolver` becomes a required dependency (fail at start, not open); `OpenTradingRelationship` with a non-null limit and `ActivateRelationship` of a draft carrying one both require `bil.creditlimit.change` and fresh MFA (Amend's `requireFreshMfa`); Activate publishes `credit_limit.changed.v1` (null → the limit) so the opening limit is an event for M8. Rejected: gating Activate only (a draft would carry an unreviewed figure into the audit trail).
