- **DEPLOY-03 infra/deploy/SETUP-2vCPU-4GB.md:155-164 (and backup.sh:21-22)** [CONFIRMED] [medium] [data integrity] The documented restore was never exercised (the PR verified `backup.sh` only) and fails or half-restores on any database that has been migrated since the dump (PR #248)
  Scenario: backup at 02:00; at noon `deploy.sh` starts an image whose Flyway migration creates table `mX.foo`; at 15:00 the operator restores the 02:00 dump as written: `pg_restore --clean --if-exists` drops and recreates only the objects in the dump, so `mX.foo` survives while `flyway_schema_history` goes back to the older state. On `up`, Flyway runs the migration again, `CREATE TABLE mX.foo` fails with "relation already exists", and the backend never becomes healthy. Separately, without `--exit-on-error` and `--single-transaction`, any error in the middle (an extension, an ownership, a lock held through PgBouncer's pooled connections) is reported at the end while the database is left part old, part restored, and the next guide line (`up -d --wait`) starts the application on it. Keycloak's database has the same shape across a Keycloak version bump. Fix: restore into a fresh database (stop backend, keycloak and pgbouncer; `dropdb --force` and `createdb` as the owner the role script expects, then `pg_restore --single-transaction --exit-on-error`), put that in a `restore.sh` beside `backup.sh`, and prove it once on the laptop kit (`compose.local-test.yml`) before the guide promises it.
  Verification: CONFIRMED by reading (not exercised). `pg_restore --clean --if-exists` issues DROP only for objects in the archive's table of contents: a table created by a later migration survives (and, if it references a dumped table, makes that table's DROP fail too); the dumped `flyway_schema_history` comes back with fewer rows, so Flyway re-runs the newer migration. Of 163 `CREATE TABLE` statements in the migrations only 3 use `IF NOT EXISTS`, and `CREATE POLICY` (628 uses) has no such form, so the re-run fails and the backend never becomes healthy (`MIGRATION_OUT_OF_ORDER=false` is irrelevant: the migration is pending, not out of order). Without `--exit-on-error` pg_restore continues past errors and reports them only at the end; the guide's next line starts the stack regardless. One sub-claim weakened: PgBouncer's idle server connections hold no locks under transaction pooling, so locks are an unlikely failure cause; the dependency and migration cases stand without it.
  Suggested fix scope: script and docs only (`restore.sh`: stop backend, keycloak and pgbouncer, drop and recreate the database, `pg_restore --single-transaction --exit-on-error`; then one drill on the local-test kit). No design decision.

Fix: in the Caddyfile answer 404 for `/auth/admin/*` and `/auth/realms/master/*` (the backend already reaches the admin API inside the network, `OIDC_ADMIN_URL: http://keycloak:8080/auth`); reach the console through an SSH tunnel to the container; set `bruteForceProtected: true` in `render_realm` for the demo realm.
  Verification: CONFIRMED by reading.   Suggested fix scope: config only (Caddy `respond 404` for `/auth/admin/*` and `/auth/realms/master/*`, a `bruteForceProtected` substitution in `render_realm`, guide text for an SSH tunnel). One operating decision: how the operator reaches the console once it is off the internet.
