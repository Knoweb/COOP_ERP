## backend/app/src/main/resources/db/migration/m7customers (3)

- **RLS-01 m7customers/V0001__customers.sql:25** [high] [privacy] `customers.customer.nic_hash` is an unsalted, unpeppered SHA-256 of the NIC stored next to `nic_last4`, and the row is readable by the registering society, every society holding an account (`account_holder_read`), FEDERATION_VIEW (`fed_view`) and a regulator's grant (`ext_view`); the NIC is recoverable from it in milliseconds (PR #221; hash in `m7customers/internal/customer/NicNumbers.java:34`).
  Scenario: a FEDERATION_VIEW or EXTERNAL_TIMEBOXED session selects `nic_hash, nic_last4` from customers.customer. A new-form NIC is 4 digits of year, 3 of day (+500 for women), 4 of serial and a check digit; the stored last four fix the serial tail and check digit, leaving roughly 100 x 732 x 10 = 7.3e5 candidates, each one `sha256("nic:" + candidate)`. The old form is the same order. Every member's NIC is recovered, although M7's README and AGENTS.md treat the NIC as never stored in the clear. Fix: key the hash (HMAC-SHA-256 with a secret held outside the database, as `PendingSeal` does for notifications), re-hash on the next migration, and take `nic_hash` out of reach of `fed_view` and `ext_view` (a masking view, or no ext_view on customers.customer, as security.app_user and notification_contact already do).
  **Verification: CONFIRMED, high.** M7CR-01 (wave2-m7-credit.md, reproduced there with a script) has the same root cause, the unkeyed hash, so the brute-force analysis is not repeated here. This finding adds who can read the row, which V0001:164-193 settles. `own_read` gives it to the registering society. `account_holder_read` gives it to any OWN society holding an account for the customer, although M7CR-13 shows no second society can open one today. `fed_view` gives it to every FEDERATION_VIEW session, for every member of every society. `ext_view` gives it to an EXTERNAL_TIMEBOXED grantee for the societies in its grant. RLS has no column masking, so all four read `nic_hash` and `nic_last4` with the name. The RLS matrix gives customers.customer no exception, so the template's fed/ext reads are asserted as correct. The scratch test reads `nic_hash` as FEDERATION_VIEW and as EXTERNAL with grant {S2}.
  Suggested fix scope: code (HMAC with a pepper outside the database, M7CR-01) plus a re-hash step that holds the pepper (a Java job, not SQL). A new migration takes `nic_hash`/`nic_last4` out of the fed/ext path: a security_invoker masking view, or a separate `customer_identity_secret` table with own_* only. A design decision is needed on whether FEDERATION_VIEW reads member identity at all (RLS-02).

- **RLS-02 m7customers/V0001__customers.sql:168** [medium] [privacy] `fed_view` and `ext_view` on `customers.customer_phone` (and `customer`, `customer_consent`) give the Federation view and any regulator grant every member's phone number, name and consents, while the same personal data was deliberately kept from ext_view elsewhere (security.app_user, integration.notification_contact, RLS matrix EXCEPTIONS) (PR #221).

- **RLS-04 m3pricing/V0005__control_price_and_mrp_policy.sql:36** [medium] [security] `own_write` on `pricing.control_price` admits any OWN entity, and `everyone_reads` shows every row to every society and till as a gazetted ceiling, so the only thing keeping a society from imposing a federation-wide ceiling is the Java guard; the template says such policies ask `kernel.system_entity()` (PR #217).

  **Verification: CONFIRMED by reading, medium.** `own_write`/`own_update` (V0005:36-40) test only `OWN AND owner_entity_id = scope_entity()`. `GRANT INSERT` is to app_rw, so an app_rw session in a society's OWN scope inserts a `control_price` row of its own. The template says in so many words that a policy which must know the Federation asks `(SELECT kernel.system_entity())`. The guard exists only in `EnterControlPriceHandler`:87 and `RescindControlPriceHandler`:74 (`m3.control_price.federation_only`). No API path reaches the insert without it today, so this is defence in depth, but the impact is federation-wide.
