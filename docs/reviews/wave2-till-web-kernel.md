- **TWK-01 till/core/.../TillService.kt:167-182, till/core/.../snapshot/SnapshotVerifier.kt:26-53** [high] [security] The snapshot is checked for signature and table hashes only; its freshness and continuity are never checked, so an old or gapped signed snapshot is applied and the version number goes backwards or skips (PR #231, #136)
  Scenario: the manifest is signed but carries no issue time, and the verifier compares `version`, `location_id` and `full` only, never the signed `since` against the version the till holds, and never `delta.version >= current`. A proxy (or any party that can answer over the plain-http server URL, see TWK-02) replays a validly signed delta from last month, or a delta with `since=10` to a till at version 8. The till applies it: removed operators come back with their PIN hash, a lowered control price returns to its old ceiling, rows changed in versions 9 and 10 are never seen, and `snapshotVersion` is set to the replayed value so the till never asks for what it missed. Fix: reject `delta.version < current.version`; for a non-full delta require `since == current.version` (else ask for a full snapshot); put an issue time and the previous version hash in the signed manifest and refuse a snapshot older than a configured age; keep the signed `key_id` and compare it with the enrolled key.
  Verified by: wave-2 verifier (Claude Sonnet 5.5), read-only, main 91e550d8. Status: CONFIRMED (high kept). SnapshotManifest.java signs `since` and `version` (`manifest.put("since", since)`), SnapshotVerifier checks signature, `version`, `location_id`, `full` and table hashes only, and TillService.refreshSnapshot applies whenever `delta.version != current.version` (no `>=`, no `since == current`). Doc 32 section 5.2 says the device verifies hashes and swaps in one transaction and that central re-validates by `snapshot_version_in_use`; it does not say the till must reject an older version, though it sets one monotonic version per location. A replay needs an on-path party or a central fault, so the exposure depends on TWK-02.
  Suggested fix scope: the `version >= current` and `since == current` checks are till code only, no migration. Adding an issue time or previous-version hash to the signed manifest changes the manifest format in doc 32 and the OpenAPI: a design decision for the architect (flagged, not decided).

- **TWK-08 till/desktop/.../KeyVaults.kt:18-49** [medium] [security] Key creation is not atomic and not tied to the database: a crash between creating the key file and writing the key leaves an empty file, and a missing key file next to an existing `till.db` silently makes a new key (PR #231)
  Scenario: Linux: `Files.createFile` then `Files.writeString`; a crash in between leaves an empty `database.key`, every later start reads "" and `require(raw.size == 32)` fails for ever: the till cannot open and its unsent receipts are unreadable. Windows: `Files.write` of the DPAPI blob is not atomic either. Deleting the key file (or restoring `till.db` onto a new Windows user) generates a fresh key that cannot open the old database, with no explanation.   Verified by: wave-2 verifier (Claude Sonnet 5.5), read-only, main 91e550d8. Status: CONFIRMED. KeyVaults.kt: Linux `createFile` then `writeString` (not atomic, an empty file is read as the key and fails `require(raw.size == 32)`); Windows `Files.write` of the DPAPI blob is not atomic; a missing key file silently generates a new key with no check for an existing `till.db`; `cryptProtectData` is called without entropy.
  Suggested fix scope: till desktop code only, no migration. Whether a lost key means re-enrolment with a documented outbox loss is an operations decision (doc 32 section 8 gap rules): flagged.
