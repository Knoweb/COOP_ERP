Reviewer: Claude Opus 5.5, independent second opinion before any fix is built. Code read at main 91e550d8 (working tree `review/wave2-findings`). Read only; nothing was run (Docker is down). Inputs: `docs/reviews/wave2-deploy.md`, `wave2-summary.md`, AGENTS.md, `docs/DECISIONS_PENDING.md` (F-01, F-14, E-05), `docs/DEMO.md`, `docs/demo/07-phase4-administration.md`, and the cited files in `infra/deploy`, `infra/compose`, `infra/keycloak`, `.github`, `backend` (JwtClaimsMapper, ResetCredentialHandler, application.yml, demo seeds).

What the kit is for, which sets every verdict below: a public demo on one 2 vCPU / 4 GB or 4 vCPU / 8 GB server, about 80 testers sharing about 20 role users, run by a small team; later the template for shared staging and go-live. A fix is "pragmatic" here when one person can build it in a day or less in shell, Caddy, compose or realm config, and it removes the failure a tester or the operator would actually hit. Where the ideal fix belongs to doc 35 (deployment, unwritten) or to F-01 (hosting: cloud with managed PostgreSQL assumed), I say so and defer it.

## Fix groups

### G1. Deploy in lockstep (DEPLOY-01, DEPLOY-02). Order: first. Decide first: D-1.

**DEPLOY-01.** Valid: YES. `lib.sh:18` sets REPO_DIR only when `$SCRIPT_DIR/../compose/realm-dev.json` and `../../backend` exist; from `/opt/coop-erp` neither does, `sync_files` returns at line 54-57, and both guides (section 7) run `/opt/coop-erp/deploy.sh`. Worse than stated: `sync_files` itself copies `deploy.sh` into `/opt/coop-erp` (line 62), so the wrong command is always there to be run.
Fix: NEEDS CHANGES (small). Do not "record the clone path in .env" (the alternative in the finding): once G1 pins by the clone's SHA the clone *is* the version, and a second entry point only adds a way to deploy something the operator did not pull. Build: (a) both guides, section 7 and the troubleshooting row, say `cd ~/COOP_ERP && git pull --ff-only && sudo ./infra/deploy/deploy.sh`; (b) `deploy.sh` fails when `REPO_DIR` is empty ("run deploy.sh from the clone: cd ~/COOP_ERP && ..."); (c) stop copying `deploy.sh` and `bootstrap.sh` into `/opt/coop-erp` (they are clone-only), keep `demo-data.sh` and `backup.sh` (they legitimately run from there).
Business: the operator is one person following a page; the page must be the only path. Verdict BUILD AMENDED, S, no migration, risk low.

**DEPLOY-02.** Valid: YES. compose.yml:218/294/325 default `${IMAGE_TAG:-main}`, bootstrap writes `IMAGE_TAG=main`, `package-main` publishes `:main` and `:$GITHUB_SHA` only after every test job (ci.yml:723-729, docs-only is forced false on push, ci.yml:115, so every green main commit gets a SHA image). Nothing ties the clone to the image.
Fix: NEEDS CHANGES. The finding's direction (pin to `git rev-parse HEAD`, check with `docker manifest inspect`, record the previous tag, back up first) is right; four gaps:
1. Write the tag into `.env` (`env_set IMAGE_TAG <sha>`, plus `PREVIOUS_IMAGE_TAG`), not only into deploy.sh's environment: `demo-data.sh` runs `demo-tools` later with `.env`'s tag, and must run the same SHA as the seeds it loads. Update the `env_set` comment (it says address keys only).
2. Pinning makes `docker image prune -f` useless: SHA-tagged images are never dangling, so every deploy leaves about 1.5 GB (backend-worker with Chromium, web, demo-tools) and a 50-80 GB disk fills in weeks. Replace the prune with: remove `$REGISTRY/*` images whose tag is neither `IMAGE_TAG` nor `PREVIOUS_IMAGE_TAG`, then `docker image prune -f`.
3. Refuse a dirty clone (`git status --porcelain -- infra backend/app/src/main/resources/seed`): local edits would run against an image that does not have them. `--allow-dirty` for the laptop test. With `--no-pull` (laptop) keep `.env`'s tag untouched.
4. Run `backup.sh` at the start of every deploy (seconds on demo data; `--no-backup` to skip) and print its stamp. A migration is the irreversible step; a rollback is then "`restore.sh <stamp>`, `git checkout $PREVIOUS_SHA`, `deploy.sh`", which the guide states in three lines. A bare tag rollback without the restore is wrong after any migration and the guide must say so.
Put the SHA resolution in one `lib.sh` function (`pin_image_tag`) used by both `bootstrap.sh` (line 241) and `deploy.sh`. Check all four images (`backend-worker`, `web`, `demo-tools`, and `backend` if compose uses it) with `docker manifest inspect`; on a miss: "CI has not published <sha> (still running, or main's tests failed on it): wait for Package (main), or `git checkout` an earlier commit of main".
Business: the demo follows main, but by explicit, recorded SHAs (D-1). Verdict DECIDE THEN BUILD (the decision is small and recommended below), S-M, no migration, risk low (worst case the deploy refuses and says why).

### G2. A restore that works, uploads included (DEPLOY-03, DEPLOY-04, DEPLOY-13). Order: second, after G1 (G1's pre-deploy backup and IMAGE_TAG record feed it). Decide first: D-2.

**DEPLOY-03.** Valid: YES. `pg_restore --clean --if-exists` drops only what the archive lists; a table created by a later migration survives, `flyway_schema_history` goes back, the migration re-runs and fails on `CREATE TABLE` / `CREATE POLICY` (no IF NOT EXISTS form). No `--exit-on-error`, and the guide starts the stack regardless.
Fix: CORRECT in direction, NEEDS CHANGES in detail. `infra/deploy/restore.sh <stamp>`:
1. Both files for the stamp exist (`coop_erp-<stamp>.dump`, `keycloak-<stamp>.dump`), and, from G1, the stamp's recorded `IMAGE_TAG` (have `backup.sh` write `backups/<stamp>.tag`). Refuse when the running image is *older* than the dump's (Flyway's default `ignoreMigrationPatterns=*:future` would start old code on a newer schema silently); an equal or newer image is fine, Flyway migrates forward.
2. Ask for the word `restore`; run `backup.sh` first (the undo of a restore).
3. `compose stop backend keycloak pgbouncer` (pgbouncer holds server connections; `dropdb --force` would kill them anyway, but a stopped pooler cannot reconnect mid-restore).
4. `dropdb -U postgres --force coop_erp`, `createdb -U postgres -O coop_migrator coop_erp` (template1 carries the ICU locale from initdb); same for `keycloak` with owner `keycloak`. Database ownership is also re-asserted by `01-roles.sh` (`ALTER DATABASE ... OWNER TO`), which `apply_db_roles` already runs; database-level grants are not in a plain `pg_dump`, and none are needed (checked: migrations do no `GRANT ... ON DATABASE` / `ALTER DATABASE`; the three extensions are in V0001 and in the dump).
5. `pg_restore -U postgres -d <db> --single-transaction --exit-on-error < dump` (single-transaction implies exit-on-error; owners and grants to `app_rw`, `app_relay`, `app_report`, `app_seed` restore because the roles are cluster-level and already exist; triggers and FKs are post-data, so COPY fires no insert-only triggers).
6. Objects back (`mc mirror` from the backup, see 04), then `start_stack` and `smoke`.
The drill is part of the fix, not optional: on `compose.local-test.yml`, bootstrap, `demo-data.sh`, `backup.sh`, then, as `coop_migrator`, create a table the dump does not hold (standing in for a later migration: `CREATE TABLE kernel.zz_drill(x int)`), restore, and check the table is gone, the backend is healthy, the demo users sign in and an uploaded image still shows. Record what was run in the PR. A nightly CI drill is worth having before staging; defer it.
Business: RPO 24 h is fine for a demo; the F-14 target (RPO 15 min) cannot be met by dumps at all, so before real data the database backup is PITR (F-01's managed PostgreSQL, or pgBackRest), and `restore.sh` remains the staging tool. Verdict BUILD AMENDED, M, no migration, risk low (new script; the old guide text is what is risky).

**DEPLOY-04.** Valid: YES. `backup.sh:11` calls the store regenerable; `attachments` (presigned PUT, GRN and claim photos) and `images` (#249 SKU images) are user content, and `kernel.document_attachment` / catalogue rows point at them.
Fix: CORRECT; take the backup option, not the docs-only option (D-2). In `backup.sh`, after both dumps (so every object a dumped row references is older than the mirror), `compose run --rm --no-deps -v "$APP_DIR/backups/objects:/backup" --entrypoint sh minio-init -c 'mc alias set ... && mc mirror --overwrite local/attachments /backup/attachments && ... images ... packages'`. One current mirror, not one copy per stamp (objects are written once under unique keys; no `--remove`, so an object a later restore needs is not lost). S3 off-site: `aws s3 sync backups/objects s3://$BUCKET/coop-erp/objects`. Leave out `audit-anchors` for the demo (object-locked; anchors are re-derivable by re-anchoring a demo log); before real data it is the one bucket that must go to an object-locked off-site bucket, because it is evidence. `restore.sh` mirrors back the other way.
Business: a restore that leaves broken photos on GRNs is a restore the demo audience sees as data loss. Verdict DECIDE THEN BUILD, S, no migration, risk low (disk: demo uploads are megabytes).

**DEPLOY-13.** Valid: YES (backup.sh:51-57 put the keys on the `docker run` command line; no encryption; the cron line reports nowhere; a failed dump leaves `.part`).
Fix: NEEDS CHANGES in emphasis. Build now: `--env-file` with a `mktemp` 0600 file removed on EXIT; `rm -f backups/*.part` at start; a marker (`backups/LAST_OK` with the stamp, `backups/LAST_FAILED` from an ERR trap) that `deploy.sh` and `smoke` print ("last good backup 3 days ago" is the alert a team without an MTA will actually see). `MAILTO` is useless without an MTA; drop it. Encryption (`age` with a recipient key whose private half is kept off the server with the `.env` copy, never beside `.env` as the finding suggests, or the key dies with the server): required before real data, optional for demo data. Verdict BUILD AMENDED, S, no migration, risk low.

### G3. Keycloak front door and the demo's identity policy (DEPLOY-05, DEPLOY-06, DEPLOY-08, DEPLOY-09). Order: first, in parallel with G1 (the testers are the exposure). Decide first: D-3, D-4.

A point that applies to 05 and 06 and that the verifier's fix scope misses: `render_realm` changes reach only a Keycloak that imports the realm, i.e. a fresh server or `demo-data.sh --reset` (realm import is ignore-existing). The running demo must get the same settings through `kcadm` on every `deploy.sh`, as `set_web_client_urls` already does for the addresses. Add one idempotent `apply_realm_policy` in `lib.sh` and call it from `bootstrap.sh` and `deploy.sh`.

**DEPLOY-05.** Valid: YES (Caddyfile:55-58 proxies all of `/auth/*`; guides publish `/auth/admin/` as the console).
Fix: NEEDS CHANGES. Use an allowlist, not a deny-list of two paths: `handle /auth/realms/coop/*` and `handle /auth/resources/*` go to Keycloak (sign-in pages, tokens for the web client and the tills' device tokens via `OIDC_TOKEN_ENDPOINT`, certs, well-known, `login-actions` for the temporary-password page of phase 4, theme files); every other `/auth/*` answers 404 (admin console, admin REST for every realm, master realm, welcome page). Inside coop, also 404 `/auth/realms/coop/account*` (06) and `/auth/realms/coop/clients-registrations/*` (dynamic client registration; not used). `redir /auth /auth/` goes. The smoke's `/auth/realms/coop/.well-known/openid-configuration` stays green.
Console access (D-3): publish Keycloak on `127.0.0.1:8081:8080` only (loopback publishing is not internet-reachable, unlike 0.0.0.0, see DEPLOY-C1) and set `KC_HOSTNAME_ADMIN=http://localhost:8081/auth`, Keycloak's documented option for a console on a different address than `KC_HOSTNAME`; the operator runs `ssh -L 8081:127.0.0.1:8081 root@<server>` and opens `http://localhost:8081/auth/admin/`. Fallback for anything scripted: `kcadm` from `lib.sh`. The guide's section 5 table changes accordingly.
Brute force: `bruteForceProtected=true` for `coop` and `master` via `kcadm` in `apply_realm_policy` (and in `render_realm` for fresh imports), temporary lockout only (`permanentLockout=false`, Keycloak's defaults of 30 failures, up to 15 min). With ~4 testers per shared user a permanent lockout would be a self-inflicted outage; a success clears the counter, so temporary lockout costs testers nothing.
The bootstrap admin is left as is for the demo; before real data, a named admin per operator with OTP and the bootstrap admin removed. Verdict DECIDE THEN BUILD, S-M, no migration, risk medium-low (an allowlist that misses a path breaks sign-in: the smoke plus one browser sign-in, one temporary-password change and one till enrolment on the local kit settle it).

**DEPLOY-06.** Valid: YES, and wider than written. Three paths let one tester change a shared user's credential: the account console (`manage-account` default role), application-initiated actions (`kc_action=UPDATE_PASSWORD` / `CONFIGURE_TOTP` on the auth URL, as the verifier added), and the application itself: `fed-steward` holds `gov.user.manage` (`seed/m1security/demo-users.demo.sql`, role ...0306), and `ResetCredentialHandler` (M1, `requiresMfa`, satisfied by #184) issues a temporary password to any Federation user, by design of the phase-4 story (`docs/demo/07`).
Fix: NEEDS CHANGES. The verifier's "disable the `UPDATE_PASSWORD` required action" is wrong for this demo: phase 4 issues a temporary password and the new user must choose a new one at first sign-in, which is the `UPDATE_PASSWORD` required action; disabling it breaks the storyline. Build instead:
1. Caddy: 404 for `/auth/realms/coop/account*` (closes the console and the account REST API whatever the roles say); also remove `manage-account` and `manage-account-links` from `default-roles-coop` in `apply_realm_policy`, so the policy is not only in the proxy.
2. Caddy: on `/auth/realms/coop/protocol/openid-connect/auth`, 404 a request whose query has `kc_action` (`query kc_action=*`) and any POST (OIDC allows POSTing the auth request; the web client and the tills only GET it; the sign-in form posts to `login-actions`, which is untouched). This closes AIA without touching the forced required action.
3. `CONFIGURE_TOTP` disabled in the demo realm (no OTP in the demo; nothing needs it).
4. A repair command, because path 3 (the app) stays open on purpose and testers will find others: `demo-data.sh --repair-users` resets every user in `realm-dev.json` to DEMO_PASSWORD (non-temporary), clears their required actions and OTP credentials, and clears brute-force lockouts, all by `kcadm`, without touching data. One minute, versus `--reset`, which wipes the class's work.
D-4 records the policy. Verdict DECIDE THEN BUILD, S-M, no migration, risk low (verify phase 4 end to end on the local kit).

**DEPLOY-08.** Valid: YES (lib.sh:98 writes the backend secret, :112 `chmod 644`).
Fix: NEEDS CHANGES: drop the alternative "`chmod 700` on `/opt/coop-erp`": the postgres container (uid 999) and Keycloak (uid 1000) read bind mounts under that folder with their own uids, so 700 stops both from starting, and 711 still leaves a 0644 file readable by anyone who knows the path. Build the first option: `chown 1000:0 "$out" && chmod 600 "$out"` (Keycloak's image runs as uid 1000, gid 0), and fix the comment. On the laptop kit (Docker Desktop on Windows) chown on a bind mount is a no-op; that is fine. Verdict BUILD AMENDED, S, no migration, risk low (one start of Keycloak on a fresh realm proves it).

**DEPLOY-09.** Valid: PARTLY. The grant is a client setting, so the public token endpoint accepts it during step 3; but every tester already holds DEMO_PASSWORD and can get the same tokens through the browser, so the window adds little for a demo. The verifier's correction (the EXIT trap does run on SIGHUP) stands; a reboot, SIGKILL or a failed `kcadm` leaves the grant on.
Fix: NEEDS CHANGES: the dedicated confidential demo-tools client is not the pragmatic fix. The `ent`, `cls`, `lang`, `uid` and `roles` mappers live on the `coop-erp-web` client (realm-dev.json:52-104), and the backend refuses any other `azp` (`accepted-clients`, application.yml:117), so the new client needs five copied mappers and a widened `OIDC_ACCEPTED_CLIENTS` on the demo server: more surface than it removes. Build: `smoke` (run by every deploy) fails when `coop-erp-web` has `directAccessGrantsEnabled=true` outside a `demo-data.sh` run, so a grant left on is caught; generate DEMO_PASSWORD as `Demo-` plus 12 hex for new servers (an existing `.env` keeps its value); brute force comes from 05. Verdict BUILD AMENDED, S, no migration, risk low.

### G4. The #184 shortcut on a public issuer (DEPLOY-07). Order: any time; kernel code (platform pair). Decide first: D-5.

Valid: YES. JwtClaimsMapper.java:91-100 logs "Loud, not fatal"; #184's description says it is refused; compose.yml:252 sets it on with a public issuer; with the flag on, `mfaAt` returns `auth_time` (or `iat`) whatever the `acr`, so step-up equals password re-entry.
Fix: NEEDS CHANGES in the condition. The suggested second opt-in property is right; "never fall back to `iat` for a token whose `azp` is not the web client" should not be built now: `device-*` tokens are the tills', step-up on the till is a PIN matter (E-05), and narrowing it is a separate kernel change with its own tests. Build: a second property `coop-erp.security.mfa.password-reauth-public-issuer-ack` (env `COOP_ERP_MFA_PASSWORD_REAUTH_PUBLIC_ACK`) that must equal the literal `demo-data-only`; the constructor throws `IllegalStateException` when the flag is on, the issuer is not a development one and the ack is absent. `infra/deploy/compose.yml` sets both, with the comment pointing at D-5. Unit tests: dev issuer + flag starts; public issuer + flag without ack fails; with ack starts and logs a WARN. Correct the kernel README sentence. Verdict DECIDE THEN BUILD, S, no migration, risk low (the two test constructors default to a localhost issuer).

### G5. Front-door and container hardening (DEPLOY-10, DEPLOY-11, DEPLOY-12, DEPLOY-14). Order: 10 and 11 with G3 (same Caddyfile); 12 and 14 before any real data. Nothing to decide.

**DEPLOY-10.** Valid: YES. Fix: NEEDS CHANGES for the objects. Build now for the site: `Strict-Transport-Security "max-age=31536000"` (ignored by browsers on a bare IP, correct on sslip.io or a domain), `X-Content-Type-Options nosniff`, `Content-Security-Policy "frame-ancestors 'self'"` plus `X-Frame-Options SAMEORIGIN`, `Referrer-Policy strict-origin-when-cross-origin`; for `@objects` `nosniff`. Do not add `Content-Security-Policy: sandbox` to objects until it is tried with a printed PDF opened inline in Chrome and Firefox: Chromium refuses to render PDFs in sandboxed documents, and printed PDFs are served from these buckets. The safer object control is the content-type allowlist (keep `image/svg+xml` and `text/html` out of `attachment.content_types`; the register-item guard belongs to M9/kernel, not here). Verdict BUILD AMENDED, S, no migration, risk low-medium (a too-strict header breaks the PDF view; test it).

**DEPLOY-11.** Valid: YES, plus the verifier's addition (`/api/actuator` index is public). Fix: NEEDS CHANGES in order of work. Now: matcher `path /actuator /actuator/*` with the health exclusions (one line). The management port split (`MANAGEMENT_SERVER_PORT=8081`) is the right defence in depth but touches the compose healthcheck, the Caddy health route, the laptop stack and the stack smoke; build it with doc 35 for staging, not for the demo. Verdict BUILD AMENDED, S, no migration, risk low.

**DEPLOY-12.** Valid: YES. Fix: CORRECT. `minio-init` adds user `coop-erp-app` with a policy on `attachments`, `images`, `packages` (Get/Put/List) and `audit-anchors` (Put, PutObjectRetention, Get; no `BypassGovernanceRetention`, no bucket deletes), from two new generated `.env` values; the backend gets those. `bootstrap.sh` must add the two values to an existing `.env` once (it never regenerates; add "append when absent"). Demo-acceptable for now; before real data. Verdict BUILD AS SUGGESTED, S, no migration, risk low.

**DEPLOY-14.** Valid: YES. Fix: NEEDS CHANGES: `cap_drop: [ALL]` cannot go on every service. The `postgres` and `rabbitmq` entrypoints chown their data and drop to their user with gosu (they need CHOWN, SETUID, SETGID, DAC_OVERRIDE, FOWNER); leave their capabilities alone. Build: `security_opt: [no-new-privileges:true]` on every service (now; cheap); `cap_drop: [ALL]` on backend, keycloak, mailpit, pgbouncer, minio, minio-init, demo-tools, and on caddy with `cap_add: [NET_BIND_SERVICE]`; `read_only` + `tmpfs /tmp` deferred to the staging template. Chromium keeps `--no-sandbox` (its sandbox needs user namespaces the default seccomp profile blocks). One start of the local kit plus the smoke proves it. Verdict BUILD AMENDED, S-M, no migration, risk medium (a service that needs a capability fails to start; the local kit catches it).

### G6. CI publish supply chain (DEPLOY-15). Order: any time; small. Nothing to decide.

Valid: YES, with the verifier's addition (`persist-credentials` default true puts the token in `.git/config` for every later step, including `pnpm install` lifecycle scripts and Gradle plugins). Checked: zero of the 50 `uses:` lines in `.github/workflows` are SHA-pinned; Dependabot covers `github-actions` (`/`) and `docker-compose` for `/infra/compose` only, not `/infra/deploy` and not the three Dockerfiles.
Fix: NEEDS CHANGES (scope). Build now: (a) SHA-pin every action in every workflow (the `github-actions` Dependabot entry already updates SHA pins, with the version in a trailing comment); (b) `persist-credentials: false` on the checkout of the anchored package steps (nothing later pushes to git); (c) digest-pin `caddy`, `eclipse-temurin` (three places including `jibBaseImage` in `backend/gradle.properties`, which no bot updates: comment it), `debian:trixie-slim`, and add Dependabot `docker` entries for `infra/web-image`, `infra/demo-tools`, `infra/worker-image` and a `docker-compose` entry for `/infra/deploy`. Do not pin the apt `chromium` version: Debian drops superseded versions from the mirror and the build breaks; the base digest plus the SBOM is enough. Defer the split into a docker-only publish job: a compromised Gradle plugin can still alter the image it builds whatever job pushes it, and moving four images between jobs costs about 1.5 GB of artefact per push; it belongs with signed images and provenance (`attest-build-provenance`) in the doc 35 release workflow, which `deploy.sh` would then verify. Verdict BUILD AMENDED, S, no migration, risk low (a wrong SHA fails the run visibly).

## Decisions to record

Each is written so it can be recorded "accepted on the architect's delegation" if the architect so chooses; none is accepted by this review.

- **D-1 (DEPLOY-02) The demo runs explicit commit SHAs of main, chosen by the operator.** `deploy.sh` pins `IMAGE_TAG` to the clone's HEAD after checking GHCR has that SHA, records the previous one, and backs up first; the `main` tag stays published but no script uses it. Rejected: following the moving `main` tag (clone and image drift, no rollback record); automatic deploy on every merge (#247's model: the demo would change under a class mid-session, and a failed migration would land unattended); release tags now (there is no release process until doc 35). Why: one rule that makes files, seeds and images the same commit, at no cost to the team.

- **D-2 (DEPLOY-04) Uploaded objects are backed up with the databases.** `backup.sh` mirrors `attachments`, `images` and `packages` after the dumps, locally and to the S3 target; `audit-anchors` is left out for the demo and becomes mandatory (to an object-locked bucket) before real data. Rejected: "uploads are not backed up" in the guide (a restore then shows broken documents, which reads as data loss; the alternative costs fifteen lines); a volume tarball (inconsistent while MinIO writes, tied to MinIO's on-disk format). Why: a restore must give back what testers made.

- **D-3 (DEPLOY-05) Keycloak's public surface is the coop realm and the theme files only; the console is reached through an SSH tunnel.** Caddy proxies `/auth/realms/coop/*` (less `account*` and `clients-registrations/*`) and `/auth/resources/*`; Keycloak is published on 127.0.0.1:8081 with `KC_HOSTNAME_ADMIN=http://localhost:8081/auth`; brute-force protection with temporary lockout on both realms. Rejected: a deny-list of two paths (misses the next one); basic auth in front of the console (keeps the admin endpoints internet-reachable and adds a second shared password); an IP allowlist (operators on dynamic addresses lock themselves out). Why: admin endpoints off the internet at the cost of one SSH command for a task done rarely.

- **D-4 (DEPLOY-06) Demo identity policy for a class of testers.** Shared role users with one DEMO_PASSWORD remain (the users are characters of the storyline, bound to entities and scopes by the seeds; per-tester copies would need seeded scopes for each); no self-service on the demo (account console and application-initiated actions blocked, OTP enrolment disabled, registration and reset-by-mail already off); the forced password change for a new user stays (phase 4); credential changes made through the application are accepted and repaired by `demo-data.sh --repair-users`. Rejected: one user per tester (seed work for every class, and the story is told by role); disabling the `UPDATE_PASSWORD` action (breaks phase 4). Before real data the policy inverts: one account per person, self-service password change, OTP for admin and money roles. Why: keeps the story working for 80 people and makes the inevitable lock-out a one-minute repair, not a data wipe.

- **D-5 (DEPLOY-07) A public issuer may run the #184 shortcut only on a demo server holding demo data, by an explicit second opt-in; never on staging with real parties or in production.** The backend refuses to start when the flag is on with a non-development issuer and the acknowledgement `COOP_ERP_MFA_PASSWORD_REAUTH_PUBLIC_ACK=demo-data-only` is absent; only `infra/deploy/compose.yml` sets it; staging gets Keycloak OTP and the flag off. Rejected: fatal outside development without exception (the demo then cannot show any step-up action: publishing a price list, signing a balance); keeping the log line (the template would carry it into a real environment silently). Why: the demo needs the shortcut; nothing else may inherit it by copying a compose file.
