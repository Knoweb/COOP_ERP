- **WCD-01 web/src/shell/auth/oidc.ts:77-84, web/src/shell/api/client.ts:161, web/src/shell/auth/StepUpReplay.tsx:39** [medium] [security] The step-up replays the interrupted command as whoever completes the sign-in, not as the user who was interrupted (PR #123, kept by #264).
  Scenario: user A (an accountant) confirms a payment reversal on a shared counter PC; the server answers `mfa.required`; the shell stores A's command in the login state and calls `signinRedirect({ prompt: "login" })` with no `login_hint` or `id_token_hint`. The sign-in page has an editable username (the theme's `login.ftl` always shows the field), so user B signs in. `onSigninCallback` keeps the command (it only checks URL and keys), `StepUpReplay` sends it with B's fresh token, B's scope headers and A's Idempotency-Key. A's command now runs as B, who never confirmed it and may hold a wider role; the audit row names B.
  Fix: put the session's `sub` in `LoginState`, send `login_hint` (or `id_token_hint`), and in `onSigninCallback` drop the command (and say "enter the details again") when `user.profile.sub` differs.
  **CONFIRMED** (medium). Verified by: Claude Opus 5.5, reading. `client.ts:161-165` sends only `prompt`, `acr_values` and `state` (no `login_hint`/`id_token_hint`); `LoginState` (`oidc.ts:37-42`) has no subject; `onSigninCallback` (`oidc.ts:77-84`) checks only `mayKeep` (URL and keys); `login.ftl:77` renders an editable `username` input. No server guard helps: the idempotency row is per user (`kernel/V0010__idempotency_key.sql`, `user_id`), so A's key under B's token is a new command, and the backend's MFA check only needs a fresh `auth_time`. B's own permission check still applies, so B can only run what B's role allows; the harm is a command B never confirmed, attributed to B. Not run in a browser.
  Suggested fix scope: S, no migration, no design decision (web only: `sub` in `LoginState`, `login_hint`, compare in the callback, one test in `StepUpReplay.test.tsx`).

- **WCD-02 web/src/shell/auth/StepUpReplay.tsx:36-60 with web/src/shell/scope/ScopeContext.tsx:96-103** [medium] [correctness] The replay runs as soon as an access token exists, before the session read has told the shell the user's one location, so for a location-scoped user it goes out with `X-Scope-Entity` and no `X-Scope-Location` (PR #123; plausible, not run).

  **CONFIRMED** (medium).   Suggested fix scope: S, no migration, no design decision (gate on `permissions !== null`, or store the two scope ids in `PendingCommand`; add a test with a location-scoped user).
