## till/core: sign-in, supervisor, clock, snapshot (5)
- CONFIRMED **TILLM6-02 till/core/src/commonMain/kotlin/lk/coopfed/knoweb/till/core/TillService.kt:296** [medium] [security] The PIN lock-out counter is one per till and every successful sign-in sets it back to 0 (also `correctBusinessDate` :430), so a cashier who knows her own PIN can guess another operator's PIN without ever being locked out. (PR #266)
  Scenario: the cashier picks the supervisor on the sign-in screen and tries 4 PINs (PIN_FAILURES = 4), signs in as herself with her correct PIN (PIN_FAILURES = 0), signs out, and repeats. The limit of 5 is never reached, no `TILL_PIN_LOCKOUT` fact goes to central, and a 4-digit supervisor PIN falls in at most 2,500 rounds. With it she holds `pos.session.manage`, and later void and refund once the till checks them. Fix: keep the failures per target operator (a setting keyed by user id, persisted the same way) and the till-wide count as a window that a success does not clear. A success resets only the counter of the operator who signed in. Add a test that interleaves wrong PINs for B with correct sign-ins by A and expects the lock-out.
  Verification: `signIn` (TillService :289-299) writes `PIN_FAILURES = 0` on any correct PIN, whatever operator failed before; `countWrongPin` (:317-331) keeps one till-wide counter; `correctBusinessDate` (:437) resets it too. The sign-in screen lists every operator (`TillApp` :227-241), so the cashier can pick the supervisor. The scenario holds.
  Suggested fix scope: S, no migration (till settings), no design decision.
  Verified by: Claude Opus 5.5 (wave 3 verifier, main ec4c5758, by reading; no Gradle run, Docker down).

Add a contributor test with a TILL user without the code.
  Verification: the only permission test in till/core is `SUPERVISOR_PERMISSION in supervisor.permissions` (:418); `openSession` (:366-389) and `sellForCash` (:446 on) need only a signed-in operator; `Catalogue` (:115-124) builds an operator from every `operator` row with no permission filter; the contributor's query needs any ACTIVE role at the shop, not `pos.receipt.issue`. - CONFIRMED (narrowed) **TILLM6-05 till/core/src/commonMain/kotlin/lk/coopfed/knoweb/till/core/TillService.kt:406-435** [low, was medium] [security] When a supervisor moves the business date back, the till records nothing: no `audit.*` fact in the outbox, no local anomaly. The move also has no lower bound, so the date can go to any earlier day. Every later session and receipt carries that date. (PR #266)
  Scenario: a supervisor (or the cashier of TILLM6-02 with the supervisor's PIN) moves the business date from 9 October back to 1 October with no session open and sells all day. The receipts reach central dated a business day M8 has long reported and the society may have closed. Central has no record of who moved the date or when, and M6 raises no flag for a business date far behind `issued_at`. Fix: write an `audit.till_business_date_corrected.v1` fact in the same transaction, with the supervisor's user id, the from and to dates and the reason, as `TILL_PIN_LOCKOUT` does (a catalogue code, REVIEW, `offline_capturable`). Refuse a date earlier than central's last `server_time` date minus the lead. Add an M6 flag for a receipt whose business date is more than a day before its `issued_at` date.
  Verification: no `record(...)` call and no anomaly in `correctBusinessDate` (:406-442), and no `business_date_corrected` fact anywhere; M6 stores `business_date` with no plausibility flag. The unaudited move is confirmed. The scenario's back-dating is not: `openBusinessDay` (:901-904) opens a session on the later of today (by the till's corrected clock) and the stored date, so a move back to 1 October is undone by the next `openSession` on 9 October. Sessions dated 1 October need the till's clock to read 1 October too, which with a stored offset means moving the PC clock back (offset dropped, CLOCK anomaly kept locally); `issued_at` then also reads 1 October, so the proposed "business date before issued_at" flag would not catch it (central's received time would). Severity lowered to low: the lower bound is in effect the till's own date; what remains is the missing audit fact.
  Suggested fix scope: S, catalogue seed row for the fact (no schema migration), no design decision.
  Verified by: Claude Opus 5.5 (wave 3 verifier, main ec4c5758, by reading; no Gradle run, Docker down).
- CONFIRMED **TILLM6-06 till/core/src/commonMain/kotlin/lk/coopfed/knoweb/till/core/TillService.kt:261-262** [low] [security] A snapshot answer at the version the till already holds (signed `since = version = held`) only refreshes `LAST_SNAPSHOT_AT`. Any captured no-change answer can therefore be replayed for ever to keep the staleness banner off. The decision names that banner as the control in place of a signed issue time. (PR #266)
  Scenario: an on-path party that can answer for central (it needs the TLS trust of D-1, e.g. a CA added with `COOP_TILL_CA_FILE` or a corporate proxy) withholds a lowered control price. It answers every `GET snapshot?since=v` with the signed no-change answer it captured at version v. The till stays at v, and the "prices may be out of date" banner never appears. Fix: put an issue time in the signed manifest and set `LAST_SNAPSHOT_AT` from it, refusing one older than the stored value. Otherwise refresh staleness only on a version change or a signed heartbeat time.
  Verification: `refreshSnapshot` (:260-263) sets `LAST_SNAPSHOT_AT` from the local clock when `delta.version == current.version`; the signed manifest carries version, location_id, full, tables and since (SnapshotVerifier :48-66), no issue time, so a captured no-change answer verifies for ever. Needs the attacker to hold TLS trust, as stated.
  Suggested fix scope: M (central and till), no migration, small design decision (manifest field).
  Verified by: Claude Opus 5.5 (wave 3 verifier, main ec4c5758, by reading; no Gradle run, Docker down).
- CONFIRMED **TILLM6-07 till/core/src/commonMain/kotlin/lk/coopfed/knoweb/till/core/TillService.kt:337-340** [low] [security] The lock-out end is compared with `now()`, which is the PC's clock once the offset is dropped, or when none is stored. Moving the Windows clock forward 15 minutes ends a lock-out. With no stored offset, nothing is recorded. (PR #266)
  Scenario: the till has not synced since the last restart (no `CLOCK_OFFSET_MS`), or the clock jump drops the offset. After 5 wrong PINs the cashier sets the PC clock ahead by 16 minutes and gets 5 more tries, again and again. `now()` writes a CLOCK anomaly only when an offset existed. Fix: store the remaining lock time and count it down with `clock.elapsedMillis()`. After a restart, treat the full remaining time as still to run. Never let a forward clock shorten it.
  Verification: `lockedOutMessage` (:336-339) compares `PIN_LOCKED_UNTIL` with `now()`; `now()` (:864-891) returns the raw PC clock when no offset is stored, and on a jump drops the offset and returns the raw clock (anomaly local only). Moving the clock forward ends the lock-out.
  Suggested fix scope: S, no migration, no design decision.
  Verified by: Claude Opus 5.5 (wave 3 verifier, main ec4c5758, by reading; no Gradle run, Docker down).

Nothing in M1 calls `ChangeLog.append` when a role is assigned, revoked or amended, a PIN is reset or a user is deactivated (m1party README :168, "Still M1-10's"). A till that syncs normally only ever gets deltas, so the till roles of #304 and #301 reach a till only at its first enrolment. (PR #304, #301; the gap is the open M1-10 ticket)

AssignRole, RevokeRole, AmendRole (fan out to the role's holders from a worker consumer, as 19A says), ResetCredential (PIN), UpdateUser (kind) and DeactivateUser append `Change.upsert("operator", userId)` for each shop where the user operates, `urgent = true` when a permission or the user is removed. Add a test where a revoke produces a tombstone in the next delta.
  Verification: on main the only `ChangeLog.append` caller is `m7customers/.../CustomerChangeLogFanOut`; no Java handler and no SQL (`change_log_append` appears only in kernel V0080-V0087) appends an `operator` change; m1party README :168 still lists the producers as M1-10's. `RevokeRoleHandler` :89 deletes the `user_role` row, so the contributor would drop the user, but nothing tells a delta to look. Open PR #314 (`M1ChangeLogFanOut`, not merged, not counted here) would close it: event consumers on RoleAssigned/RoleRevoked (targets from the event's scope, urgent on revoke), RoleChanged (fans out to every holder's shops, urgent), UserDeactivated/UserCredentialReset (urgent) and UserCreated/UserUpdated/UserActivated, each appending `Change.upsert("operator", userId)`; deactivation keeps the `user_role` rows, so its target lookup finds the shops, and the till applies tombstones (`Snapshot.kt`). Points for #314's own review: its location events append for any location type, not only SHOP; its integration tests were not run here; it also drops `ARCH_TESTS=:app:test` from CI and sets `maxHeapSize`, unrelated to the finding.
  Suggested fix scope: M, no migration, no design decision (merge #314 after review).

  Suggested fix scope: S-M, possibly a migration (per-series hold), no design decision.
