## Fix group A: journal export integrity (M9-05, M9-03, M9-01)

The accountants of a cooperative need four guarantees from the export: (1) a file for a closed period is complete when it is generated, or says plainly that it is not; (2) each posting reaches the package exactly once; (3) anything that arrives late for a period already exported is flagged and can be fetched as a supplement; (4) a file can be downloaded again, byte for byte, with the hash that proves it is the same file. The build gives (2) only. The supplement mechanics of (3) exist, but nothing flags a late posting. (1) and (4) are missing.

Order of work: M9-05 first, because the PROVISIONAL mark of M9-03 changes the file. Then M9-03. M9-01 is independent and can go in parallel, but it must land before group B, whose GRN postings are dated by location. Decide first: D1 (provisional), D2 (stored file).

### M9-05 [low] BUILD AMENDED, M, migration yes
1. **Valid: YES.** `IntegrationQueriesImpl.file` (line 116) and `reconciliation` (line 146) both re-run the current `JournalFile.csv` over `journal_line`. Nothing records which writer made `content_hash`. When the header changes, or the escaping, or a column is added (and M9-03 must add the PROVISIONAL mark), every past export fails reconciliation, and a re-download is no longer the file the package imported.
2. **Fix: NEEDS CHANGES (the verifier left the choice open).** Store the bytes, and also record a format version. A format version alone depends on nobody ever touching the frozen writer again. New migration `m9integration/V0006`:
   - `integration.journal_export_file(export_id uuid PRIMARY KEY REFERENCES integration.journal_export, format_version smallint NOT NULL, content bytea NOT NULL, content_hash char(64) NOT NULL, owner_entity_id uuid NOT NULL)`. Insert only (`GRANT SELECT, INSERT`), with the four-class template policies. PostgreSQL TOAST compresses CSV well, so a month of an MPCS's journal is a few tens of KB stored.
   - `RequestJournalExportHandler`: build the bytes once, hash those bytes, and insert the file row in the same transaction as `journal_export`. The write is in one transaction, which object storage could not give, and the kernel's `ObjectStorage`/`Attachments` APIs only issue pre-signed client PUTs, with no server-side put.
   - `file()` returns the stored bytes. `reconciliation()` checks (a) the hash of the stored bytes against `journal_export.content_hash`, and (b) the lines' totals and by-role sums, as now. It also regenerates with the writer of the recorded `format_version`, to prove that lines and file agree.
   - Exports made before V0006 have no file row. They are served by `JournalFile` frozen as version 1 (rename it `JournalFileV1`, and leave a comment that it must never change). Version 2 adds a `format_version`/PROVISIONAL marker (see M9-03).
   - Tests: the reconciliation stays true after a v2 writer exists, and a pre-V0006 export downloads unchanged.
3. **Business: stored bytes is best.** The accounting package imported a file, and an auditor asks for that file. Alternatives considered: version plus frozen writers only (cheaper, but one careless edit breaks every past hash); object storage as 29A says (not transactional, and it needs a new kernel server-put API; it can replace the bytea later through a CR if volume ever needs it). Risk: low. The handler gains one insert, and the download path changes.

### M9-03 [medium] DECIDE THEN BUILD, M, no migration
1. **Valid: YES.** `RequestJournalExportHandler` checks the period only for being present and in order (lines 79-84), and inserts `provisional=false` (line 151). The web default period ends today (`integrationView.ts:22-25`). `pending()` covers only the period entered. Doc 29 §4.2 says the guard is "period closed (all locations' day-close past period end) or explicit 'provisional' flag", and §6.2 says "marked PROVISIONAL in the file".
2. **Fix: NEEDS CHANGES.** The verifier offered "refuse `periodTo >= today`, or mark provisional". On its own, refusing breaks the demo path: a presenter issues an invoice and exports it the same day. On its own, marking leaves late postings silent. Build all three of the following:
   - **Guard (`m9.journal.period_open`, new message id in en/si/ta):** refuse when `periodTo >= today` in `coop-erp.business-timezone` and the request does not carry `provisional: true`. Add the optional boolean `provisional` to the `RequestJournalExport` command and to the OpenAPI request (an additive change; 29A §5 already lists `provisional?`). When location-dated postings arrive (group B's GRN, M5 WOF/ADJ), extend "closed" to "every location of the entity has `BusinessDate.current(location) > periodTo`". That needs `m1party::query` added to M9's `allowedDependencies`, or the location carried on the postings. Write that as a TODO that cites this decision.
   - **Provisional export:** insert `provisional=true`. Its postings are exported once, like any other: no supersede, and no unique-index rework (see D1). The list, the file name (`journal_..._PROVISIONAL.csv`) and the v2 file (after M9-05) show the mark. Audit `after` and `JournalExportGenerated` carry `provisional`.
   - **Late-posting signal ("supplement due"):** add a query, and a field on the exports list response, giving the unexported postings dated on or before the latest `period_to` this entity has exported (count, amount, earliest and latest date). The page shows a banner, "N postings for periods already exported: export the supplement". This one query catches a posting that arrives after midnight through consumer lag, a dead-letter replay, and the open-period case alike.
   - Web: the default period ends yesterday, and the form shows a provisional checkbox that is ticked, and required, when the end date is today or later.
   - Tests: refused without the flag; provisional recorded and marked; the supplement-due count appears after a late posting; the 29A property "original + supplements = fresh full export".
3. **Business:** see D1. Risk: low to medium. The OpenAPI request changes, and existing tests and the demo script that export "to today" must pass `provisional`.

### M9-01 [low] BUILD AMENDED, S, no migration
1. **Valid: PARTLY**, as the verifier narrowed it. The receipt scenario follows the design: an entity-level document's business date is the Colombo date of issue (`IssuanceProtocol.businessDateFor:251-261`). What holds is that M9 derives the date (`JournalPostingsConsumer:59-62`) instead of carrying `d.businessDate`. That is harmless today, apart from a midnight straddle between `issuedAt` and `occurredAt` (both are `clock.instant()` in one transaction, milliseconds apart). It will be wrong for every location-dated document: the buyer's GRN, M5 WOF/ADJ.
2. **Fix: NEEDS a small change.** Add `LocalDate businessDate` to `m4trading/api/JournalPostingsReady` and fill it from the issued `DocumentRecord.businessDate()` at all six publishers (IssueInvoice:261, IssueCreditNote:142, SettleDiscrepancy:251, ApproveClaim:249, RecordPaymentReceipt:218, RecordChequeOutcome:222). For the cheque reversal, use the reversal PRC's own date, not the original receipt's. M9 reads `payload.businessDate` and falls back to `occurredAt` only when the field is absent, which happens only for events published before the change and later replayed. Comment the fallback with that reason. Additive payload, well under the 8 KB limit. Tests: one per publisher asserting the field, and one consumer test with the field absent.
3. **Business:** keep receipts dated by issue date (D5). The officer who records a 30 September cheque on 2 October produces an October document. Doc 29 §6.3 handles this as a late document in a supplement, and the bank reconciliation in the package uses the cheque's own date. Optional, after M9-05: carry `receivedOn` in `journal_line.reference` (a column that exists and is unused) so the accountant can see it. Risk: low.

## Fix group B: buyer-side postings (M9-02, with M4MONEY-10)

### M9-02 [medium] DECIDE THEN BUILD, L (interim S), no M9 migration
1. **Valid: YES.** `posting-map.yaml:15-17` seeds the BUYER rows. Every M4 call asks for "SELLER". `RecordJournalPostingsHandler:101` files every line under `scope.entityId()`, whatever its `side`, and accepts BUYER (line 130). `ConfirmGrn` publishes no postings. Doc 29 §3.3 and §6.2 require "GRN and INV (buyer)". An MPCS's export has no purchases, no payables and no VAT input, so its trial balance cannot match its supplier's statement. That matters most to the 800 MPCS, which are buyers first. M4MONEY-10 is the same gap seen from M4. It is a recorded deferral in the progress deviations, but it is missing from M9's README and from NEXT.md.
2. **Fix: the verifier's options need a decision (D3). Recommended build:**
   - **GRN (buyer):** `ConfirmGrnHandler` publishes `journal.postings_ready.v1` in the buyer's own scope (the buyer confirms the GRN, which is idea 2 of AGENTS.md), with side BUYER and INVENTORY/GRN_ACCRUAL at the price the invoice will use (the delivery note's price snapshot). If the accrual uses another cost, INV BUYER leaves a residue on GRN_ACCRUAL, and M4's map would need a price-variance role. M4 must state which price it uses. This path needs no new mechanism, but it needs M9-01, because a GRN at a location takes that location's business date.
   - **INV, CN, DN2 and PRC (buyer):** the buyer does nothing in the system when an invoice is issued, so there is no buyer act to hang the posting on. M4 adds the BUYER lines (map rows for CN BUYER, DN2 BUYER and PRC BUYER, for example PAYABLE/BANK for a payment, added to the seed) and `counterpartyEntityId` to the seller's event. The kernel's consumer dispatcher gains a counterparty delivery: a consumer registered for the counterparty (for example `@EventConsumer(..., party = COUNTERPARTY)`) is invoked in the OWN scope of the payload's counterparty, taken by the same rule as `NotificationDispatcher.otherParty`, only for events whose source is central (never a till's event), and with its own inbox row. M9 registers `m9.journal.buyer`, which records only the BUYER lines, under the normal `own_write` policy. The existing `m9.journal` records only the SELLER lines.
   - **Interim, now (S):** in `JournalPostingsConsumer`, record only lines whose side is the scope's side (SELLER on the owner's event), and log BUYER lines at WARN with the document id, so that an early M4 change cannot file the buyer's books under the seller. Add a README deviation, "buyer-side postings not exported (M4MONEY-10, M9-02)", and a NEXT.md item.
3. **Business:** see D3. Risk: medium. It touches a kernel dispatcher used by every consumer, and it is a CR for docs 19 and 19A. The GRN part is low risk and can ship first.

## Fix group C: notification log and delivery, kernel (M9-07, M9-08, M9-10; with TWK-20, TWK-21, TWK-22)

One kernel PR for the platform pair, with one kernel migration (next free number above `V0083`; coordinate it with the TWK-20 fix, which is the same work). Order: decide D4 and D6, then build M9-07 and M9-10 (no decision needed for the hash itself), then M9-08 on the same migration.

### M9-07 [medium] BUILD AMENDED, M, migration yes (data)
1. **Valid: YES.** `NotificationLog.hash:66-73` is plain SHA-256 of `channel:recipient`. `IntegrationQueriesImpl:242` returns 48 bits of it to the event owner, so the seller sees a hash of the buyer's ACCOUNTS phone. The 10^8 mobile space falls in minutes, as reproduced. TWK-20 is the same defect, seen at rest.
2. **Fix: NEEDS CHANGES.**
   - HMAC-SHA-256 under `coop-erp.notification.recipient-hash-key` (base64, 32 bytes). Handle the key like `pending-key`: a development key with a warning only for a development issuer, otherwise a failed start, and generated by the deploy bootstrap. Use a separate key, not `pending-key`, because that key is meant to rotate daily, and every rotation breaks de-duplication and the unique `(rule_id, event_id, recipient_hash)`. The output is still 64 hex characters, so `char(64)` fits.
   - **The verifier's "no migration" leaves every existing row brute-forceable at rest.** The clear recipient is gone, so legacy hashes cannot be re-keyed. Add a kernel data migration that sets `recipient_hash = encode(gen_random_bytes(32), 'hex')` for rows created before the cut-over (pgcrypto is installed). Each row stays unique. This loses only the one-hour de-duplication for those old rows, which is past anyway.
   - **The verifier's stopgap ("no hash for counterparty recipients") cannot be built:** the row does not record the recipient's entity. The stopgap that can ship alone is to drop `recipientHash` from the log endpoint, the OpenAPI response and `NotificationsPage.tsx:204` altogether.
   - The lasting screen (D4): add `recipient_entity_id uuid NULL` and `audience_role text NULL` to `kernel.notification_log`. Fill them from a widened `NotificationAudience.Recipient(channel, recipient, language, entityId, roleCode)`, an additive kernel API change; ContactAudience knows both values. The screen shows "MPCS Horana, ACCOUNTS, SMS" plus an 8-character tag of the keyed hash, so that two numbers of one role can be told apart. The same column serves M9-08.
3. **Business:** see D4. Risk: low to medium. The dispatcher, the unique key and the de-duplication all move to the new hash at deploy, and one in-flight retry across the deploy keeps its old hash, which is harmless. Shares a pattern with M7CR-01 (NIC pepper): consider one kernel `KeyedHash` facility.

### M9-08 [medium] DECIDE THEN BUILD, M, migration yes (shared with M9-07)
1. **Valid: YES.** `NotificationService:150-155` marks the row SUPPRESSED before the hold is written. `:211-216` suppresses and clears on a retry. A SUPPRESSED row is never claimed again. The window is read in `ctx`/`owner`, the event owner's scope (`NotificationSuppression:73`). TWK-22 is the same defect. Its "malformed window" half is mitigated by the registry pattern, but `inQuietHours` should still treat a value it cannot parse as "no quiet hours" and log a WARN, rather than throw past the dispatcher's `ProblemException` catch.
2. **Fix: NEEDS CHANGES to the suggested scope.**
   - `NotificationSuppression` returns either a suppression reason (kill switch, duplicate) or a "defer until" instant: the next end of the window, in `coop-erp.business-timezone`.
   - At queue time, deferral writes the hold as usual, sets `next_attempt_at` to the window's end and does not register the after-commit attempt. The row stays QUEUED.
   - At retry time, the claim has already done `attempts + 1`, so add `NotificationLog.defer(id, until)`, which sets `attempts = attempts - 1, next_attempt_at = until` while the row is QUEUED. A deferral is not an attempt. Do not clear the hold.
   - `MAX_AGE` needs no exemption: a window is shorter than 24 hours, and the three backoffs add 21 minutes. The verifier's "exclude the wait from the age" is unnecessary. State this in a comment.
   - The window is read for the recipient's entity, `recipient_entity_id` from M9-07 (the owner when null: EXPLICIT, CUSTOMER).
   - The log screen shows a QUEUED row whose `next_attempt_at` is in the future and whose `attempts = 0` as "deferred (quiet hours) until 07:00". No new status.
   - Change `NotificationsPostgresIntegrationTest.theKillSwitchAndTheQuietHoursSuppress`: the kill switch still suppresses, and quiet hours defer and send at 07:00. In `NotificationDeliveryPostgresIntegrationTest.arrange`, clear the window for the buyer, not the seller.
   - Write a CR for 19A §10 (its test list says "quiet-hours suppression"), to read "quiet-hours deferral".
3. **Business:** see D6. Risk: medium. The retry state machine changes, and the sweep then drains a burst at 07:00 (a few hundred SMS at most; the daily cap is not built yet).

### M9-10 [low] BUILD AMENDED, S, no migration
1. **Valid: YES (latent).** `NotificationService:255` puts `class: message` into `last_error`, and `:260` puts the message into the insert-only audit row. `SmsChannel.send:31` passes the gateway's exception through unchanged. TWK-21 is the same defect at kernel level.
2. **Fix: NEEDS CHANGES.** Fix it where every channel passes through, in the kernel (TWK-21). Store `failure.getClass().getSimpleName()` plus, for a `ProblemException`, its message id, never `getMessage()`. The audit `after.error` gets the same value. The full text goes to the application log at DEBUG only, with the notification id. Also wrap in `SmsChannel` (catch, then rethrow `IllegalStateException("SMS gateway did not take notification <id> (<class>)")`, as SMTP does), and add one line to the `SmsGateway` javadoc: "must not put the recipient or body in an exception message; the notification id is the idempotency key". A unit test makes a gateway throw a message containing `+9477...` and asserts that neither `last_error` nor the audit row contains it.
3. **Business:** this is AGENTS.md's no-phone-in-audit rule, and an audit row cannot be corrected afterwards. Risk: low. Operators lose the provider's text in the log row and keep it in DEBUG logs.

## Fix group D: the contact door (M9-06)

### M9-06 [low] DECIDE THEN BUILD, S to M, migration yes
1. **Valid: YES.** `V0003:24-40`: the SECURITY DEFINER function has no scope reference, and EXECUTE is granted to `app_rw`. `fed_view` (line 16) contradicts the migration's own "own contacts only". No path is reachable today (`ContactAudience` binds the event's parties).
2. **Fix: NEEDS CHANGES, in two steps.**
   - Now: `m9integration/V0007` (or `V0006`, if group A has not taken it). `DROP POLICY fed_view ON integration.notification_contact`, and `CREATE OR REPLACE FUNCTION` adding `WHERE kernel.scope_class() = 'OWN'` (FEDERATION_VIEW and EXTERNAL then get nothing). Update the `RlsMatrixIntegrationTest` departure for `notification_contact` to "federation and external read nothing", or the matrix fails. Never edit V0003.
   - After D7: the function answers only when `p_entity = kernel.scope_entity()`, or when the two entities are parties to an issued document. The `document_counterparty_idx` index exists. The verifier's alternatives: an M1/M4 relationship lookup breaks module boundaries; an outbox-based check duplicates the dispatcher's `otherParty` in SQL and fails on a replay after outbox partitions are dropped; resolving in a system scope widens the scope rather than narrowing it.
3. **Business:** an entity may reach the contacts of the entities it trades documents with, which is exactly whom its rules notify. Risk: low. A brand-new buyer has its first document issued in the same transaction that publishes the event, so the check passes.

## Fix group E: SMTP adapter (M9-09, M9-11)

## Decisions to record

Each decision below is written so that it can be recorded "accepted on the architect's delegation". None is accepted by this review.

- **D1 (M9-03), the provisional export.** Decision: an export whose `periodTo` is today or later in Asia/Colombo (later: any location of the entity whose business date has not passed `periodTo`) is refused, `m9.journal.period_open`, unless the request says `provisional: true`. A provisional export takes its postings once, like any other export, and is marked PROVISIONAL in the list, the file name and the file. What arrives later for its period is a supplement, never a superseding re-export. Every export list shows "supplement due" for unexported postings dated within periods already exported. Rejected: doc 29's "superseded later" (the accountant would have to reverse an imported file in the package, and the posting-once unique index would need rework); refusing open periods outright (it breaks the same-day demo export and month-to-date reviews); marking without refusing (the default action would make provisional files silently). Why: imports are append-only for the accountant, and nothing is lost or doubled. Doc 29 §6.2 and 29A §5 need a CR for the meaning of "provisional".
- **D2 (M9-05), the stored file.** Decision: the generated bytes are stored in `integration.journal_export_file` (bytea, insert-only), in the export's own transaction, with a `format_version`. Exports made before it are served by the version-1 writer, frozen. Rejected: a format version alone with frozen writers (one edit breaks every past hash); object storage now (not transactional, and no server-side put in the kernel). Why: the auditor's question is "show me the file you gave the package". Amends README deviation 2.
- **D3 (M9-02, M4MONEY-10), the buyer's postings.** Decision: the buyer's GRN postings are published by ConfirmGrn in the buyer's scope. The buyer's INV, CN, DN2 and PRC postings travel on the seller's event as BUYER lines with `counterpartyEntityId`. A new kernel counterparty delivery runs a registered consumer (`m9.journal.buyer`) in the OWN scope of that counterparty, only for central events, and that consumer records the BUYER lines. M4 seeds the missing BUYER map rows and states the price the GRN accrual uses. Rejected: a buyer "acknowledge invoice" act (800 MPCS would have to click to make their books right, and a missed click is a missing payable); M9 inserting under a SECURITY DEFINER function for the counterparty (a second narrow door like M9-06, which is harder to test than RLS); removing the dead map rows (the MPCS's books are the point). Why: the payable exists when the invoice is issued, whoever looks at it. A CR is needed for docs 19 and 19A (dispatcher) and 24 (map rows).
- **D4 (M9-07, TWK-20), the recipient on the log.** Decision: `recipient_hash` is HMAC-SHA-256 under a dedicated, non-rotating key, `coop-erp.notification.recipient-hash-key`. Legacy hashes are replaced by random values. The log screen shows the recipient's entity, the role and the channel, plus an 8-character tag of the keyed hash, and never the unkeyed hash. Rejected: keeping the 12-hex SHA-256 prefix (reversible); showing nothing (an operator cannot tell whether the buyer's accounts desk was reached); a per-row random label (it cannot show that two rows reached the same person). Why: docs 19 §7 and 29 §8 ask for "recipients hashed", which an unkeyed hash of a phone number does not achieve.
- **D5 (M9-01), the date of a receipt.** Decision: every posting carries the business date of its document as issued (`document.business_date`, CR-19A-8), receipts included. `receivedOn` is shown as a reference, not used as the date. Rejected: dating by `receivedOn` (it would make the September export change after it was generated, against doc 29 §6.3). Why: a document is immutable, and its date is part of it. Late paper is a supplement.
- **D6 (M9-08, TWK-22), quiet hours.** Decision: doc 29 §6.4 governs. A notification that falls in quiet hours is deferred to the end of the window (07:00 by default) in Asia/Colombo, never dropped. The window is the one configured for the recipient's entity (the event owner's when the recipient has no entity). The kill switch and the hourly duplicate still suppress. Rejected: 19A's "suppression" (an evening bounced cheque would never reach the MPCS by SMS); the sender's window (a distributor would decide when a society's staff phones ring); a per-rule "drop if deferred" flag (no v1 rule needs it; add it with the first time-critical template). Why: "per recipient" in doc 19 §7. With no per-person settings in M1, the entity is the nearest owner of the setting. A CR is needed for 19A §10.
- **D7 (M9-06), the counterparty in the contact resolver.** Decision: `notification_recipients` answers only in an OWN scope, and only for the scope's own entity or for an entity that shares an issued document with it, through a kernel `are_document_parties` helper. `fed_view` on contacts is dropped. Rejected: M1/M4 relationship tables (module boundaries); the outbox (replays); a system scope for the dispatcher (it widens access). Why: you may reach those you trade with, and no one else.

## Findings I could not settle

- **M9-02, GRN accrual price.** I could not establish from M4's code or doc 24 which price `GRN GOODS BUYER` would use (PO, delivery-note snapshot or invoice).
