# Code review wave 2: the fix plan

Written 6 October 2026 on the architect's delegation, after every "decide then build" finding of the eight fix reviews was decided. The decisions are the files `docs/progress/deviations/2026-10-06-wave2-*.md` (23 files); the twelve change requests they needed are `CR-18-2`, `CR-19A-12`, `CR-19A-13`, `CR-21A-7`, `CR-23A-1`, `CR-24A-3`, `CR-25A-1`, `CR-27A-1`, `CR-28A-2`, `CR-29-1`, `CR-30-2`, `CR-32-1`. Nothing below is built yet; this file says what each pull request carries, in which order they merge, and what may run side by side.

The brief asked for nine to twelve pull requests. The plan has **seventeen**: one module per PR, so one reviewer reads one module's migration and one module's handlers, and the demo server (strict Flyway, database kept across releases) sees each module's migrations in numeric order. Three pairs may be folded by the builder if they prefer fewer, larger PRs (02 into 01; 12 into 10; 17 into the last module PR to merge); nothing else should be.

## Rules every PR follows

- **Main stays green and the demo path works after every merge.** A PR that changes a demo-visible behaviour (expiry, approval limits, provisional exports, the receipts list) checks the demo loader and `docs/demo/*` in the same PR and says so in its body.
- **Migrations are new files only.** The numbers below are pre-allocated per module and **binding**: within one module the PR with the lower number merges first (Flyway on the demo server refuses a lower number after a higher one). Kernel numbers continue above `V0083`; the lane table in `kernel/README.md` is history.
- **Shared seed files take entries in a commented block at the end**, headed `-- wave 2, PR <n>` (or `# wave 2, PR <n>`), so parallel PRs append and never edit the same lines: `seed/m1party/permissions.yaml`, `seed/kernel/config-items.yaml`, `seed/m1security/demo-users.demo.sql`, `seed/m9integration/posting-map.yaml`. i18n files are per module and do not conflict.
- **Tests, always**: for any new or changed table, `RlsMatrixIntegrationTest` rows and `OwnPoliciesTestTheClassIntegrationTest`; a failing-case test per guard; every handler test asserts `kernel.committedAudit()` and `kernel.committedEvents()`; a Flyway test start on a database at the previous migration (the demo server's situation). The verifiers' reproduction tests (M4, M7, RLS; kept outside the repository until Docker is up) run red before and green after their PR.
- **`make format`, `make test`, `node tools/check-*.mjs`** before push; `make reset` is never needed by these PRs (new migrations only), and each PR body says so.
- **Each PR body** names its decision files and change requests, lists the findings it closes, and moves their tracker rows (`docs/reviews/TRACKER.md`) to fixed.
