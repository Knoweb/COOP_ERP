- **M7M8M9-02 backend/app/src/main/java/lk/coopfed/knoweb/m7customers/internal/customer/NicCapture.java:97** (procedure in `m7customers/README.md:50-54`) [medium] [correctness] The duplicate check computes its candidates under the current key only. After the documented "ordinary" rotation, every row under the old key is invisible to `nic_holders`. After the documented "emergency" rotation (`HMAC(new, stored)`), the stored values are ones no lookup ever computes. Either way, duplicate detection fails with no signal (PR #278).
  Scenario (ordinary): the pepper is replaced. Member A, captured under the old key, holds an account at MPCS 1. A second registration of A at MPCS 2 (another phone) opens an account with A's NIC. `hasher.candidates` gives `HMAC(new, sha(form))` and the plain SHA-256 values, none equal to `HMAC(old, sha)`, so there is no `nic_held_elsewhere` and one person holds two credit lines. That lasts until A happens to present the card again at MPCS 1, which a member with one account never does. Scenario (emergency): the README's chain stores `HMAC(new, HMAC(old, sha))`, while `NicHasher.keyed` computes `HMAC(new, sha)`. So every chained row answers `m7.account.nic_mismatch` to its own society and is never found as a duplicate, and nothing reports either. `NicRekeyJob` handles `nic_key_id IS NULL` only, so no code exists for either rotation. Fix (design decision): keep every retired key configured for lookup (`nic-pepper-previous`, a list) and put each key's keyed forms into `candidates` and `requireSameCard`. Or, if chaining is kept, compute the chain in `candidates` (`HMAC(new, HMAC(old, sha))`), which also needs the old key. Remove the chaining sentence until one of these exists, and add a test: capture, rotate, try to capture the same NIC for another customer, expect `nic_held`.
  Verified by: wave-3 verifier (Claude Opus 5.5), read-only, main ec4c5758. Status: CONFIRMED, medium. `NicHasher.candidates` builds only `hash.hex(sha(form))` under the one configured key plus the plain SHA-256 values; `customers.nic_holders` matches `nic_hash = ANY(p_hashes)` with no key-id awareness, so a row under a retired key never matches. `requireSameCard` (NicCapture:~86-89) requires `current.keyId() == hasher.keyId()` and the hash to be `keyed` or in `keyedForms`, so the README's emergency chain (`HMAC(new, stored)` with the key id bumped) makes every chained row fail `m7.account.nic_mismatch`. The README (m7customers/README.md, "Rotation") admits the mismatch for the ordinary path but not the loss of duplicate detection. `NicRekeyJob`/`legacy_nic_rows`/`rekey_nic` act only on `nic_key_id IS NULL`, so no code supports either rotation. Not higher than medium: no rotation has been done and nothing triggers one; the harm starts only when someone follows the README.
  Suggested fix scope: M, no migration (key id column exists), design decision (keep retired keys for lookup, or drop the chaining procedure).

- **Contact door and SMTP (#283)**: the `notification_recipients` body; `isLocalRelay`; `SendFailed` carries a category and no relay text; the password comes from the environment only.
- **M8 money tiles under repeated and redelivered events (#284)**: `trade_document_event` is `ON CONFLICT (event_id)`.
