## m7customers/internal/customer (2)
- **M7CR-01 backend/app/src/main/java/lk/coopfed/knoweb/m7customers/internal/customer/NicNumbers.java:37** [high] [privacy] **CONFIRMED (reproduced)** The NIC "hash" is plain SHA-256 of `"nic:" + NIC`, with no secret salt or pepper, and the last four characters are stored beside it, so anyone who can read `customers.customer` can recover the full NIC in under a second. (PR #221)
  Scenario: a new NIC is `YYYY DDD SSSS C`. `nic_last4` gives away the last three serial digits and the check digit. What is left is the year (about 100 values) × the day of the year (732, with the +500 for women) × one serial digit (10), about 7.3e5 candidates. An old NIC `YYDDDSSSCV` gives the same count. Running SHA-256 over 7.3e5 strings takes milliseconds. This works for a database dump, a backup, a FEDERATION_VIEW reader (see M7CR-10) or the ACCESS export. Doc 27 (sections 3.1 and 9.3: "NIC stored only as a salted hash plus last four digits") asks for a salted hash. A constant prefix is not a salt. Fix: use HMAC-SHA-256 with a server-side pepper held in the secret store, not in the database, and keep comparing by equality on the HMAC. Re-hash the existing rows in a migration step that runs with the pepper. Consider keeping fewer than four characters, or keeping only the check digit.
  Verification: doc 27 asks for a salted hash in three places (section 3.1 line 113, section 9.3 line 502, DR table line 553). 27A only says "hash" (`NicHash`, `nic_hash char(64)`). A single-threaded Node script enumerated 783,240 candidates from a made-up 12-digit NIC and its last four, and found the number in 1.2 s. Exposure is narrower than the scenario implies. No API returns `nic_hash`: `CustomerCard` carries `nicLast4` only, and the snapshot carries neither. The only ways to read it are SQL access (a dump, a backup, or any `app_rw` session, including FEDERATION_VIEW) and the ACCESS export (`select *`, see M7CR-11). Severity stays high because doc 27 explicitly requires a salted hash and the NIC is a national identifier.
  Suggested fix scope: a keyed hash is feasible. A per-row random salt is not: `m7.account.nic_held` and `nic_mismatch` find the same NIC by equality across rows, and that needs one deterministic key. HMAC with a pepper keeps the equality lookup. The existing rows can be re-keyed without knowing any NIC, by storing `HMAC(pepper, existing_sha256)` and computing the lookup the same way. That needs a migration: a Java/application-side step, because the pepper must not be in SQL. It also needs a small design decision: where the pepper lives (a kernel secret, which the platform pair owns) and how it rotates. Whether to keep four characters is a doc 27 decision (Federation legal, DR row "NIC capture").

## m7customers/internal/consumers and internal/payment (3)
- **M7CR-06 backend/app/src/main/java/lk/coopfed/knoweb/m7customers/internal/consumers/PostAccountTenderHandler.java:77** [medium] [data integrity] **CONFIRMED** A till tender with a missing account id, a missing amount or a zero amount throws `m7.tender.malformed`. The consumer loop (ReceiptTenderConsumer.java:55-72) runs every ACCOUNT tender of the receipt in one transaction, so one bad tender rolls back all of them, and the event is dead-lettered after 3 attempts (EventConsumerDispatcher.java:87-109). This breaks "never reject a till fact". It also contradicts the handler's own Javadoc, which says a tender naming no account at all is flagged ACCOUNT_TENDER_UNKNOWN. (PRs #221, #238)
  Scenario: a till build sends one ACCOUNT tender with `customer_account_id` null, or an unparseable `business_date`, which makes `LocalDate.parse` throw in the consumer. The whole receipt's credit charges never reach the ledger. All central records is EVENT_CONSUMER_DEAD_LETTERED, and nobody gets a REVIEW naming the receipt. Separately, an amount like `100.005` is not refused or flagged: the `numeric(14,2)` column silently rounds it to 100.01. Fix: treat a missing or unparseable account, amount or date as a flagged fact (an ACCOUNT_TENDER_UNKNOWN or MALFORMED REVIEW naming the receipt, and no posting), parse each field defensively inside the loop, and flag an amount with more than two decimals.
  Verification: the dispatcher runs `inbox.applyOnce(...)` and the whole consumer inside one `transaction.execute`, retries on any RuntimeException, and dead-letters on the third attempt. `UUID.fromString`, `new BigDecimal` and `LocalDate.parse` in the consumer also throw on bad text. The handler checks `signum() <= 0` but not the scale. Reproduction test: `m7cr06_aTenderWithNoAccountIsRefusedNotFlagged_andThirdDecimalIsRounded`.
  Suggested fix scope: no migration and no design decision. AGENTS.md already says "apply and flag". A new audit code for MALFORMED needs its i18n ids.
- **M7CR-07 backend/app/src/main/java/lk/coopfed/knoweb/m7customers/internal/consumers/PostAccountTenderHandler.java:87** [low] [data integrity] **PLAUSIBLE** The redelivery check runs before the account lock. `account_posting` is partitioned, so it has no unique key on (document_id, account_id, kind, tender_seq), and two concurrent deliveries of the same receipt both post the charge. (PR #221)
  Scenario: the consumer framework's inbox fails over, or a receipt arrives both as `receipt.issued.v1` and through a replay, and two workers deliver it at once. Both see no posting, both lock the account in turn, and both insert, so the balance is doubled. A related gap: if `seq` is absent, `asInt()` returns 0 for every tender, so a second ACCOUNT tender on the same receipt and account is dropped as a duplicate. Fix: take the account lock first, then run the existing-posting check. For a stronger guarantee, add a non-partitioned dedupe table with a unique key on (document_id, account_id, kind, tender_seq). Treat a missing `seq` as malformed and flag it (M7CR-06).
  Verification: the scenario as written is guarded. `InboxGuard.applyOnce` inserts `(consumer, event_id)` with ON CONFLICT inside the same transaction. A second concurrent delivery of the same event therefore blocks on that unique key and then applies nothing, and `Replayer` re-sends the outbox row with its original event id. The gateway also refuses a re-used event id (`EventApplier`, DUPLICATE_ID). The race needs two different events that carry the same receipt document, which only a faulty till could produce, plus concurrent workers. The check-before-lock ordering is real, and the `seq` absent → 0 collapse is confirmed by reading (`tender.path("seq").asInt()`). Neither could be shown end to end.
  Suggested fix scope: moving the check after `ledger.lock` needs no migration. A dedupe table would be a migration. Flagging a missing `seq` goes with M7CR-06. No design decision needed.
- **M7CR-08 backend/app/src/main/java/lk/coopfed/knoweb/m7customers/internal/ledger/Ledger.java:103** [medium] [correctness] **CONFIRMED** What is "open" of a charge is the charge less its allocations. CREDIT postings (refunds and voids), negative ADJUSTMENTs and unallocated payment credit never settle a charge. The ageing, the oldest open charge (AccountQueriesImpl.java:84-100) and the next payment's allocation then disagree with the balance. Doc 27 section 3.3 says ageing is computed from unpaid charges. (PRs #221, #230)
  Scenario: day 1, CHARGE 1,000.00. Day 2, the receipt is voided, giving CREDIT -1,000.00, and the balance is 0. The card still shows 1,000.00 "open" since day 1, which moves into the 90+ bucket three months later on an account that owes nothing. The next office payment of 500.00 (which leaves a credit) is allocated to the voided charge. Second scenario: payment A 1,000.00 is allocated to charge X; payment B 300.00 sits unallocated; A is reversed. X now shows 1,000.00 open while the balance is 700.00. Fix: allocate a CREDIT or a negative ADJUSTMENT against the charge it refers to, or against the oldest open charge, through the same Allocator and allocation rows, as a payment does. After a reversal, re-run oldest-first for the account's unallocated credit. Add the property "sum of open charges − unallocated = balance" to the ledger property test.
  Verification: the first scenario holds. `openCharges` subtracts only `allocation` rows, and only payments write allocations. Reproduction test: `m7cr08_aVoidedChargeStaysOpenWhileTheBalanceIsZero`. The second scenario is weaker than stated. Open 1,000 less unallocated 300 equals the balance of 700, so the proposed invariant holds there. The only defect in that case is that B's 300 is not re-applied to X. 27A section 6.3 says nothing about how a CREDIT or a negative ADJUSTMENT settles a charge.
  Suggested fix scope: no table migration, because a credit can be recorded in `allocation` rows. Whether `allocation.payment_posting_id` may cite a CREDIT or ADJUSTMENT posting should be checked against its foreign key. A design decision is needed on how credits settle charges: against the referenced charge or oldest first. This is a gap in 27A section 6.3 and needs a CR.

## db/migration/m7customers (1)
- **M7CR-13 backend/app/src/main/resources/db/migration/m7customers/V0001__customers.sql:188** [medium] [correctness] **CONFIRMED** ADR-15 (doc 27 section 3.3: "A customer of two societies has two independent accounts", "the identity is federation-wide") cannot happen. Society B cannot see society A's customer until B holds an account for it (the `account_holder_read` policy), and OpenAccount needs to see it first: CustomerGuards.java:117 reads `... for update`, which also needs the UPDATE policy that only the owner has. Registering the person again at B is refused by reuse detection (`m7.customer.phone_held_elsewhere`). The `account_holder_read` policies are therefore dead. (PR #221)
  Scenario: a member of MPCS A asks MPCS B for credit. B's officer cannot find them by phone (RLS), OpenAccount with A's customer id answers `m7.customer.not_found`, and RegisterCustomer with the same phone answers `phone_held_elsewhere`. The only way through is registering with a different phone, which creates a second identity for the same person and defeats both reuse detection and the NIC guard. Fix: either add a lookup that lets B find a customer by phone with a minimal answer (id plus a masked name, audited) and open an account against it, with OpenAccount reading the customer without `FOR UPDATE` and through a SECURITY DEFINER check, or record in the README and in a change request that one person belongs to one society, and drop `account_holder_read`.
  Verification: the design intent is explicit. Doc 09 has ADR-15 "Customer identity: global ID, entity-scoped account" (Accepted). Doc 27 section 3.1 says "the identity is federation-wide" and section 3.3 says "A customer of two societies has two independent accounts (ADR-15)". Section 9.5 says "another MPCS opening an account for the same person sees the identity (name, phone) but not the other society's balance". 27A assumes "Name and phone visible to any MPCS holding an account for the customer". (`docs/adr` holds only ADR-051/052, so ADR-15 lives in doc 09.) The code cannot reach that state. There is a further block beyond the cited one: OpenAccount also counts B's own `CREDIT_ACCOUNT` consent, and `customer_consent` has no `account_holder_read`. The module's own test (`CustomerHandlersIntegrationTest.anotherSocietySeesTheIdentityOnlyWhenItHoldsAnAccountAndNeverTheBalance`) inserts B's account as the superuser and says "the cross-society registration path comes with the till". The gap is acknowledged in a test comment but is not in the README's Deviations or in `docs/progress/deviations`. Reproduction test: `m7cr13_aSecondSocietyCannotOpenAnAccountForTheSamePerson`.
  Suggested fix scope: a design decision is needed first, on how B discovers A's customer (a minimal, audited lookup, a PDPA point the 27A assumptions table leaves to Federation legal). After that, a migration: a SECURITY DEFINER lookup or open-account function, and a consent policy. Until then, record it as a deviation.

Doc 27 section 5.2 lists `LookupCustomer` with scope "OWN (MPCS and its shops); Federation view", and section 9.5 says "Federation view-only". Other modules keep `fed_view` on personal data too: m9integration V0003 keeps it on `notification_contact` (e-mail and phone), and `RlsMatrixIntegrationTest.EXCEPTIONS` lists no table where FEDERATION_VIEW is withheld for privacy. The real harm in the finding, NIC recovery, is M7CR-01. If the federation should not see member identities, that is a PDPA change request against doc 18 and doc 27, not a code defect.

## Covered, no findings
- Ledger insert-only: the `account_posting`, `allocation` and `allocation_reversal` grants are SELECT and INSERT only, and the partitions are secured by `secure_posting_partition`. The `balance` cache is set only to `Ledger.sum` after the account row lock in every posting handler (PostAccountTender, RecordCustomerPayment, RecordTillPayment, ReverseCustomerPayment, ApproveAdjustment), and no path writes any other value.
- Reversal: the REVERSAL posting of +amount and one `allocation_reversal` per live allocation exactly undo the payment. A double reversal is blocked by the count under the account lock plus the `one_reversal_per_payment` unique index, and `allocation_reversal`'s primary key blocks undoing an allocation twice. Reversing a reversal is refused. No rounding: amounts are kept at scale 2 throughout.
- Allocator (oldest first, specific with the exceeds-open and exceeds-amount guards) and its tests.
- Limit breach as a flag only for till facts (`limit_breached`, ACCOUNT_LIMIT_BREACH, HARD_BLOCK_BYPASSED_OFFLINE, OFFLINE_CAP_EXCEEDED). Two concurrent sales are serialised by `FOR UPDATE` on the account.
- The MFA step-up on a limit increase. SoD on adjustments (same-person guard, lock on the adjustment row).
- RecordTillPayment idempotency (count check plus the primary key on `doc_customer_payment`), the flags (CLOSED_ACCOUNT, UNKNOWN_ACCOUNT, METHOD_UNKNOWN, LOCATION_MISMATCH), and `observeDeviceNumber`.
- Phone normalisation and ReuseDetector: `phone_holders` returns ids only, CONFLICT / NEEDS_CONFIRMATION, and the audit records holder ids only.
- Events: every M7 event record carries ids and amounts only, never a name, phone or NIC. Audit maps in the handlers carry no name, phone or NIC, apart from the free-text reasons noted in M7CR-10. There are no log statements in the module.
- Snapshot contents: no NIC hash, last four, attributes or consents, and anonymised customers are excluded.
- RLS: ENABLE + FORCE plus the template on all 11 tables. The column-level UPDATE grants are limited to the mutable columns.
- Statement query, period limit, payment view. The web module (no NIC is persisted client-side or logged, NIC input has autocomplete off, only `****last4` is shown).
