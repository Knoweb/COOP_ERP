## kernel/internal/sync (2)
- **K4-01 backend/app/src/main/java/lk/coopfed/knoweb/kernel/internal/sync/BatchIngestor.java:204-214 with IngestTransactions.java:324-345** [medium] [correctness] The version-floor ALERT is written on every upload attempt of a till past its grace, before the claim and with no de-duplication, so it is raised per batch (including 409 in-flight retries, sequence-gap refusals and replays), while a till past its grace that only heartbeats never raises it (PR #335)
  Scenario: the floor rises to 1.4 and a shop's till stays on 1.3.1 past the 14 days. The till uploads after every sale (`syncSoon`) and every 20 s while facts are pending (TillController.kt:56, 302-313), one batch of at most 50 facts each; a shop with 300 sales a day writes about 300 `SYNC_APP_VERSION_BELOW_FLOOR` ALERT rows a day, every day, and 500 such tills write some 150,000 ALERTs a day into the insert-only audit ledger and any ALERT queue built on it. A 409 `sync.batch_in_flight` or `sync.sequence_gap` adds another ALERT per retry for a batch that was not taken. Conversely a till with nothing to upload (closed shop, no sales) keeps heartbeating below the floor and never appears, although doc 31 section 6 says the device "appears in the helpdesk queue automatically". The tests prove one ALERT after one upload and none within the grace; none uploads twice. Fix: raise it once per device and floor (e.g. record the floor last alerted on `kernel.device_sync_cursor`, or check for an existing ALERT for the device and floor, inside the same transaction as the claim), evaluate it on the heartbeat as well as on the batch, publish `sync.anomaly.v1` with it as the other sync ALERTs do, and add a test that two uploads and a heartbeat give one ALERT.
  Verification: CONFIRMED (medium). `checkFloor` runs before `transactions.claim` (BatchIngestor.java:79-80) and calls `recordFloorAlert` whenever `afterGrace()`; `recordFloorAlert` has no lookup; HeartbeatService.record never evaluates the floor; TillService.syncOnce uploads only when facts are pending (line 631). Verified by: Claude Opus 5.5 (wave 4, 12 Oct 2026; read, not run). Suggested fix scope: S-M, no migration if the de-duplication reads the audit ledger, a small kernel migration if a column is added; no design decision (doc 31 already says one helpdesk entry).
- **K4-02 backend/app/src/main/resources/i18n/kernel/en.json:74 (si.json, ta.json the same) and IngestTransactions.java:329-337** [low] [maintainability] The message id `sync.app_version_below_floor` added in three languages is used by nothing (no ProblemException, no audit reason, no screen reads it), and the ALERT's after-state carries the same instant twice, as `graceEndedAt` and `graceEndsAt` (PR #335)
  Scenario: a translator or a later change keeps the unused id in step with `sync.app_below_floor` (the one the 426 actually uses), and a report reading the after-state has two keys for one fact. Fix: drop the unused id (or use it as the audit reason through the message catalogue) and keep one of the two keys.
  Verification: CONFIRMED (low). `grep -rn app_version_below_floor` finds only the three i18n files. Verified by: Claude Opus 5.5 (wave 4, 12 Oct 2026; read, not run). Suggested fix scope: S, no migration, no design decision.

## kernel config_value RLS and the matrix (1)
- **K4-03 backend/app/src/test/java/lk/coopfed/knoweb/kernel/internal/RlsMatrixIntegrationTest.java:411-431 (policy: kernel V0052:74-76; app guard: JdbcConfigRegistry.java:155-167)** [low] [security] FIX-11 narrowed only the read; the matrix departure it added declares `INSERT_WITHOUT_LOCATION` and `INSERT_AT_ANOTHER_LOCATION` DONE for every OWN scope, so it asserts as correct that `config_value.own_write` has no location line (the V0064 template's "own writes stay at the location") and admits `scope_entity_id IS NULL` from any entity's OWN session, and the app guard in `set()` checks the entity but never the location (PR #315; policy from V0052)
  Scenario: a shop-scoped administrator of MPCS A (scope location L1) sets a location value for sibling shop L2, or an entity-wide value, through any future caller of `ConfigRegistry.set`: neither `set()` nor RLS refuses it. At the database level any entity's OWN session can insert a federation-wide row (`scope_entity_id` NULL), which every till and job of every entity then resolves; only the Java check `config.federation_only` stands in the way. The matrix never exercises the NULL-entity insert and now passes with the location gap written in as expected. Latent: no production code calls `set()` today. Fix: add the template's location line to `own_write` (new migration), restrict NULL-entity inserts to the system entity (a class-tested definer `kernel.is_system_entity()` or a role check), make `set()` refuse a location other than `ctx.locationId()` for a location-scoped caller, and replace the DONE expectations by the template's REFUSED.
  Verification: CONFIRMED (low). V0052 own_write is `scope_class() = 'OWN' AND (scope_entity_id IS NULL OR scope_entity_id = scope_entity())`; no later migration replaces it (V0086 and V0090 do not touch it); `set()` has no location check; no caller of `set()` in `src/main`. Verified by: Claude Opus 5.5 (wave 4, 12 Oct 2026; read, not run). Suggested fix scope: S, one kernel migration plus test changes, no design decision.
