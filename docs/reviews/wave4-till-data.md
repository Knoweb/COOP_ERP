## m2catalogue/internal/snapshot (4)
- CONFIRMED **TD-01 backend/app/src/main/java/lk/coopfed/knoweb/m2catalogue/internal/snapshot/CatalogueShops.java:36-37,77,115** [high] [data integrity] Every M2 change is appended only to ACTIVE shops (`LocationFilter(STATUS_ACTIVE, "SHOP", ...)`), but a shop's tills are enrolled and syncing before it is ACTIVE, and a DORMANT shop's tills keep their version. The delta is per location (`SnapshotBuilder` :177-178, `where location_id = ? and version > ?`), so a change that was never appended at a shop is never delivered there. (PR #336)
  Scenario: a new shop is ONBOARDING. ActivateLocation requires a primary till (`ActivateLocationHandler` :52-53; RegisterTillPosition accepts PLANNED/ONBOARDING shops per CR-21A-5), so the till enrols and takes its full snapshot first. During the week before activation the Federation shares 20 SKUs, registers new barcodes, and deactivates 2 SKUs. None is appended at this shop. After activation the till's version equals central's, `olderThanRetention` finds no rows to be old, and no full snapshot is ever forced: the till cannot scan the 20 new items and keeps selling the 2 deactivated ones until a continuity failure or a re-enrolment. The same holds for a DORMANT shop that reopens. M1's producers (all SHOP locations) and M7's `SocietyShops` (status filter null) do not have this gap. Fix: drop the status filter (pass null as SocietyShops does), or at least include PLANNED, ONBOARDING and DORMANT; add a test with an ONBOARDING shop.
  Verification: re-read `CatalogueShops.listEntityShops`/`listAllShops` (filter `STATUS_ACTIVE`), `EnrolDeviceHandler` (no location status guard), `RegisterTillPositionHandler` :29-31, `ActivateLocationHandler` :52-53, `SnapshotBuilder.build` :106-117 and `olderThanRetention` :246-259 (it looks only at change-log rows after `since`; none exist). Nothing on activation triggers a full snapshot (M1 appends only a `location` upsert on LocationActivated).
  Verified by: Claude Opus 5.5, 12 Oct 2026, by reading. Suggested fix scope: S, no migration, no design decision.
- CONFIRMED **TD-02 backend/app/src/main/java/lk/coopfed/knoweb/m2catalogue/internal/snapshot/CatalogueSnapshotContributor.java:248-272; M2ChangeLogFanOut.java:189-215** [high] [performance] The new `batch` snapshot table serves every batch the till's scope can read, and `catalogue.batch` has `shared_read USING (kernel.scope_class() <> 'NONE')` (m2catalogue V0001 :381-382). A full snapshot therefore carries every batch ever registered in the federation for every SHARED SKU, SUPERSEDED ones included, with no expiry or holder filter. V0001 :333-334 sizes the table at "millions per year". In addition, every BatchRegistered on a SHARED SKU is appended at every active shop of the federation. (PR #336)
  Scenario: after a year of GRNs across the societies, a till enrols (or its retention lapses). `SnapshotBuilder.fullTables` (:193-205) calls `allRows("batch", shop)` and builds millions of rows in memory, hashes and signs them, and sends them in one answer: the API node runs out of heap or the till's download fails on a shop's mobile link. Separately, a society's GRN with 30 batch lines of shared SKUs appends 30 change-log rows at each of N shops and bumps every till's version, which then downloads deltas of batches it does not hold (and does not use, TD-04). Fix: serve only batches relevant to the shop (those of lots its entity holds, from M5's lot query, or only REGISTERED batches with an expiry not passed and at most the latest K per SKU), target BatchRegistered/BatchCorrected at the holder entity's shops, not the federation; until there is a till consumer, remove `batch` from `tables()`.
  Verification: `batches(shop, ids)` ignores `shop` (no location or entity predicate; only the SKU status join), so `allRows` returns every readable batch. The batch RLS policies admit every non-NONE scope. `fullTables` materialises all rows of every contributor.
  Verified by: Claude Opus 5.5, 12 Oct 2026, by reading. Suggested fix scope: M, no migration, design decision (which batches a till needs; doc 32 section 5.1 lists the snapshot contents).
- PLAUSIBLE **TD-03 backend/app/src/main/java/lk/coopfed/knoweb/m2catalogue/internal/snapshot/CatalogueShops.java:88-107,126-150** [medium] [security] A module class builds its own FEDERATION_VIEW `ScopeContext` (entity 0) and then hand-writes the session settings back (`restoreScope`). The kernel guards federation-wide reads: `JobExecution.federationView` may be called only from a `@ScheduledJob` (ArchUnit, CR-19A-7) and consumers have `ScopedExecution.federationView()`. Constructing the context directly sidesteps both, and no rule stops other modules from copying it. The `@Transactional(propagation = REQUIRES_NEW, readOnly = true)` on `listEntityShops`/`listAllShops` never applies (self-invocation from `of`/`all`), so the forged scope is set inside the consumer's own transaction, and only the finally block puts it back. (PR #336)
  Scenario: a later edit throws between `parties.listLocations` and the finally, or adds a write after `all(...)` that relies on the aspect's settings: `restoreScope` writes `scope.policyClass().name()` verbatim (for a DEVICE or API_CLIENT context it would write `DEVICE`, which `ScopeConnectionCustomizer.sessionClass` maps to OWN), so the session can be left in a class no policy expects. Today the dispatcher's consumer scope is OWN and the restore works. Fix: use `ScopedExecution.inScope(scopes.federationView(), ...)` / `scopes.own(entity)` and delete `restoreScope`; add an ArchUnit rule that only kernel and demo code call `new ScopeContext(...)` with FEDERATION_VIEW.
  Verification: PLAUSIBLE, not CONFIRMED: no wrong outcome reachable today (consumer scope is OWN, restore is in a finally), so this is a guard-rail bypass rather than a live leak. Only listing locations is exposed.
  Verified by: Claude Opus 5.5, 12 Oct 2026, by reading. Suggested fix scope: S, no migration, no design decision.
- CONFIRMED **TD-04 till/core/src/commonMain/kotlin/lk/coopfed/knoweb/till/core/snapshot/Catalogue.kt:97,115; CatalogueSnapshotContributor.java:259-269** [low] [correctness] The till reads only `sku` and `operator` from the snapshot; nothing reads `batch`. The PR's title says batches are synced to tills and its README item 30 says corrections reach them, but no MRP cap or expiry check on the till uses them, and the rows include SUPERSEDED batches (status served but no filter) and duplicate the expiry under two keys (`expiry_date`, `expiry`). Fix: either add the till consumer (with SUPERSEDED rows excluded or mapped through `corrects_batch_id`) in the same change as TD-02's narrowing, or remove `batch` until it exists and correct README item 30.
  Verification: grep of `till/core/src/commonMain` for `"batch"` and `mrp` finds no snapshot reader; `Catalogue.kt` builds items from `table("sku")` and operators from `table("operator")` only.
