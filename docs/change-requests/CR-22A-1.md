# CR-22A-1 — The tag code is a global key, so a local tag of one entity collides with another's

- **Status:** accepted as revised (27 September 2026, on the architect's delegation); applied in the repository (m2catalogue V0007); 22A, doc 22 and doc 18 not re-issued yet
- **Decided 27 Sep 2026:** accepted as revised in PR #PRNUM, on the architect's delegation (see "Decision" at the end).
- **Date raised:** 2026-09-26
- **Raised by:** Claude Code session, from the review of pull request #114 (M2-01, the catalogue schema) and its fix branch `fix/m2-01-schema-review`
- **Documents affected:** 22A §3 (`catalogue.tag`), 22A §6 (DefineTag), doc 22 §3.5, doc 18 Part F (the schema register)
- **Code affected:** `db/migration/m2catalogue/V0007__tag_key_and_supplier_read.sql` (V0001 stays as merged); `M2SeedLoader` (the governed seed); `CatalogueSnapshotContributor` (tag codes through a join); M2-03's DefineTag and TagSku handlers, not written yet

## What is wrong or missing

22A §3 writes the tag table with the code as its whole key:

> `CREATE TABLE catalogue.tag (tag_code varchar(40) PRIMARY KEY, name_en text NOT NULL, name_si text, name_ta text, governed boolean NOT NULL DEFAULT false, owner_entity_id uuid, CHECK (governed = (owner_entity_id IS NULL)));`

and doc 22 §3.5 says what the two kinds of tag are:

> "Governed tags are Federation-owned and used for federation-wide comparison and for policy attachment ... Local tags belong to an entity for its own merchandising."

A local tag belongs to one entity, and its row is visible to that entity alone (`own_read`; a governed tag is visible to everyone through `governed_read`). But the key is the code alone, federation-wide: two entities cannot both have a local tag `seasonal`, and no entity can have a local tag whose code the Federation later takes for a governed one.

## Why it matters

- **A hidden row is revealed by a duplicate key.** MPCS A defines the local tag `promo`; MPCS B, which cannot see A's tag, defines `promo` too and is refused with a duplicate key. B learns that some other entity has that tag, which row-level security was meant to keep from it, and B cannot use the name it wants.
- **A governed tag cannot be introduced once any entity took the code.** The Federation's DefineTag for a governed `fresh` fails if any society defined a local `fresh` first, and the seed of a new governed tag (22A §3.1, `tags.yaml`) fails the same way at start-up.
- `sku_tag` keys on `(sku_id, tag_code)`, so the same collision reaches the assignments.

The code as merged keeps 22A's key, because the key is a contract of doc 18 and of every module that reads tags (`TagQueries.isGoverned`, doc 22 §3.5), not M2's to change alone.

## Proposed change

22A §3, doc 22 §3.5 and doc 18 Part F:

1. The key of `catalogue.tag` becomes the code within its owner: `UNIQUE (tag_code, coalesce(owner_entity_id, '00000000-0000-0000-0000-000000000000'::uuid))` as a unique index (a table constraint cannot hold an expression, the same as the batch key), with a surrogate `tag_id uuid PRIMARY KEY` that `sku_tag` references instead of the code. A governed tag (owner null) and an entity's local tag may then share a code without either seeing the other.
2. A reserved prefix for governed tags, `gov-` or a namespace decided by the architect, so that the Federation's vocabulary and an entity's own never read the same on a screen or in an export, and `TagQueries.isGoverned` can answer from the code alone as the consuming validators of M3 and M5 expect.
3. 22A §6, DefineTag: "governed tags F only; local tags owner" gains "a local code is unique within the entity; a governed code is unique federation-wide and carries the reserved prefix".

## Impact if accepted

22A re-issued (v0.2) for §3 and §6; doc 22 §3.5 for the prefix; doc 18 Part F for the key. Code: a new migration of the m2catalogue lane changes the key and adds `tag_id` (V0001 is never edited); the governed seed `tags.yaml` takes the prefix; `sku_tag` re-keys on `tag_id`; M2-03's DefineTag and TagSku are written to the new rule, and `CatalogueRlsIntegrationTest` gains the case "two entities define the same local code". Nothing changes before acceptance.

## Decision

Decided 27 Sep 2026: accepted as revised (PR #PRNUM), on the architect's delegation. Items 1 and 3 as proposed; item 2 (a reserved prefix for governed tags) is not adopted.

- **The key** (item 1). `catalogue.tag` has a surrogate `tag_id uuid PRIMARY KEY` and the unique index `tag_code_per_owner` on `(tag_code, coalesce(owner_entity_id, '00000000-0000-0000-0000-000000000000'::uuid))`: a governed code is unique among governed tags, a local code within its entity. `catalogue.sku_tag` names the tag by `tag_id` (key `(sku_id, tag_id)`); its `tag_code` column is gone, and the rows already there were carried over by their code, which the old key made unambiguous. Its `own_write` now also requires the tag to be governed or the caller's own local tag, because a foreign key is checked without row-level security. Two policies, `governed_write` and `governed_update`, let the Federation (`kernel.system_entity()`, kernel V0061) write governed tags in its OWN scope; before them no application path could write a tag with no owner.
- **No reserved prefix** (item 2). The governed codes stay as doc 22 section 3.5, doc 18 Part F and 22A section 3.1 name them (`core-range`, `rice` ...), which M3's control-price and MRP-policy tag scope will cite. Instead: a local DefineTag refuses a code a governed tag already has (governed tags are read by every scope, so the refusal reveals nothing); a governed code introduced later may equal an entity's older local code, and the two stay apart by `tag_id` and the `governed` flag, which a screen and an export show. `TagQueries.isGoverned(code)` answers from the governed rows, where the code is unique.
- **DefineTag** (item 3), for M2-03: "governed tags F only (`cat.tag.govern`, CR-22A-3); local tags owner (`cat.tag.manage`); a local code is unique within the entity and may not equal a governed code; a governed code is unique among governed tags".

Reasons: the surrogate key is the only shape in which neither kind of tag can block or reveal the other, and it costs one migration now against re-keying `sku_tag` and every consumer once M2-03 and M3 write rows. A prefix would rename the seeded vocabulary that three documents already cite, for a collision that the refusal at DefineTag avoids in the usual order and the governed flag tells apart in the other. Proof: `CatalogueRlsIntegrationTest` (two entities with the same local code, a governed code beside a local one, uniqueness within an owner and among governed tags, governed tags written by the Federation only, another entity's local tag refused on an item), `CatalogueSchemaIntegrationTest`, `M2SeedLoaderTest`, `CatalogueSnapshotContributorIntegrationTest`, `RlsMatrixIntegrationTest`.
