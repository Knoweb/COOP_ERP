# CR-19A-2 — The idempotency table has no ticket, and its expiry cannot be a DELETE

- **Status:** raised
- **Date raised:** 2026-09-21
- **Raised by:** Claude Code session, while preparing the 19A phase (branch `chore/19a-kernel-prep`, pull request #61)
- **Documents affected:** 19A §3 (line 188, the interceptor order), §12 (line 657, the job `idempotency-expiry`), §14 (the ticket table); doc 18 Part E, table `idempotency_key` (line 1080)
- **Code affected:** `kernel.api.IdempotencyStore`, `kernel.internal.stub.IdempotencyFilter` and the in-memory store behind it

## What is wrong or missing

1. **Nobody builds the table.** Doc 18 defines `kernel.idempotency_key` ("Result store for mutating web and API commands"). 19A's interceptor depends on it (§3: "idempotency check -> handler -> record result. Order fixed; tested."), and §12 seeds a job `idempotency-expiry`. No section of 19A gives its DDL and no ticket in §14 lists it.
2. **The expiry contradicts the grants.** Doc 18: "rows expire after 24 hours". The application role `app_rw` holds no `DELETE` on anything; AGENTS.md forbids adding one, and `SchemaRulesIntegrationTest` fails the build for a `DELETE` grant to `app_rw`. 19A does not say which role the expiry job runs as, or how it removes rows.

## Why it matters

Today the store is in memory, per instance. With two instances, a retry that lands on the other one is not recognised. For a command that records money, that is the one failure idempotency exists to prevent. `make smoke TWO=1` skips that check for this reason, and `hello/README.md` lists it as a known limit. It is the known correctness hole of Sprint 0, and the table that closes it belongs to no ticket.

## Proposed change

- **19A §14:** ticket **K-03a**, split from K-03 (decided by the architect on 21 September): "`kernel.idempotency_key` table and DDL, `JdbcIdempotencyStore`, the command interceptor order, a two-instance replay test". K-03b keeps the permission resolver, the SoD helpers and the snapshot signer.
- **19A §3:** add the DDL: primary key `(user_id, idempotency_key, created_on)`, then `request_hash`, `response_status`, `response_body`, `created_at`; **partitioned by day on `created_on`**.
- **19A §12 and doc 18:** the expiry is **dropping the partitions older than the window**, done by the partition maintenance job with the migrator's rights, as for the ledgers. No role receives `DELETE`, the build rule keeps no exception, and removing a day is one catalogue operation instead of a slow delete.
- The window (24 hours) is a configuration item, not a constant (AGENTS.md).

Alternative considered: a dedicated role with `DELETE` on this one table. It works, and it is the first exception to a rule the build enforces everywhere; an exception to that rule should not start with a convenience.

## Impact if accepted

19A v0.2; doc 18 amended in one sentence. K-03a becomes buildable at once, because it needs no M1 table. `make smoke TWO=1` gains the replay check it skips today.
