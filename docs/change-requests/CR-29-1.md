# CR-29-1 — The journal export: a provisional export is a first instalment, never superseded; the file is stored; the buyer's side

- **Status:** accepted (6 October 2026, on the architect's delegation; wave 2 code review); the documents are not re-issued yet
- **Date raised:** 2026-10-06
- **Raised by:** Claude Code session, wave 2 code review decisions (`wave2-fixreview-m9-integration.md` D1, D2, D3, D5), recorded in `docs/progress/deviations/2026-10-06-wave2-journal-export.md` and `2026-10-06-wave2-buyer-postings.md`
- **Documents affected:** doc 29 §4.2 (the export guard: "period closed (all locations' day-close past period end) or explicit 'provisional' flag"), §6.2 ("marked PROVISIONAL in the file"; the status SUPERSEDED, "a later export for an overlapping period supersedes"), §6.3 (late documents are supplements), §3.3 (the export carries "GRN and INV (buyer)"); 29A §3 (DDL: `journal_export_file`), §5 (`RequestJournalExport` with `provisional?`), §6 (`JournalBuilder`, the file), §7 (the export is kept in object storage)
- **Code affected:** `m9integration/V0006` (`integration.journal_export_file`); `RequestJournalExportHandler`, `IntegrationQueriesImpl.file/reconciliation`, `JournalFile` (frozen as `JournalFileV1`), a version-2 writer; `openapi/m9integration.yaml`; `JournalPostingsConsumer`; the exports page

## What is wrong or missing

1. The build exports an open period as final (`provisional = false` always; the web default period ends today) and nothing flags a posting that arrives for a period already exported. Doc 29 §4.2 asks for the guard; §6.2 says a later export "supersedes" an earlier one, but the build's "each posting exported once" (`journal_line.posting_id` unique, deviation 3 of 29 September) and the accountant's append-only import make superseding wrong: the package would have to reverse an imported file.
2. The file is rebuilt from the lines on every download (deviation 2 of 29 September); when the writer changes (the PROVISIONAL mark is such a change) every past hash fails reconciliation and a re-download is no longer the file the package imported. 29A §7 wants object storage, which is not transactional and has no server-side put in the kernel.
3. The export has no buyer side (see CR-19A-13 and CR-24A-3 item 5).
4. M9 derives the business date from the event's `occurredAt`; right for entity-level documents today, wrong for every location-dated one (the buyer's GRN, M5 write-offs).

## Why it matters

An accountant needs: a file for a closed period complete when generated or plainly marked otherwise; each posting once; late arrivals flagged and fetchable as a supplement; a file downloadable again byte for byte with its hash. The build gives the second only.

## Proposed change

1. **Doc 29 §4.2, §6.2; 29A §5**: an export whose `periodTo` is today or later in the business time zone (later: any location of the entity whose business date has not passed `periodTo`) is refused, `m9.journal.period_open`, unless the request carries `provisional: true`. A provisional export takes its postings once, like any other, and is marked PROVISIONAL in the list, the file name and the file. **What arrives later for its period is a supplement (§6.3), never a superseding re-export**: the status SUPERSEDED and the "supersedes" link are withdrawn. Every exports list shows "supplement due": the unexported postings dated within periods already exported (count, amount, earliest and latest date).
2. **29A §3, §6, §7**: `integration.journal_export_file (export_id PK, format_version, content bytea, content_hash, owner_entity_id)`, insert-only, written in the export's own transaction; downloads serve the stored bytes; reconciliation checks the stored hash and regenerates with the writer of the recorded version; object storage is not used (it may replace the bytea later by a request of its own if volume asks).
3. **Doc 29 §3.3; 29A §6**: the buyer's GRN postings arrive from `ConfirmGrn` in the buyer's scope; the buyer's INV and CN postings by counterparty delivery (CR-19A-13), recorded by `m9.journal.buyer`; `m9.journal` records SELLER lines only; the handler dedupes by `(owner_entity_id, document_id)`.
4. **29A §6**: every posting carries its document's business date as issued (`JournalPostingsReady.businessDate`, from `document.business_date`); `occurredAt` is the fallback for events published before the field existed; a receipt's date is its issue date, `receivedOn` a reference.

## Impact if accepted

- **Documents**: 29 re-issued (§3.3, §4.2, §6.2); 29A (§3, §5, §6, §7).
- **Code**: the migration; the handler builds and hashes the bytes once; the optional `provisional` on the command and the slice; the two consumers; the web's default period ends yesterday with a required provisional box when the end date is today or later; the demo script that exports "to today" passes the flag.
- **Tests**: refused without the flag; provisional recorded and marked; the supplement-due count after a late posting; the 29A property "original + supplements = fresh full export"; reconciliation stays true after a version-2 writer exists; a pre-V0006 export downloads unchanged; one test per publisher for `businessDate` and one consumer test with it absent.
- **Rejected**: superseding (above); refusing open periods outright (breaks the same-day demo export); marking without refusing; a format version with frozen writers alone; object storage now; dating receipts by `receivedOn`.
- **Open**: whether one shop offline for two days (doc 32 allows it) should block an entity's final export once location-dated postings reach M9; the provisional flag is the escape either way.
