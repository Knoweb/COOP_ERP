# CR-18-1 — Primary keys of partitioned tables, and foreign keys out of the kernel schema

- **Status:** raised
- **Date raised:** 2026-09-21
- **Raised by:** Claude Code session, while preparing the 19A phase (branch `chore/19a-kernel-prep`, pull request #61)
- **Documents affected:** doc 18 Part D, table `audit_event` ("audit_id uuid PK"; "owner_entity_id, location_id uuid FK"; "device_id, till_position_id uuid FK"), and Part E, table `event_outbox` (line 992: "event_id uuid PK"; "owner_entity_id, location_id uuid FK"); 19A §4 and §5 (the DDL)
- **Code affected:** none yet (K-04, K-05)

## What is wrong or missing

Doc 18 and 19A describe the same two tables differently, and in both points 19A is the one that can be built.

1. **Primary keys.** Doc 18: `audit_id uuid PK` and `event_id uuid PK`, with both tables partitioned monthly on `received_at`. PostgreSQL requires the partition key in every unique constraint of a partitioned table, so a primary key on the id alone is refused. 19A has `PRIMARY KEY (received_at, audit_id)` and `PRIMARY KEY (received_at, event_id)`.
2. **Foreign keys.** Doc 18 types `owner_entity_id`, `location_id`, `device_id` and `till_position_id` as `uuid FK`. Their targets are M1's tables in the `party` schema. The kernel is layer 0 and its migrations run before any module's, so the targets do not exist when the kernel tables are created; and a kernel table that references `party` inverts the layering that `ArchitectureTests` enforces for code (R5) and `tools/check-schema-ownership.mjs` for SQL ("a foreign key into another module is refused"). 19A's DDL declares the four columns as plain `uuid`.

## Why it matters

A developer who follows doc 18, the document AGENTS.md names as authoritative for shared tables, writes DDL that PostgreSQL refuses or that the repository's own schema check refuses.

One consequence deserves a sentence in doc 18: with the composite key, **the database does not enforce that `event_id` or `audit_id` alone is unique**. That rests on UUIDv7 generation and, for events, on the consumer's `event_inbox (consumer, event_id)`.

## Proposed change

- **Doc 18, both tables:** primary key `(received_at, id)`; a note that the id is unique by construction (UUIDv7) and not by constraint, and that a lookup by id alone should bound `received_at` as well.
- **Doc 18, the four columns:** type `uuid`, meaning "the identifier of a row in M1's `party` schema; not a database foreign key, because the kernel does not depend on a module (doc 17 R5)". The writers keep the meaning: the scope a row is written under comes from the verified token.
- **Doc 18 Part F, as a general rule:** "A kernel table never declares a foreign key into a module's schema."

## Impact if accepted

Doc 18 re-issued (the register decides the version). 19A unchanged on these points. No code exists yet.
