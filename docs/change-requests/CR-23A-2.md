# CR-23A-2 — Shelf-label job request and failure events

- **Status:** accepted (21 October 2026, explicit PRC-03 design approval); the documents are not re-issued yet
- **Date raised:** 2026-10-21
- **Raised by:** Codex session implementing PRC-03
- **Documents affected:** doc 23 §5.3 event catalogue; 23A §6 PrintShelfLabels handler and §7 label job
- **Code affected:** `m3pricing.api`, `m3pricing.internal.label`, and M3 tests

## What is wrong or missing

Doc 23A specifies that `PrintShelfLabels` inserts a `QUEUED` `label_job`, audits
`LABEL_JOB_CREATED`, and names only `label_job.rendered.v1`. Rendering cannot happen in that
command: `A4Renderer` must run outside its transaction on the worker, and doc 19A identifies M3's
label renderer as a scheduled job. Publishing `label_job.rendered.v1` when the row is only queued
would announce a fact that has not happened.

The repository's command-handler rule requires every handler to call both `audit.record` and
`events.publish`. The same rule applies to the handler that persists a terminal `FAILED` outcome;
neither the requested nor rendered event truthfully describes that transition.

## Why it matters

Without a request event the queue-creation handler fails the architecture build. Reusing the
rendered event at request time would let consumers act as though a PDF existed. Updating a failed
job outside a command handler would bypass the audit/event rule and the database-write boundary.

M8's print workflow is the repository precedent: it publishes a requested event when it creates
the queued run and a distinct completion fact after the worker finishes.

## Proposed change

- `PrintShelfLabels` audits `LABEL_JOB_CREATED` and publishes `label_job.requested.v1` after it inserts the `QUEUED` row.
  Its payload is limited to job id, location id, and requested SKU count.
- Successful completion via `CompleteLabelJobHandler` audits `LABEL_JOB_RENDERED` and publishes the already specified `label_job.rendered.v1`, with job id,
  location id, and rendered label count.
- Terminal render failure via `CompleteLabelJobHandler` audits `LABEL_JOB_FAILED` and publishes `label_job.failed.v1`, with job id and location id. It is the
  additional event and audit required by the existing command-handler rule; no failure detail or sensitive
  data enters the event.
- The scheduled worker continues to discover queued rows from `pricing.label_job`; the request
  event does not create a second queue.

## Impact if accepted

- **Documents:** docs 23 and 23A add the requested and failed lifecycle events and completion audit types (`LABEL_JOB_RENDERED`, `LABEL_JOB_FAILED`) at their next re-issue.
- **Code:** three public M3 event records, two completion audit types in `audit-event-types.yaml`, and the queue/completion handlers.
- **Tests:** queue creation proves `LABEL_JOB_CREATED` and only the requested event; successful rendering proves `LABEL_JOB_RENDERED` and the
  rendered event; terminal failure proves `LABEL_JOB_FAILED` and the failed event; failed guards publish nothing and record no audit.
