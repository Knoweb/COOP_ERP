# CR-22A-3 — Two catalogue permissions beyond 22A's eleven: cat.sku.view and cat.tag.govern

- **Status:** accepted (27 September 2026, on the architect's delegation); applied in the repository; 22A not re-issued yet
- **Decided 27 Sep 2026:** accepted in PR #146, on the architect's delegation (see "Decision").
- **Date raised:** 2026-09-27
- **Raised by:** Claude Code session, M2 catalogue decisions (the deep review of M2-01, `.handover/findings-deep-m2-01-ci.md`: "cat.sku.view not in 22A section 3.1's eleven codes"; "cat.tag.manage scope ENTITY only; governed tags F has no policy")
- **Documents affected:** 22A §3.1 (the permission catalogue), §5 (x-permission of the reads and of defineTag), §6 (DefineTag / TagSku); doc 22 §5.1 (DefineTag: "cat.tag.manage (F for governed; owner for local)")
- **Code affected:** `seed/m1party/permissions.yaml`, `seed/m1party/role-templates.yaml`, `M1SeedLoaderTest`; `m2catalogue/web/ViewPermission` and the reads of `openapi/m2catalogue.yaml` (unchanged, now recorded); M2-03's DefineTag and TagSku, not written yet

## What is wrong or missing

22A section 3.1 lists eleven codes, all for commands: `cat.sku.create (F)`, `cat.sku.create_local`, `cat.sku.promote (F)`, `cat.sku.deactivate`, `cat.barcode.manage`, `cat.image.manage`, `cat.tag.manage (ENTITY; governed tags F)`, `cat.tax.publish (F, mfa)`, `cat.batch.correct (mfa)`, `cat.supplier.manage`, `cat.import.run`.

1. **No code for the reads.** Every operation of a slice carries an `x-permission` (17A; `tools/check-slices.mjs` fails a slice without one), including the reads of 22A section 5 (`listSkus`, `getSku`, the lookup, the batch and supplier lists). M2-02 added `cat.sku.view` (ENTITY) for them and gave it to the three role templates, so a Federation Viewer or a Regulator reads the catalogue without holding a command permission.
2. **One code with two scopes.** "`cat.tag.manage (ENTITY; governed tags F)`" is one row of `security.permission` with one scope. As an ENTITY code the Federation's authority over the governed vocabulary is not a permission at all: any role holding `cat.tag.manage` at the Federation entity could define governed tags, and a role cannot be given local tags without governed ones or the other way round.

## Options considered

- Reads: (a) remove `cat.sku.view` and give the reads a command code: a read-only role would then hold a command permission, and the read-only classes resolve no command anyway; (b) keep `cat.sku.view` as the read code of the whole slice, as `gov.entity.view` and `prt.location.view` are for M1: chosen.
- Governed tags: (a) keep one ENTITY code and test for the Federation in the handler (`FederationCaller`): the guard holds, but the role catalogue cannot express who governs the vocabulary; (b) a second code `cat.tag.govern` with scope FEDERATION, the pattern of `cat.sku.create` (F) beside `cat.sku.create_local`: chosen.

## Decision

Decided 27 Sep 2026: accepted (PR #146), on the architect's delegation.

- `cat.sku.view` (ENTITY) stays: the permission of every read operation of `m2catalogue.yaml` (checked by `web/ViewPermission` in the OWN class, as the kernel checks a command's). It is recorded here as the twelfth M2 code.
- `cat.tag.govern` (FEDERATION) is added: define and rename governed tags, and put governed tags on SHARED items. `cat.tag.manage` (ENTITY) is now the entity's own local tags and its tagging of its own items ("Define the entity's own tags and tag its items").
- For M2-03 (DefineTag, TagSku): one operation with `x-permission: cat.tag.manage` and `x-permission-any-of: [cat.tag.manage, cat.tag.govern]`, routed to two handlers the way `createSku` / `activateSku` route LOCAL and SHARED (`SkuCommandRouter`): a local tag under `@CommandHandler(permission = "cat.tag.manage")`, a governed tag under `@CommandHandler(permission = "cat.tag.govern")` with `FederationCaller` as its guard. The database already admits governed tags from the Federation only (m2catalogue V0007, CR-22A-1).
- The role template "Federation Catalogue Steward" gains `cat.tag.manage` and `cat.tag.govern`.

Reasons: the design text already means two authorities ("F for governed; owner for local", doc 22 §5.1), and a permission row is the place the role catalogue, the separation-of-duty rules and an auditor look for authority; a code for reads is what the slice convention requires and M1 already does. Changing codes is cheap now, before any tag handler or production role exists, and costly after.

## Impact

22A §3.1 (thirteen codes), §5 (`x-permission` of the reads; `defineTag` any-of), §6 (DefineTag / TagSku permissions) and doc 22 §5.1 at their next re-issue. `M1SeedLoaderTest` counts the codes of the whole file (38 after CR-21A-1 and this CR).
