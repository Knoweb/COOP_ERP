# CR-30-2 — The web shell keeps an interrupted command across a step-up only when its body holds no personal or secret field

- **Status:** accepted (6 October 2026, on the architect's delegation; wave 2 code review); doc 30 not re-issued yet
- **Date raised:** 2026-10-06
- **Raised by:** Claude Code session, wave 2 code review decision (`wave2-fixreview-till-web-kernel.md` TWK-16, D-6), recorded in `docs/progress/deviations/2026-10-06-wave2-web-shell.md`
- **Documents affected:** doc 30 §3 (the shell: "step-up TOTP prompt rendered by the shell when an API call returns the step-up challenge")
- **Code affected:** `web/src/shell/auth/stepUp.ts` (`pendingCommandOf`, `replayPendingCommand`), a new `web/src/shell/api/forbiddenFields.ts` with a test pinned to `OutboxWriter.FORBIDDEN_WORDS` and `SECRET_WORDS`

## What is wrong or missing

Doc 30 §3 says the shell renders the step-up prompt and continues the call; it does not say what the shell may keep while the person signs in again. The shell as built keeps the command's URL and whole JSON body in the identity library's login state (session storage by default) and replays to the stored URL with the fresh token and no origin check. `openAccount` carries a NIC; phone changes carry a phone. AGENTS.md forbids a phone, NIC, password, PIN or token in an event payload, log line or audit row; browser storage is the same class of place.

## Why it matters

Session storage survives the redirect to the identity provider and back and is readable by any script on the origin; a replay to an arbitrary stored URL would send the bearer token wherever a crafted state pointed.

## Proposed change

Doc 30 §3, one sentence after the step-up prompt: "The shell keeps the interrupted command across the step-up only when its URL is under the configured API base and no key of its JSON body matches the kernel's forbidden-field rule (`FORBIDDEN_WORDS`, `SECRET_WORDS`); otherwise, after the step-up, the form is shown again with 'sign-in was refreshed; enter the details again'."

## Impact if accepted

- **Documents**: 30 re-issued (§3).
- **Code**: the two functions; the ported rule and its pin test; `openAccount` and phone commands are re-asked, an adjustment with a `reasonText` is kept.
- **Tests**: a pending command with a forbidden key is not stored; one with a foreign URL is dropped; one under the API base with plain keys is replayed once.
- **Rejected**: keep everything (personal data in session storage); keep nothing (every step-up loses the clerk's work); encrypt in storage (the key would sit beside it).
