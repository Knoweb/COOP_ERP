## What is wrong or missing

24A section 3 gives every trading table `owner_entity_id` and `received_at` (the partition key) and section 6 has the seller write on the buyer's order (AcceptOrder sets `allocated_qty`, `tier_price`, `committed_eta`, `lock_at` and the status ACCEPTED on `doc_order`; IssueDeliveryNote adds to `fulfilled_qty`) and the receiver write on the seller's delivery note (ConfirmGrn's `drops.markReceived`). The kernel base as built (K-07; kernel V0050, V0055, V0061) admits the rows of a document to their owner only: `kernel.document_owned(document_id)` is the WITH CHECK of `document_line`, `document_state_history` and `document_link`, and `RLS_POLICY_TEMPLATE.md` extends it to "a module's extension table keyed on document_id". A seller in its own OWN scope therefore cannot update the buyer's order rows or move the buyer's document to ACCEPTED, and a receiver cannot mark the seller's drop RECEIVED. AGENTS.md idea 3 says the same in words: no record is ever written by two parties.

Three smaller points found at the same time: 24A section 6.1 registers the batch after issuance and writes `line.batchId` on the kernel line, which is frozen at issuance (the synthetic batch number needs the GRN's number, doc 22 section 3.7); section 3.1 names no permission for the reads of section 5, which the kernel now checks for every GET (#144); and the partitioning of the extension tables presumes a partitioned base, which K-07 did not build.

## Options considered

1. **A `party_write` policy for the counterparty** on the buyer's order rows and the seller's drop rows: keeps 24A's columns, but two parties write one record (idea 3), the template says "nothing else", and a mistaken handler on either side could overwrite the other's facts with nothing in the database to stop it.
2. **The seller's decision as the seller's own record** (`trading.order_allocation`, `order_allocation_line`, owner the seller, counterparty the buyer, `party_read`), the receiver's GRN as the only record of a drop's receipt, and derived states read by the queries: idea 3 holds in SQL, every table takes an existing policy shape, and 24A's columns move rather than change meaning. The document's kernel status carries the owner's transitions only; the other party's answer is read beside it. Chosen.
3. **Two documents per step** (an order confirmation document type the seller issues): the same ownership, at the cost of a new numbered document type per answer, not in the registry and not in 24B.

For the batch: register before issuance (no number for the synthetic batch; and issuance may still refuse), or after issuance on the extension row (chosen: the extension row is the module's, the kernel line stays frozen, `grn.confirmed.v1` carries the batch id per line from `doc_grn_line`).

For the reads: one read code for the slice, `trd.document.view` (ENTITY), the pattern of `cat.sku.view` (CR-22A-3) and M1's `*.view` codes. Chosen.

For the partitions: partition the extension tables alone (a composite key everywhere for no read path that uses it), or follow the base as built and partition both together when doc 14's tiering policy (D-02) is applied. Chosen: not partitioned for the demo; deferred with the base.

## Decision

Decided 27 Sep 2026: accepted, on the architect's delegation.

- Extension tables keyed on `document_id` carry no `owner_entity_id` and no `received_at`; they take `document_read` on `kernel.document_visible(document_id)`, `document_write` and (where a column is updated) `document_update` on `kernel.document_owned(document_id)`, and are not partitioned until the base is.
- `trading.order_allocation` and `order_allocation_line` (owner the seller, counterparty the buyer, template with `party_read`) hold the seller's acceptance or rejection, the allocation run, committed ETA, lock time, per-line allocated and fulfilled quantities and tier price. `doc_order` keeps the buyer's request. The order's ACCEPTED, REJECTED, LOCKED, PARTIALLY_FULFILLED and FULFILLED states are derived by the order queries; SUBMITTED and CANCELLED are the buyer's transitions on the document.
- A drop's RECEIVED state and a delivery note's CLOSED state are derived from the confirmed GRNs that name the drops; `drops.markReceived` is not written.
- `doc_grn_line.batch_id` and `unit_cost` are written after issuance, in the confirmation transaction; the kernel line's `batch_id` stays null for a GRN.
- `trd.document.view` (ENTITY) is the `x-permission` of every read of `openapi/m4trading.yaml`; it is the 28th M4 code, in `seed/m1party/permissions.yaml`.

Reasons: the design documents already say it (idea 3; doc 18 section 3.7; the K-07 policies), the shape is the kernel's own for document rows, nothing is merged, and each part is one `ALTER` or one table away from 24A's wording if the architect prefers it. 24A sections 3 and 6 and doc 24 sections 3.1 to 3.3 are to be re-issued with these changes.
