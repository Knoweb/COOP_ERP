# CR-19A-11 — `NumberingService.observeDeviceNumber`: central keeps a device-held series' high-water mark

- **Status:** accepted
- **Date raised:** 2026-09-28
- **Raised by:** Claude Code session, a bug found on a live run (two receipts `M101-S01-T1-RCT-1` on the local stack), decided on the architect's delegation (branch `fix/till-number-high-water`)
- **Documents affected:** 19A §7 (numbering: the service's methods and the device-held series), doc 32 §8 (counter transfer: "central returns next_number per series computed from the highest applied doc_number"), 26A §10 (ReceiptBundleHook: what the ingest does with the number), 24B (N-4: numbers are never reused)
- **Code affected:** `kernel.api.NumberingService.observeDeviceNumber(UUID seriesId, long number)`, `kernel.internal.document.JdbcNumberingService`, caller `m6pos.internal.ingest.RecordReceiptHandler`

Decided 28 Sep 2026: accepted (PR on branch `fix/till-number-high-water`), on the architect's delegation. Reasons: doc 32 §8 already requires central to hand a new or replacement device the next number "computed from the highest applied doc_number", and the enrolment answer (K-08) reads `kernel.numbering_series.next_number`, so that column must follow what the tills send; the kernel owns the counter (19A §7, one writer per series row), so the raise belongs on its service and not in M6 writing `kernel.numbering_series` (AGENTS.md: never write another owner's schema). Options weighed: (a) compute the next number at enrolment or holder change from `max(doc_number)` of the applied documents (no write on ingest, but the kernel would read M6's `pos.receipt`, and every future device-held document type in M5 or M7 would have to be added to that query); (b) a kernel method each ingest calls that raises `next_number` when the number is higher (chosen: one line per ingest handler, the kernel reads nobody's tables, the row lock serialises two documents of one series); (c) leave it to the till (it cannot know what a lost or replaced predecessor issued). The raise is not audited on its own: it is derived from the applied document, whose `RECEIPT_RECORDED` record carries the number, and one extra audit row per receipt at 10,000 shops buys nothing. A number lower than the mark leaves it alone; a duplicate is never refused (AGENTS.md) but flagged by the ingesting module.

## What is wrong or missing

19A §7 gives `NumberingService` register, holder change, release, close and the list of a holder's series, and gives central's issuance `takeNumber`. For a series a device holds, nothing moved `next_number` when the device's documents arrived, so it stayed at the value it had when the series was registered (1). The enrolment answer and a holder change hand that value to the next device, which then reuses numbers already issued: two receipts `M101-S01-T1-RCT-1` on the local stack on 28 Sep, the second stored without a flag.

## Proposed change

- **19A §7:** add to the service: "`boolean observeDeviceNumber(UUID seriesId, long number)`: a module that applies a document a device issued from its own series calls it in the applying transaction; `next_number` becomes `number + 1` when that is higher, never lower. Not audited on its own. A device given the series later (enrolment, holder change, replacement) is answered from this mark (doc 32 §8)."
- **26A §10:** the ReceiptBundleHook calls it for the receipt's series and number, and flags a receipt whose series and number another receipt already has (`DUPLICATE_NUMBER`, REVIEW `RECEIPT_FLAGGED` and ALERT `RECEIPT_NUMBER_DUPLICATED`); both receipts are kept.
- **25A, 27A:** a till-issued document of their own (stock count, receiving, khata payment) calls it the same way when those ingests are built.

## Impact if accepted

19A §7 and 26A §10 gain the text above at the next re-issue. Code on the branch: the method and its implementation, the M6 call and flag, `TillSaleEndToEndIntegrationTest` (a replacement till continues 1, 2, 3; a forced duplicate stored and flagged) and `DocumentBasePostgresIntegrationTest` (raises, never lowers, not audited).
