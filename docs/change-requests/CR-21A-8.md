# CR-21A-8 — Additive location-activation prerequisite

- **Status:** accepted for INV-08 implementation, 24 October 2026; 21A not re-issued yet
- **Date raised:** 2026-10-24
- **Raised by:** Codex session implementing INV-08
- **Documents affected:** 21A §6, ActivateLocation handler specification; 25A §6, opening-balance workflow
- **Code affected:** `m1party.api.LocationActivationPrerequisite`, `m1party.internal.location.ActivateLocationHandler`, `m5inventory.internal.opening.OpeningBalanceActivationPrerequisite`

## What is wrong or missing

INV-08 requires a SHOP or WAREHOUSE to have a POSTED opening balance before its first activation. The opening-balance fact belongs to M5, while the location transition belongs to M1. The frozen M1 contract has no extension point through which M5 can contribute that prerequisite, and M1 must not depend on M5.

## Why it matters

Putting an M5 database query directly in M1 would reverse the module dependency and make M1 write business rules owned by inventory. Checking after activation would expose an ACTIVE stock location without its required opening stock. The prerequisite must run inside the existing M1 activation transaction, after M1's own guards and before the location mutation, audit and event.

## Proposed change

Add `LocationActivationPrerequisite` to the frozen `m1party::api` package. It is a small additive service-provider interface whose implementations receive the location's owner, identifier and type and either return or throw their module's domain error. `ActivateLocationHandler` invokes all registered implementations before moving an ONBOARDING location to ACTIVE.

M5 implements the interface with a read-only check for a POSTED opening balance belonging to the exact entity and location. It applies to SHOP and WAREHOUSE only; OFFICE activation and DORMANT reactivation are unchanged. The REST API has no shape change, so `m1party.yaml` remains version 1.5.0 and names this change request in `info.x-change-request`.

## Impact if accepted

- **Documents:** 21A §6 and 25A §6 gain the cross-module activation prerequisite when re-issued.
- **Code:** one additive M1 API interface, invocation from the existing transactional handler, and one M5 implementation.
- **Security and transactions:** the existing OWN scope, permission interceptor and PostgreSQL RLS remain authoritative; prerequisites do not mutate M1 state.
- **Compatibility:** existing M1 clients and REST operations are unchanged. A deployment without prerequisite beans preserves the previous activation behavior.
- **Tests:** the M5 prerequisite has focused unit coverage and PostgreSQL activation coverage for missing, draft and posted opening balances.
