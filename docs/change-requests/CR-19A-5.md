# CR-19A-5 — The outbox relay has a role and no way to log in

- **Status:** accepted
- **Decided 27 Sep 2026:** accepted as proposed (PR #TBD), on the architect's delegation. A login user `coop_relay` exists (`infra/compose/postgres/init/01-roles.sh`), a member of `app_relay` only, created by the idempotent role script and never by a migration (AGENTS.md); the relay uses its own small connection pool (PROGRESS "K-05 Event backbone": "relayed... through a separate `coop_relay` data source"), opened by worker instances. The grant is `GRANT SELECT, UPDATE (published_at) ON kernel.event_outbox TO app_relay` (`V0031__event_backbone.sql`, and copied to every partition by `ensure_event_outbox_partitions`), with an explicit `event_outbox_relay_select` policy (`USING (true)`) stating the relay reads every entity's events, as the CR asks. Reason: this is the only way to keep `app_relay`'s grant meaningful — granting it to `coop_app` (the shortcut the CR warns against) would let every module's code set `published_at`, removing the separation the role exists for; a dedicated login and pool costs nothing further to keep now and is far cheaper than un-mixing the roles later once other code has come to depend on `coop_app` doing double duty. 17A and 19A are not re-issued by this pull request; the re-issue should add these lines as proposed.

## What is wrong or missing

The relay is the only code allowed to set `published_at`, through the role `app_relay`. Roles are `NOLOGIN` by design and a login user is granted one: the application connects as `coop_app`, which has `app_rw`. No document names a login user for `app_relay`, no ticket creates one, and 19A does not say how the relay obtains a connection with that role: a second data source, or `SET ROLE` on the application's connection. The second would make `coop_app` a member of `app_relay`, and then every module's code could set `published_at` too.

The grant line is also incomplete for a relay: it gives `UPDATE (published_at)` and no `SELECT`, and the relay reads what it publishes. It reads every entity's events, so under `FORCE ROW LEVEL SECURITY` it needs a policy that lets it.

## Why it matters

It is work inside K-05 that nobody counted, and the shortcut (grant `app_relay` to `coop_app`) silently removes the separation the role exists for.

## Proposed change

- **17A §6 and 19A §5:** a login user `coop_relay` with `app_relay` only, created where the other login users are (compose locally, doc 35 for deployed environments). The relay uses **its own small data source** (a pool of 2), configured under `coop-erp.relay.*`, and only instances with the `worker` role open it.
- **19A §5:** `GRANT SELECT, UPDATE (published_at) ON kernel.event_outbox TO app_relay`, and a policy for `app_relay` that reads all entities, stated explicitly as the system class.
- **19A §14, K-05:** the ticket text gains "relay login user and data source".

## Impact if accepted

17A and 19A re-issued with these lines. K-05's estimate rises accordingly; the planning estimate of 5 days against the guide's 3 already assumes it.
