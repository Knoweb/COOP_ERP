# CR-19A-12 — Quiet hours defer a notification; they never suppress it

- **Status:** accepted (6 October 2026, on the architect's delegation; wave 2 code review); 19A not re-issued yet
- **Date raised:** 2026-10-06
- **Raised by:** Claude Code session, wave 2 code review decisions (`wave2-fixreview-till-web-kernel.md` TWK-22, `wave2-fixreview-m9-integration.md` M9-08), recorded in `docs/progress/deviations/2026-10-06-wave2-notifications.md`
- **Documents affected:** 19A §10 (the K-10 ticket: "quiet hours and hourly de-duplication checked before send"; the test list "Replayed event sends once; quiet-hours suppression; fallback language; provider failover"); doc 19 §7 and doc 29 §6.4 are the sources and do not change
- **Code affected:** `kernel.internal.notify.NotificationSuppression`, `NotificationService`, `NotificationLog`, `NotificationAudience.Recipient` (gains `entityId`, `roleCode`); `m9integration.internal.notify.ContactAudience`; `NotificationsPostgresIntegrationTest`, `NotificationDeliveryPostgresIntegrationTest`

## What is wrong or missing

Doc 19 §7 (restated in doc 29 §6.4): "Per recipient quiet hours (22:00–07:00 default for SMS)" and, in doc 29's rule catalogue, "quiet hours: deferred to 07:00". 19A §10 names the test "quiet-hours suppression". The kernel as built follows the guide's word: `NotificationSuppression.reasonToSuppress` returns `QUIET_HOURS`, the row is marked SUPPRESSED before any hold is written and is never claimed again; a retry inside the window suppresses and clears the hold. A bounced cheque at 21:00 never reaches the society by SMS. The window is read in the event owner's scope, so a distributor's configuration decides when a society's staff phones ring.

## Why it matters

The two design documents give the reasoning (an alert wanted in the morning, not never); the guide's test name is wording, not procedure. AGENTS.md: the design's reasoning holds, and a contradiction is raised, not picked silently.

## Proposed change

19A §10, the K-10 ticket text and its test list:

- "Quiet hours **defer**: a notification due inside the window is held QUEUED with `next_attempt_at` at the window's end in the business time zone (today or tomorrow); a deferral is not an attempt. The kill switch and the hourly duplicate suppress. The window is read for the **recipient's entity** when the audience resolver names it (ROLE_AT_COUNTERPARTY names the counterparty; `NotificationAudience.Recipient` carries `entityId` and `roleCode`), else the event owner's. A window longer than fifteen hours is refused by the configuration validator so the 24-hour maximum age is never reached by a deferral alone; an unparsable window is 'no quiet hours' with a warning."
- Test list: "quiet-hours **deferral** to the window's end; the recipient's entity's window, not the sender's".

## Impact if accepted

- **Documents**: 19A re-issued (§10). Docs 19 and 29 unchanged.
- **Code**: `NotificationSuppression` returns `Suppress(reason)` or `Defer(until)`; `NotificationService.deliver` and `attempt` hold instead of suppressing; `NotificationLog.defer(id, until)` (`attempts - 1`, `next_attempt_at = until`); the log screen reads a QUEUED row with a future `next_attempt_at` and `attempts = 0` as "deferred until"; no new status, no migration (the columns exist since V0054).
- **Tests**: `theKillSwitchAndTheQuietHoursSuppress` becomes "the kill switch suppresses; quiet hours defer and send at 07:00"; the delivery test clears the window for the buyer, not the seller.
- **Rejected**: suppression (above); the sender's window; a per-rule "drop if deferred" flag (no v1 template needs it; add it with the first time-critical template).
