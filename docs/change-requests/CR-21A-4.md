# CR-21A-4 — LocationFilter gains entityId

- **Status:** accepted, on the architect's delegation, 27 September 2026
- **Date raised:** 2026-09-27
- **Raised by:** Claude Code session, building the M1 freeze conditions and cross-slice checks (decisions of 27 September 2026)
- **Documents affected:** 21A §7 (the query table: `listLocations`), 22A §4 (`m1party::api`/`m1party::query` prerequisites)
- **Code affected:** `m1party/query/LocationFilter.java` (frozen at M1-13; `api`/`query` packages of `m1party.yaml` v1.0.0); `m1party/internal/queries/PartyQueriesImpl.java`; `m1party/web/LocationsController.java`; `LocationsPostgresIntegrationTest`

## What is wrong or missing

22A section 4 needs `listLocations(entity)` from M1's query package before M2 can build against it: a caller that is not scoped to one entity (FEDERATION_VIEW, and later an EXTERNAL_TIMEBOXED grant over several entities) has no way to ask for one entity's locations, only "everything the caller's scope can see". `m1party.yaml` reached 1.0.0 at M1-13 (#133), so this is a change to a frozen contract package under `tools/check-frozen-contracts.mjs` (built alongside this CR): a Java-only change to `m1party/query` needs either a version bump of the slice or an `info.x-change-request` naming this file. The REST slice itself is unchanged (no new query parameter is exposed over HTTP by this change), so the fix is recorded here rather than by bumping `m1party.yaml`'s `info.version`.

## Why it matters

Without this, M2 (and later M3, M5) cannot list one entity's locations through the query package alone and would have to filter the full page themselves, which duplicates the row-visibility rules 21A §7 already states for OWN, PARTY, FEDERATION_VIEW and EXTERNAL_TIMEBOXED.

## Change made

`LocationFilter` gains an optional `entityId` (fourth of five components, before `cursor`/`limit`, matching `EntityFilter`'s shape). `PartyQueriesImpl.listLocations` adds `and owner_entity_id = ?` when it is set. Row-level security already restricts an OWN caller's rows to its own entity, so the added filter only ever narrows what RLS returns: an OWN caller naming its own entity sees what it always saw; naming another entity gets nothing (RLS already excludes those rows; the filter adds no new exposure). A FEDERATION_VIEW or EXTERNAL_TIMEBOXED caller, which RLS lets see more than one entity, can now narrow to one. Covered by `LocationsPostgresIntegrationTest.theEntityFilterNarrowsTheFederationViewAndEmptiesAnOwnCallerNamingAnotherEntity`.

## Impact if accepted

- `m1party.yaml` `info.x-change-request` names this file (no `info.version` bump: the REST slice's shape did not change).
- No REST parameter is added by this CR; the `entityId` filter is reachable through the Java query package only, which is what 22A §4 needs.
- `m1party/README.md` "Contract freeze" section is updated to record this as a query-package change under the guard.
