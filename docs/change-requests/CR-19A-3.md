# CR-19A-3 — A database sequence cannot give the outbox the dense numbering doc 18 demands

- **Status:** accepted
- **Decided 27 Sep 2026:** accepted as proposed (PR #TBD), on the architect's delegation. `OutboxWriter` fills `source_seq` for `source = 'central'` from `kernel.central_source_seq` (a plain sequence, `V0031__event_backbone.sql`), which is correct for central under this CR's reading: consumers need a total order, and a sequence gives that, not density. `DeviceEventWriter` writes the till's own `device_seq` (dense by construction on the device, checked at ingestion by the 409 sequence-mismatch rule of doc 32), so density is preserved exactly where it matters — a till losing events. No `GapCheckJob` over `kernel.event_outbox` exists yet (only `kernel.internal.document.GapCheck`, for document numbers); when it is built it must check `(source, source_seq)` density for device sources only, never for `central`, and this is recorded as a follow-up in `docs/PLAN_TO_M2.md` (this pull request). Reason: a sequence is not transactional and a rolled-back transaction leaves a permanent hole, so checking density for `central` would raise a REVIEW every night in normal operation and the check would be ignored within a week — exactly what this CR warns against; the alternative (a locked counter row for central) was correctly rejected, since it would serialise the whole backend's command throughput on one row. Doc 18 and 19A are not re-issued by this pull request.

## What is wrong or missing

Doc 18 requires `source_seq` to be **dense per source**, and 19A's `GapCheckJob` verifies every night the "density of doc_number and of (source, source_seq); REVIEW on gap". 19A §5 fills `source_seq` for `source = 'central'` from a PostgreSQL sequence, inside the caller's transaction.

A sequence is not transactional: a value taken by a transaction that rolls back is never handed out again. Every command that fails after publishing its event (a guard in a later step, a constraint, a retry after a deadlock) leaves a hole. The same guide knows the difference: document numbers (§7, line 428) use a locked counter row, with the comment "row lock = gapless, monotonic".

## Why it matters

The gap check would raise a REVIEW for central every night in normal operation. A check that always reports is ignored within a week, and then it no longer catches the case it exists for: events lost between a till and central.

## Proposed change

Density matters for **devices**: a till numbers its own events, and a gap there means lost facts. For central, consumers need a total order, and a sequence gives that.

- **Doc 18, `event_outbox.source_seq`:** "dense per source for device sources; for `central`, strictly increasing and not necessarily dense".
- **19A §7, `GapCheckJob`:** checks the density of `(source, source_seq)` for device sources only.
- 19A §5 stays as written.

Alternative considered: number central events from a locked counter row, as documents are. Every command in the system would then queue on one row, and the throughput of the whole backend becomes that of one lock. Not proposed.
