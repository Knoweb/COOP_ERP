# CR-17A-1 — The problem document needs a field list, and one name for the message id

- **Status:** raised
- **Date raised:** 2026-09-20
- **Raised by:** Claude Code session, ticket S0-06 (server-side OpenAPI generation), after the architect's decision that the kernel enforces the shape of a request
- **Documents affected:** 17A §4.4 (conventions, row "Errors"); 21A §5 (one sentence); doc 30 §3 (row "Forms", one sentence); the same sentence as 21A §5 wherever a later nA guide restates it
- **Code affected:** `kernel.internal.stub.RequestValidationHandler`, `ProblemResponses`, `openapi/common.yaml` (`Problem`, `FieldProblem`), the nine `request.*` messages in `i18n/{en,si,ta}.json`. Already built, under `docs/PROGRESS.md` "S0-06 decisions" item 2; see "Why it matters" for why it did not wait.

## What is wrong or missing

**1. No field list.** 17A §4.4 defines the error format in one sentence:

> RFC 9457 problem details; error codes are stable strings (relationship.overlap) and are message-catalogue ids so the web renders them in the user's language.

That describes one error per response. Doc 30 §3 expects more of the same API:

> Forms — Validation schema generated from the contract; inline errors in the shop language

An inline error belongs to a field. A form with three wrong fields needs three errors, each naming its field, in one response. Nothing in 17, 17A or 19A says how the server reports that, and the client-side schema of doc 30 cannot be the only check: the till, the integration partners of M9 and a stale web client all reach the server without it.

**2. Two names for the message id.** 17A §4.4 says "error codes are stable strings". 21A §5 says:

> errors are problem details whose type is a message id

In RFC 9457 `type` is a URI reference that identifies the problem type; a bare `relationship.overlap` there is read as a relative URI. The hello template and the kernel carry the message id in an extension member `code` and leave `type` at its default, which is what 17A's wording suggests. A module developer who follows 21A literally produces a second format.

## Why it matters

S0-06 turned on enforcement of the OpenAPI schemas (the architect's decision of 2026-09-20: with trainees building modules in parallel, a forgotten null check must not become a 500). Enforcement needs an answer format at once, and every module copies the hello template, so the format had to exist before M1 starts. It was built as the smallest extension of the 17A sentence and recorded as a deviation. If the design settles on something else, the change is confined to one kernel class and one shared schema; no module writes validation code.

If it stays unwritten, the S0-07 API client, the till's error handling and each module's forms will each guess the shape.

## Proposed change

**17A §4.4, row "Errors"**, replace the sentence with:

> RFC 9457 problem details (`application/problem+json`). The extension member `code` carries the error code: a stable string (`relationship.overlap`) that is a message-catalogue id; `title` is that message in the caller's language and `params` holds the values it mentions. `type` is not used. A broken business rule answers 422 with the rule's own code. A request that does not match its OpenAPI schema answers 400 `request.invalid` and lists every mismatch in `errors`: `{ field, code, message, params }`, where `code` is one of the generic ids `request.field.required`, `.too_short`, `.too_long`, `.too_small`, `.too_large`, `.format`, `.invalid`. A body that cannot be read answers 400 `request.malformed`. The kernel produces the 400 answers for every module from the schema; a module writes neither code nor messages for them.

**21A §5** (and the same sentence in later guides): "errors are problem details whose `code` is a message id (17A §4.4)".

**Doc 30 §3, row "Forms"**, add: "The server checks the same contract and reports mismatches per field (17A §4.4); the form places each `errors[]` entry under its field and shows `title` for anything else."

## Impact if accepted

17A re-issued as v0.2; 21A and doc 30 amended by one sentence each, or by a register note "amended by CR-17A-1". Code: none, it matches what is proposed; `docs/PROGRESS.md` item 2 of "S0-06 decisions" then stops being a deviation. If rejected or changed: `RequestValidationHandler` and `common.yaml` change to the agreed shape, `web/src/generated/*.ts` is regenerated, and the tests `RequestValidationHandlerTest` and the five shape tests in `HelloModuleIntegrationTest` follow.
