# CR-19A-6 — An internal command has no permission and no idempotency key of its own

- **Status:** raised
- **Date raised:** 2026-09-27
- **Raised by:** Claude Code session, ticket M2-05 (branch `feat/m2-05-batches`)
- **Documents affected:** 19A §3 (the command interceptor: "permission → MFA → idempotency → handler"); 17A (R7: every handler carries a permission that is the x-permission of an operation); doc 22 §4.1 ("RegisterBatch (internal) … internal (caller module)"); 22A §4 ("RegisterBatch (internal command, exported for M4/M5)")
- **Code affected:** `kernel.api.CommandHandler` (constant `INTERNAL`), `kernel.internal.CommandInterceptor`, `tools/check-permissions.mjs`; first user `m2catalogue.internal.batch.RegisterBatchHandler`

## What is wrong or missing

Doc 22 and 22A make RegisterBatch an internal command: M4's GRN confirmation and M5's repack call it "in their own transaction", and its permission is the caller module's. 19A §3 knows one kind of command, one that arrives over HTTP with its own permission and its own Idempotency-Key. The repository enforces that shape three times: `ArchitectureTests` requires a non-blank permission on every `@CommandHandler`, `check-permissions.mjs` requires it to be the x-permission of an operation of the module's slice, and `CommandInterceptor` checks the permission and claims the request's idempotency key for every handler it wraps.

An internal command fits none of them. It has no operation, so no x-permission; any real permission code (a `cat.*` one) would refuse the GRN clerk who holds M4's permission only; and when M4's handler calls it inside the same HTTP request, the interceptor would claim the request's key a second time and find it taken by M4's own command.

## Why it matters

Without a rule, each module that exports a command invents one: a borrowed permission that refuses the right users once enforcement is on, or a second idempotency claim that breaks the calling command.

## Proposed change

- **19A §3:** "A command another module calls inside its own command (an internal command) declares `@CommandHandler(permission = CommandHandler.INTERNAL)`. The interceptor checks neither permission nor idempotency for it and requires the caller's transaction: the calling command was checked and holds the key. An internal command is exposed to other modules through an interface in the owning module's `api` package, never through an operation."
- **17A (R7):** the permission check of the slices skips `INTERNAL`.

## Impact if accepted

19A and 17A gain the sentences above. The code is already written this way in M2-05 (built to this proposal and cited in `CommandHandler.INTERNAL`); if the architect decides otherwise, `RegisterBatchHandler` and the three kernel lines change, nothing else.
