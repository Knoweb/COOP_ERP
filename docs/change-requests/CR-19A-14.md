# CR-19A-14 — The audit review reader, and no scope-minting API for modules

- **Status:** accepted (13 October 2026, on the architect's delegation; wave 4 code review); the documents are not re-issued yet
- **Date raised:** 2026-10-13
- **Raised by:** Claude Code session, wave 4 fix of `docs/reviews/wave4-m3.md` M3R-08 and M3R-09 (PR #334 added both kernel APIs without the architect)
- **Documents affected:** doc 19 §4 (audit: the log is insert-only for the application) and 19A §4 (`AuditFacade`); 19A §12 (jobs) through CR-19A-7; 23A §7.1 (the gazette and batch-MRP reviews: "consumer → fan-out") 
- **Code affected:** `kernel.api.AuditReviewReader`, `kernel.internal.audit.JdbcAuditReviewReader`, kernel `V0093` (role `kernel_audit_reader`, the two definer functions); `kernel.api.ScopedExecution` and `kernel.internal.job.DefaultScopedExecution` removed; `m3pricing.internal.review` (consumers, `PricingReviewJob`, two internal commands), m3pricing `V0007` (`pricing.review_trigger`); `ArchitectureTests.onlyScheduledJobsTakeAnEntitysScope`

## What is wrong or missing

1. M3's pricing reviews (23A §7.1: BATCH_MRP_BELOW_LIST, TRADE_ABOVE_MRP, LIST_ABOVE_CEILING_AT_GAZETTE) are REVIEW audit records, and `listReviews` and the replay check must read them back. The audit log grants the application INSERT only (doc 19 §4), so a read needs a narrow door. #334 added `kernel.api.AuditReviewReader` with a kernel SQL function that listed M3's three codes, and read the log through a grant to `app_seed` with a policy `USING (true)`, which let the migrator login read every tenant's audit rows directly.
2. The two review consumers must compare one event with every society's lists. #334 added `kernel.api.ScopedExecution`, which let any module open a FEDERATION_VIEW or any entity's OWN scope on demand: from a request handler, a module could then write into another society's rows, and nothing in the kernel stops it (the scope is the RLS boundary and this API minted it). CR-19A-7 (accepted as revised, 27 September 2026) already gives the only sanctioned way: a `@ScheduledJob` takes `JobExecution.federationView()` to find the work and `JobExecution.ownScopeOf(owner)` to act on each row in its owner's name, and the build holds that only a `@ScheduledJob` method calls it.

## Why it matters

A reader that names one module's codes in a kernel function makes the kernel depend on a module; a role-wide read of the audit log breaks tenant isolation for whoever holds the role; an API that mints any entity's scope on demand removes the boundary RLS rests on.

## Proposed change

1. **19A §4**: add `AuditReviewReader` (`listReviews(eventTypes, limit, scope)`, `reviewExists(eventType, subjectId, detailKey, detailValue, scope)`). The caller passes its own event codes; the function answers only codes whose `kernel.audit_event_type.severity` is REVIEW; an OWN caller reads its entity's rows (and its location's, when it has one), FEDERATION_VIEW reads every entity's, any other class is refused. The two functions are `SECURITY DEFINER`, owned by `kernel_audit_reader`, a NOLOGIN role that alone holds SELECT on `kernel.audit_event` (through a policy that repeats the scope test) and on `kernel.audit_event_type`; nobody inherits it (the migrator receives SET only, to hand the functions over). `app_seed` reads no audit row.
2. **19A §12 and 23A §7.1**: `ScopedExecution` is rejected. A consumer that must look across tenants records the work in its own module's table in the scope the dispatcher gives it, and a `@ScheduledJob` finds it with `federationView()` and acts on each item with `ownScopeOf(owner)` through a command handler. M3: the consumers write `pricing.review_trigger`; `PricingReviewJob` raises each review in its list owner's scope (`RaiseReview`) and marks the trigger checked in the trigger owner's scope (`CheckReviewTrigger`, audit PRICING_REVIEW_CHECKED, event `pricing.review_check_completed.v1`).
3. **The build**: outside the kernel, a method of a `kernel.api` type that hands out a `ScopeContext` (other than `CurrentScope.get`, governed by its own rule, and `ScopeContext` itself) is called only from a `@ScheduledJob` method, and only on `JobExecution` (`ArchitectureTests.onlyScheduledJobsTakeAnEntitysScope`).

## Impact if accepted

- **Documents**: 19A (§4, §12) and 23A (§7.1) re-issued with the rule; doc 19 unchanged (the log stays insert-only for the application).
- **Code**: as listed above; reviews are raised by the job within a minute of the event rather than in the consumer's transaction.
- **Tests**: a PARTY scope is refused by both functions; the job raises one review per owner and list kind, compares in the same unit with the version in force, and is idempotent on a replay; the architecture rule bites on a module that calls a scope-minting kernel API or calls `JobExecution`'s scope methods outside a job.
- **Rejected**: `ScopedExecution` (and a "fan-out per owner" mode of `@EventConsumer`, which would need a kernel decision of its own); review codes in a kernel function; the `app_seed` read of the audit log.
