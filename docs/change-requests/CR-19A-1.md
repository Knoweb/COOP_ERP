# CR-19A-1 — 19A names most published kernel types without giving their signatures

- **Status:** raised
- **Date raised:** 2026-09-21
- **Raised by:** Claude Code session, while preparing the 19A phase (branch `chore/19a-kernel-prep`, pull request #61)
- **Documents affected:** 19A §0 (service map), §1, §2, §3, §6, §7, §8, §9, §10, §12
- **Code affected:** `kernel.api`. Nothing is declared for these types yet; #61 declared only the three whose signatures 19A gives (`PermissionResolver.allows`, `Sod.assertDistinct`, `@EventConsumer`)

## What is wrong or missing

19A §0 lists the types each kernel service publishes in `kernel.api`. For most of them the guide gives a name, sometimes method names, and no parameter or return types. A module compiles against these types, so they are contract; the rule followed in #61 was not to invent one.

| Type | 19A | What is given | What is missing |
|---|---|---|---|
| `IdentityProviderClient` | §0, §2 (line 141) | `createUser`, `disableUser`, `setTemporaryPassword`, `resetTotp`, `revokeSessions` | every parameter and return type |
| `DeviceCredentials` | §0 | the name | everything |
| `PermissionResolver.resolve`, `.limits` | §3 (lines 174, 178) | `Resolved resolve(UUID userId, int catalogueVersion)`, `Optional<Limits> limits(ScopeContext, String)` | the types `Resolved` and `Limits` are defined nowhere |
| `Sod.roleModeConflict`, `Grant.withinGrantor`, `Grant.lastAdminGuard` | §3 (lines 200–201) | the names, with `(role)`, `(ctx, permissions)`, `(entity)` | the parameter types are M1 types no document defines; the return types |

| `DocumentService` | §0 | the name | everything |
| `NumberingService` | §7 | `seriesFor(typeCode, entityId, locationId, tillPositionId)`; `registerSeries`, `holderChange`, `closeSeries` | the return type of `seriesFor`; the parameters of the other three |
| `DocumentLinks` | §7 | `link(from, to, type, amount?)` | the return type; the type of `amount` |
| `Attachments` | §0, §9 | the internal `PresignService.put(documentId, attachmentId, contentType)` | the published signature |

Two disagreements between 19A and the existing, reviewed code belong to the same re-issue:

- **`ScopeContext`** (§1): nine components, no `activeScope`, `String lang`. The code has ten, an explicit `activeScope` and a `Locale` (the widening of 18 September, branch `feat/s0-foundation-fixes`); 19A §1's own prose describes choosing a scope per request.
- **`Messages.t`** (§6): returns `Text(value, fallback)`. The code returns `String`, and the web client already renders a fallback tag.

And one between 19A and AGENTS.md: the service map puts **`BrokerAdapter`** in `kernel.internal`; AGENTS.md names it beside `IdentityProviderClient` as though both were published. 19A's placement looks right, since no module publishes to a broker (they use `EventPublisher`).

## Why it matters

Each missing signature blocks the lane that needs it, and the first is on the critical path: AGENTS.md requires identity to sit behind `IdentityProviderClient`, so K-02 cannot start without it. If each developer fills a gap alone, four lanes publish four styles of contract, and every module guide from 21A on that cites these types is written against a guess.

## Proposed change

Re-issue 19A with a signature for every type in the table. Proposals for the ones that need a decision first; the rest need the architect's hand.

**`IdentityProviderClient`** (K-02), provider-neutral, no Keycloak type in it:

```java
public interface IdentityProviderClient {
    /** Creates the login; returns the provider's subject id, which M1 stores on user_account. */
    String createUser(UUID userId, String username, Locale language);

    void disableUser(String subjectId);

    /** Generated on the provider's side and returned once, for delivery by a notification; never logged (AGENTS.md). */
    TemporaryPassword setTemporaryPassword(String subjectId);

    void resetTotp(String subjectId);

    void revokeSessions(String subjectId);
}
```

**`@ScheduledJob` durations:** ISO-8601 strings (`lockTimeout = "PT10M"`), parsed and validated when the job registry starts. They read like the `interval` values of `kernel.scheduled_job`, and a `long` would need its unit in its name.

**`SyncApi`:** no Java type in `kernel.api`; the contract is `openapi/sync.yaml` and doc 32. Remove it from the `kernel.api` column of the service map.

**`ScopeContext`:** 19A §1 takes the code's ten components. **`Messages`:** K-06 adds `Text text(...)` beside `String t(...)`, so today's callers do not change. **`BrokerAdapter`:** stays in `kernel.internal`; AGENTS.md is reworded to "behind interfaces (`IdentityProviderClient` in `kernel.api`, `BrokerAdapter` inside the kernel)".

## Impact if accepted

19A re-issued (v0.2). `kernel.api` gains the declarations in one pull request before the lanes start, reviewed by the architect. One sentence of AGENTS.md. No existing code changes.
