# CR-21A-1 — Four decisions M1-03 took locally that belong to the documents

- **Status:** raised
- **Date raised:** 2026-09-23
- **Raised by:** Claude Code session, from the review of pull request #72 (M1-03, entity lifecycle)
- **Documents affected:** 21A §3.3 (the permission catalogue), §3.1 and doc 18 Part A and Part F (the tables of `party`), 17A §6.3 (the policy template), 21A §5 (the API slice) against the kernel's problem convention (17A §4.3, `openapi/common.yaml`)
- **Code affected:** `seed/m1party/permissions.yaml`; `db/migration/m1party/V0002__entity_registration_policy.sql` and `V0003__entity_party_directory.sql`; `openapi/m1party.yaml`; `RegisterEntityHandler`

#72 solved four real problems in ways the documents do not describe. Each solution may be right; none is the developer's to decide alone, and the next module will copy whatever `main` shows. Each item asks for one decision.

## 1. The permission catalogue was coarsened

**What is wrong.** 21A §3.3 names the catalogue by verb: `prt.relationship.open`, `.activate`, `.amend`, `.suspend`; `prt.location.register`, `.activate`, `.primary`; `sys.device.enrol`, `.suspend`; `gov.audit.review`. The seed on `main` ships `prt.relationship.manage` and `.view`, `prt.location.manage` and `.view`, `sys.device.manage` and `.view`, `gov.entity.view`, and `gov.entity.manage` (an unused synonym of `.register` plus `.suspend`). Fifteen codes, seven of which 21A does not name, and nine of 21A's sixteen missing.

**Why it matters.** The catalogue is the contract between the role templates (doc 07), the SoD pairs and every `@CommandHandler` from here on; 21A §6.1's amend flow needs the fine grain (a clerk may open a relationship and not amend its terms), and the SoD pair "request / approve" cannot be expressed over one `manage` verb. The catalogue is also the week-2 freeze item (M1-13).

**Proposed change.** The seed follows 21A §3.3 as written; `manage`/`view` pairs are removed; `gov.entity.suspend` is kept as an addition to 21A (21A's `activate` does not cover suspension, and a Federation clerk who may suspend is not necessarily one who may register). 21A §3.3 re-issued with `gov.entity.suspend` and `.reinstate` added.

## 2. Two tables and a fifth policy class were invented

**What is wrong.** To let the Federation register and administer entities under row-level security without a policy that recurses into the table it protects, #72 added `party.federation_identity` (one row: which entity is the Federation, maintained by a trigger) and `party.entity_party_directory` (a projection of entity ids and legal names, for counterparties), and on `party.entity` three policies `federation_admin_read`, `federation_register`, `federation_admin_update`. Neither table is in 21A §3.1 or doc 18 Part F; the policies are a class beyond 17A §6.3's template (`own_*`, `fed_view`, `ext_view`), and PR #76 adds a fourth, `party_read`, on `entity_relationship`.

**Why it matters.** AGENTS.md: a shared table is doc 18's; a policy class is the template's; "if the design looks wrong, raise a change request, never fix locally". The recursion problem is real and will recur in every module that lets the Federation act on rows it does not own. It needs one answer, in the template, not one per table. And `entity_party_directory` is a masking view by another name: 19A K-01's "masking view convention" is the place it belongs.

**Proposed change.** (a) Doc 18 Part F lists `party.federation_identity` and `party.entity_party_directory`, or 19A K-01 replaces the second with the masking-view convention and the first with a kernel function `kernel.federation_entity()` (one row, cached, no trigger). (b) 17A §6.3's template gains the two classes the modules need: **`fed_admin`** (the Federation entity, resolved by scope, writes rows it does not own where the guide says the Federation administers them) and **`party_read`** (a counterparty reads the rows it is a side of; the definition doc 18 §3.7 already gives PARTY). K-01 delivers both as the template and the RLS matrix test covers them.

## 3. A duplicate entity code answers 422, not 21A's 409

**What is wrong.** 21A §5 line 428: `registerEntity ... responses: { "201": EntityCreated, "409": Problem }`, and line 490 gives 409 for an overlapping relationship. The kernel answers every business problem with **422** (`openapi/common.yaml`, `RuleBroken`; `ProblemResponses` maps every `ProblemException` to 422 except the request errors), and the hello module answers 422 for a duplicate greeting. #72 follows the kernel: 422 with code `m1.entity.code_duplicate`.

**Why it matters.** Both are defensible; the web client's error handling and every future slice must follow one. A per-code status table in the kernel is a kernel change; a 409 written into one module's slice is a deviation the build does not catch.

**Proposed change.** Keep the kernel's rule: **one status for a broken business rule, 422, with the code saying which.** 21A §5 re-issued with 422 where it says 409, and 17A §4.3 states the rule in one sentence so no guide reintroduces 409. The alternative, a status per problem code, adds a table nobody will keep in step with the catalogue.

## 4. Request shape enforced twice

**What is wrong.** `m1party.yaml` carries `maxLength`, `enum` and `minimum`/`maximum` for the registration request, as AGENTS.md requires, and `RegisterEntityHandler` re-checks the same five things (`code_invalid`, `type_invalid`, `legal_name_required`, `default_language_invalid`, `financial_year_start_month_invalid`), each with a message id in three languages that no HTTP request can ever reach. 21A §6 lists them among the handler's guards.

**Why it matters.** Two places for one rule drift; the guide contradicts AGENTS.md's rule ("the shape of a request lives in the OpenAPI schema and the kernel enforces it; a handler guards business rules only"), and five of the translations that #72 lost were for these unreachable guards.

**Proposed change.** 21A §6 re-issued to list business guards only, with a sentence that shape is the slice's; the five guards and their message ids are removed from the handler in a follow-up once 21A says so.

## Impact if accepted

21A re-issued (v0.2) for items 1, 3 and 4; 17A §6.3 and §4.3 for items 2 and 3; doc 18 Part F or 19A K-01 for item 2. Code changes: the seed file (item 1), the slice (item 3), the handler (item 4), and K-01's template work (item 2). Nothing is applied before acceptance; #76 fixes the security defects of #72 within the design as it stands.
