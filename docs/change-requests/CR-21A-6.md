# CR-21A-6 — M1's counterparty view gains the buyer's VAT number

- **Status:** accepted, on the architect's delegation, 27 September 2026
- **Date raised:** 2026-09-27
- **Raised by:** Claude Code session, ticket `fix/invoice-buyer-vat`, from the M4-08 deviation (PR #164)
- **Documents affected:** 21A §7 (the query table: `getEntity`, PARTY visibility), 18 §3.7 (PARTY: "trading documents where the caller's entity is seller or buyer; counterparty columns masked"), 24A §6 (`IssueInvoice`'s buyer VAT number)
- **Code affected:** `m1party/query/EntityView.java` (frozen at M1-13; `m1party.yaml` v1.1.0); `m1party/internal/queries/PartyQueriesImpl.java`; `db/migration/m1party/V0013__entity_party_directory_vat.sql`; `m4trading/internal/invoice/IssueInvoiceHandler.java`

## What is wrong or missing

PR #164 (M4-08) built `IssueInvoice` to record `buyer_vat_no` empty, with a comment that the seller cannot read the buyer's VAT number: M1 gives a counterparty its legal names only (`party.entity_party_directory`, V0003/V0004), and the seller's own-scope read of `party.entity` cannot see the buyer's row at all (`own_read`, V0001, is `owner_entity_id = kernel.scope_entity()`). Doc 24A §6's handler spec for `IssueInvoice` records "the VAT numbers" without saying where the buyer's comes from, and 21A §7 documents `getEntity`'s PARTY-visibility projection as names only, silent on VAT. `EntityView` already carries a `vatRegistrationNo` field (added for the seller's own reading of its own entity) and the REST schema (`m1party.yaml`, `EntityResponse`) already exposes it; only the counterparty projection withheld it.

## Why it matters

A tax invoice is required to carry the buyer's VAT registration number when the buyer has one; recording it empty is a defect the demo and any real invoice would show. The seller is entitled to read it: it is not a column doc 18 §3.7 asks to mask from a counterparty (that section masks the counterparty's own operational data, not its registration facts), and the counterparty projection already exists for the read.

## Change made

`party.entity_party_directory` (the counterparty projection PARTY already reads) gains `vat_registration_no`, synchronised by the existing trigger from `party.entity`. Its RLS policy `party_names_read` widens from `kernel.scope_class() = 'PARTY'` to `kernel.scope_class() IN ('PARTY', 'OWN')`, keeping the same row test (the caller's own entity, or the other side of an active trading relationship): an OWN-scoped caller reading a counterparty gets exactly the same row a PARTY-scoped caller would. `PartyQueriesImpl.getEntity` falls back to this directory when an OWN-scoped caller's read of `party.entity` finds nothing (the target is not the caller's own row) instead of returning empty outright; a miss there still means "not visible" (RLS decides). `IssueInvoiceHandler` needed no logic change: it already reads `buyerVat` through `parties.getEntity(buyerId, scope)` and falls back to `""` when absent (no active relationship, or the buyer has no VAT number). Covered by `PartyQueriesImplTest` (an OWN-scoped seller's fallback reads the directory and gets the VAT number; the existing PARTY-scope test now expects it too) and `InvoiceHandlersPostgresIntegrationTest` (an invoice between two entities under an active relationship carries the buyer's VAT number; an unrelated entity's read stays empty).

`m1party.yaml` moves to 1.2.0 (`info.x-change-request: CR-21A-6`): no REST schema shape changed (`EntityResponse.vatRegistrationNo` already existed), but the field's *visibility* under `getEntity` for a counterparty is a contract-relevant behaviour change, so the version records it rather than leaving a query-package change unmarked.

## Impact if accepted
