# CR-19A-8 — Identity and permissions as built: scopes at request time, one read check in the kernel, the resolved set per class, `GET /v1/session`

- **Status:** accepted
- **Date raised:** 2026-09-27
- **Raised by:** Claude Code session, the identity and permission decisions delegated by the architect (branch `feat/decisions-identity-permissions`); the questions were raised by pull requests #105, #123 and #130
- **Documents affected:** 19A §2 (provider mapper endpoint; claims `scopes` and `roles`), 19A §3 (`PermissionResolver`: "only the OWN class resolves to anything"; the enforcement point), doc 19 §3.4 (enforcement points: "declarative annotation per service method"), doc 30 §3 ("visibility from the resolved permission set": where the set comes from), 21A §7 (`ResolveScope`, `ResolvePermissions`: "external grants for EXTERNAL users"), doc 21 flow 6.5 (the regulator's role), 21A §3 (the `regulator` template's permissions)
- **Code affected:** `kernel.internal.security` (`JwtClaimsMapper`, `JdbcUserScopes`, `JdbcPermissionResolver`, `PermissionGate`, `SliceOperations`, `ReadPermissionInterceptor`, `SessionController`), `kernel.internal.ScopeFilter`, `openapi/session.yaml`, `m1party.internal.security.role.AssignRoleHandler`, `web/src/shell/auth/*`, `tools/check-permissions.mjs`

Decided 27 Sep 2026: accepted (PR #144), on the architect's delegation. The four decisions below were taken together because they are one rule seen from four sides: where a caller may act comes from M1's tables at request time; what a caller may do is resolved once, by class, in the kernel; every operation of every slice, a GET included, is checked against that set in one place; and the web shell reads the same set from one operation. Reasons with each item.

## What is wrong or missing

1. **19A §2 puts `scopes` and `roles` into the token "through a provider mapper that reads M1's user_role through a small kernel endpoint at token issue time".** The provider we run has no such mapper without a provider-specific extension, which AGENTS.md forbids the kernel to depend on; and a claim is fixed for the token's lifetime, while doc 21 flow 6.5 says "revocation immediate". K-02 (#105) resolved the scopes at request time instead and asked the architect to confirm.

2. **19A §3 says "only the OWN class resolves to anything: the read-only classes run no command", and 21A §3 seeds the `regulator` template with `permissions: []`.** Together with AssignRole's class rule ("an EXTERNAL_TIMEBOXED role reaches a regulator through an external grant, never through an assignment") an EXTERNAL_TIMEBOXED principal could never hold a permission, so doc 21 flow 6.5 could not run end to end over HTTP once reads are checked (#130, the deep review of M1-09).

3. **Doc 19 §3.4 asks for the permission of every operation to be checked at the API layer; 19A §3 builds the check into the command interceptor only.** Reads were checked by hand, controller by controller (#120 and #130 added four), and a fifth controller could forget it.

4. **Doc 30 §3 says visibility comes "from the resolved permission set", but no operation of any slice handed that set to a client**, and doc 19 §2.2 keeps permissions out of the token ("a role can hold hundreds"). The web shell kept a hand-written role map (#123).

## Why it matters

A regulator is a real principal of version 1 (M-10, J-09); without a rule for its permissions the grant register exists and the inspection cannot happen. A read check written per controller is one that a fresh graduate forgets in the next module. A shell that decides visibility from a map of its own shows a button the server refuses, or hides a module the user holds.

## Proposed change

- **19A §2 (scopes):** "The kernel resolves the caller's scopes at request time from M1's `user_role` (OWN) and the granted entities from `security.external_grant` (EXTERNAL_TIMEBOXED), cached per instance for a minute and emptied by the role, user and grant events; a grant entry lives no longer than the earliest `valid_until` in it. A token that carries `scopes` or `grants` claims is honoured only as a narrowing of the records, never a widening. The provider mapper endpoint is not built." (What #105 built; confirmed.)

- **19A §3 (the resolved set, by class):** "`PermissionResolver.resolve(ctx)` answers, for OWN, the union of the permissions of the ACTIVE roles the user is assigned in the scope (an entity-wide assignment applies at every location); for EXTERNAL_TIMEBOXED, the union of the permissions of the user's ACTIVE roles of that class (the Regulator and Auditor templates, assigned by the Federation at the user's home entity), while the user holds a current grant, and nothing once the grant ends: the grant says where, the role says what; for FEDERATION_VIEW, every read of every slice (the x-permission of every GET a user may call), because the class is 'SELECT on everything, no writes' (doc 18 §3.7) and its template carries no permission of its own; for anything else, nothing. A command runs in the OWN class only, whatever the resolver says (a read code and a command code may be one string, as `gov.external.grant` is)." 21A §3: the `regulator` template carries `gov.entity.view`, `prt.location.view`, `cat.sku.view` (as `seed/m1party/role-templates.yaml` already does). 21A §6, AssignRole: "role class permits: OWN for everybody; FEDERATION_VIEW for the Federation; EXTERNAL_TIMEBOXED for the Federation, to a user of kind EXTERNAL." Doc 21 flow 6.5 gains the step "AssignRole of the Regulator template to the EXTERNAL user" between CreateUser and GrantExternalView (the order of the two does not matter).

- **19A §3 (the enforcement point for reads) and doc 19 §3.4:** "The kernel enforces the `x-permission` of every GET on the generated interfaces, before the controller runs: the request's path template names the operation, the slice gives its permission (read once at start from every `openapi/*.yaml`), and the same gate as for commands decides, under the same enforcement switch and without a second factor (the challenge is at the action, doc 19 §2.2). A controller checks no read by hand. A GET a user may not call is refused 403 `permission.denied`."

- **19A §2 and doc 30 §3 (the session read):** "The kernel serves `GET /v1/session` (`openapi/session.yaml`, generated into `kernel.session.web.generated`): the user, the home entity, the policy class, the scopes held, the active scope, the granted entities and the permissions resolved for the active scope. Its x-permission is `authenticated`, the one value that is not a code of the catalogue: any signed-in principal, on a GET that answers with the caller's own facts and nothing else; the permission check of the build refuses it on a mutating operation and on a `@CommandHandler`. It is the one operation a caller holding several scopes may call without naming one. The web shell reads its permission set from it, once per token, and decides visibility from that set; the token's `roles` claim is read by nobody."

## Impact if accepted

19A §2 and §3, doc 19 §3.4, doc 30 §3, 21A §3, §6 and §7 and doc 21 flow 6.5 gain the sentences above at their next re-issue; none is re-issued by this request. The code is written this way in pull request #144: the kernel's `SliceOperations`, `ReadPermissionInterceptor`, `PermissionGate.requireRead`, the resolver by class, `ScopeFilter` (a granted entity may be the active scope; the session read needs no scope choice), `SessionController` and `openapi/session.yaml`; M1's AssignRole class rule; the four hand-written read checks of #120 and #130 removed; the web shell's role map replaced by `PermissionsContext` over `GET /v1/session`; `tools/check-permissions.mjs` rule 5. Tests: `SliceOperationsTest`, `PermissionGateTest`, `ScopeFilterHoldsTest`, `ReadPermissionsPostgresIntegrationTest` (flow 6.5 over HTTP with an EXTERNAL token, enforcement on), `RoleHandlersPostgresIntegrationTest` (the Federation assigns an external role to an EXTERNAL user and to nobody else), the web unit tests and the e2e run (fed-admin, FEDERATION_VIEW, still does not see the register form; the cashier is seeded with the reads alone).
