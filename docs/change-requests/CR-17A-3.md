# CR-17A-3 — The policy template lets the read-only classes read and write through `own_*`, and lets a shop read the whole entity through PARTY

- **Status:** raised
- **Date raised:** 2026-09-24
- **Raised by:** Claude Code session, from the RLS matrix test of 19A K-01 (`RlsMatrixIntegrationTest`, branch `feat/k01-rls-policy-template-and-matrix`)
- **Documents affected:** 17A §6.3 (the policy template, lines 495–505 of the text extract); 19A §1 (the PARTY policy, line 120); doc 18 §3.7 is the authority and needs no change
- **Code affected:** every `own_read`/`own_write` policy on `main` (40 of them: `hello` 2, `kernel.audit_event` 4, `party` 15, `security` 17, `pricing` 2) and every future `party_read`

## What is wrong or missing

Doc 18 §3.7 defines the classes: OWN reads and writes its entity's rows; PARTY reads the documents it is a side of; FEDERATION_VIEW and EXTERNAL_TIMEBOXED read (everything, or the grant) and **write nothing**; "a shop sees nothing of a sibling shop because shop-scoped users carry a location scope".

17A §6.3's template tests the entity and not the class:

```sql
CREATE POLICY own_read  ... USING (owner_entity_id = kernel.scope_entity() AND (... location ...));
CREATE POLICY own_write ... WITH CHECK (owner_entity_id = kernel.scope_entity());
```

The kernel sets `app.scope_entity_id` for every class (`ScopeConnectionCustomizer`), so a FEDERATION_VIEW caller (scope entity: the Federation) and an EXTERNAL_TIMEBOXED caller (scope entity: its home entity) satisfy `own_read` and `own_write` for that entity's rows. Measured by the matrix test against 17A's text: an EXTERNAL caller granted entity C also reads its own entity A's rows, and every read-only class inserts rows owned by its scope entity.

19A §1's PARTY policy, `USING (kernel.scope_class() IN ('OWN','PARTY') AND (owner = scope_entity OR counterparty = scope_entity))`, has no location clause, so a shop-scoped user reads every document of the whole entity, and, since it admits OWN, it also undoes `own_read`'s location clause for the entity's own documents.

## Why it matters

The first is a write path for the two classes doc 18 makes read-only, on every table built so far. The second breaks M-05 (sibling shops) for every document table M4 will build. Both are invisible to the module tests, which run their commands as OWN.

## Proposed change

**17A §6.3 and 19A §1 follow doc 18.** The template in the repository (`backend/app/src/main/resources/db/migration/RLS_POLICY_TEMPLATE.md`) carries the corrected text and `RlsMatrixIntegrationTest` proves it:

```sql
CREATE POLICY own_read  ... USING (kernel.scope_class() = 'OWN' AND owner_entity_id = kernel.scope_entity() AND (... location ...));
CREATE POLICY own_write ... WITH CHECK (kernel.scope_class() = 'OWN' AND owner_entity_id = kernel.scope_entity());
CREATE POLICY party_read ... USING (kernel.scope_class() IN ('OWN','PARTY') AND ((owner ... AND (... location ...)) OR counterparty ...));
```

**Note (26 Sep 2026, from the review of K-01's close-out): the location clause applies on the owner's side only.** The first version of this request put it after the `OR`, on both sides. `location_id` is the owner's location, so a shop-scoped counterparty was compared with the seller's location and never saw the documents it is the buyer of. The corrected `party_read` above keeps a shop to its own documents (M-05) and lets a counterparty at any of its shops see the documents it is a side of; which of the counterparty's shops should see them needs a counterparty location column and is left to M4. The template carries the corrected text, and `RlsMatrixIntegrationTest` now runs location-scoped PARTY and OWN rows against it and against every real table: `kernel.document` still has the first version and is listed there with a TODO for K-07's owner.

**The 40 existing policies** are corrected by one migration per folder, `ALTER POLICY <name> ON <table> USING (kernel.scope_class() = 'OWN' AND (<the existing expression>))` and the same for `WITH CHECK`, by each folder's owner: hello's in the pull request that raises this; `kernel.audit_event` and `kernel.event_outbox` by K-04's and K-05's author, because their policies are also written by the partition functions (`ensure_audit_partitions`, `ensure_event_outbox_partitions`), which must be re-created with the class test; `m1party`, `m1security` and `m3pricing` by M1's and M3's developers. A module's RLS test then adds the two rows the matrix needs: a FEDERATION_VIEW caller cannot insert, an EXTERNAL caller reads only its grant.

## Impact if accepted

17A v0.2 and 19A v0.2 carry the corrected template. Five small migrations, no code change, the existing RLS tests extended by two cases each.
