# CR-19A-10 — `kernel.api.SyncStatus` is a kernel contract: a device's outbox state and whether it is drained

- **Status:** accepted
- **Date raised:** 2026-09-27
- **Raised by:** Claude Code session, the identity and permission decisions delegated by the architect (branch `feat/decisions-identity-permissions`); the contract was added from a module ticket by pull request #109 (M1-06) and asked for the platform pair's confirmation
- **Documents affected:** 19A §8 (the sync gateway: `device_sync_cursor`, `device_heartbeat`; the kernel services it publishes), 19A §1 (the kernel index: services and their `kernel.api` types), 21A §6.1 (AssignDeviceToPosition: "old device outbox drained (kernel SyncStatus.drained(oldDevice)) or loss recorded"), doc 21 flow 6.6
- **Code affected:** `kernel.api.SyncStatus` (`state(deviceId, ctx)`, `drained(deviceId)`, `DeviceSyncState`), `kernel.internal.sync.JdbcSyncStatus` (K-08, #114), callers `m1party.internal.device.AssignDeviceToPositionHandler` and `m1party.internal.location.SetPrimaryTillHandler`

Decided 27 Sep 2026: accepted (PR #144), on the architect's delegation. Reasons: 21A §6.1 already names the service and the call by the kernel's name, so the contract is the guide's and not an invention of the ticket; the answer it gives (every event the device emitted is applied and acknowledged at central) can only be given by the owner of `device_sync_cursor` and `device_heartbeat`, which 19A §8 makes the kernel's tables; and the safe default (not drained when central cannot tell, so the loss must be recorded and the series gap is documented, doc 21 flow 6.6) is the rule doc 32 needs from every caller, so it belongs in one place. The alternative, M1 reading the kernel's sync tables itself, breaks the schema rule (AGENTS.md: never read another owner's schema outside its `api`/`query`).

## What is wrong or missing

19A §8 describes the cursor and the heartbeat tables and the sync API, and 19A §1's index lists the kernel's services with their `kernel.api` types, but neither names a service through which a module asks "is this device drained?". 21A §6.1 calls one anyway, by name: `kernel SyncStatus.drained(oldDevice)`. M1-06 (#109) added `kernel.api.SyncStatus` with a stand-in that answered "not drained" for every device (so every replacement needed `outboxLossRecorded` until the gateway existed), and K-08 (#114) replaced the stand-in with `JdbcSyncStatus` over the real tables. The addition was made from a module ticket and never formally confirmed as a kernel contract.

## Why it matters

A counter transfer that ignores an undrained outbox hides a numbering gap (doc 21 flow 6.6: "series gap documented, never hidden"). Two modules already call the service (M1-05's SetPrimaryTill transfers the shop's counters too); M6 and the till track will read `DeviceSyncState.lastSeenAt` for fleet health. A contract two modules depend on is frozen by use (AGENTS.md), so it must be written down as one.

## Proposed change

- **19A §8:** add under the sync gateway's services: "`kernel.api.SyncStatus`: `Optional<DeviceSyncState> state(UUID deviceId, ScopeContext ctx)` (the last heartbeat, the application version, the highest applied sequence, the pending count the device last reported, the snapshot version it trades on; empty when the device never enrolled or the caller cannot see its entity) and `boolean drained(UUID deviceId)` (every event the device emitted is applied and acknowledged at central: its last heartbeat reported nothing pending, no batch of it is in flight, and it holds nothing acknowledged beyond what central holds; false also when central cannot tell). Read in the caller's transaction, under its scope. M1 asks `drained` before a position's counters move to another device (21A §6.1); the safe side of a transfer is to ask for the loss to be recorded."
- **19A §1:** the index row of the sync gateway names `SyncStatus` among its `kernel.api` types.
- **21A §6.1:** unchanged; the reference now resolves to a named kernel contract.

## Impact if accepted

19A §8 and §1 gain the text above at the next re-issue; no code changes (the contract and its implementation are on `main` since #109 and #114, with `DevicesPostgresIntegrationTest` and `HeartbeatConformanceIntegrationTest` proving it). From here a change to `SyncStatus` is a change request against 19A, as for every kernel contract a module depends on.
