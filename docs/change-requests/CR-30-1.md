# CR-30-1 — The till is one Kotlin Multiplatform application for Android, Windows and Linux, updated automatically from central

- **Status:** accepted (architect, 2026-09-28); the documents are not re-issued yet
- **Date raised:** 2026-09-28
- **Raised by:** Claude Code session, after the architect asked whether shops could run the till on Windows or Linux PCs, and required automatic updates from central on every OS
- **Documents affected:** 30 §4.1 (DR-1 and its comparison table) and the decision table; 26 and 26A (receipt printing, the sync contract's version field, the till's update flow); 17A §2 (the `till/` module list)
- **Code affected:** `till/` (module layout; `core`, `sync` and `peripherals` are already plain Kotlin/JVM and carry over); backend: a release registry and a release screen, a version field in the sync contract. Nothing built yet.

## What is wrong or missing

DR-1 decides "native Android (Kotlin, Compose) with a dedicated till track". Shops may already own Windows or Linux PCs, and an Android app cannot run on them: Microsoft ended the Windows Subsystem for Android on 5 March 2025. The design also leaves how a till is updated to each device's store or MDM, so central does not decide when a till takes a new version.

## Why it matters

Buying an Android terminal for every counter is a cost some societies will not carry when a PC is already there. Three separate till applications would implement receipt numbering, sessions, the Z-report and sync three times, which the design treats as fiscal truth. And a till that updates on a store's schedule can change version in the middle of a session.

## Proposed change

1. **DR-1, new text:** "The till is a Kotlin Multiplatform application with a Compose Multiplatform UI. Targets: Android (primary: integrated POS terminals such as Sunmi-class, and tablets) and a desktop JVM application packaged for Windows 10/11 64-bit and Linux 64-bit. Domain, sync, snapshot verification, persistence (SQLDelight over encrypted SQLite), receipt layout and all screens are shared (about 85–90% of the code). Per platform: device transports, secure key storage, the receipt rasteriser wrapper, kiosk integration, packaging and the last step of an update. The dedicated till track stays." The driver app stays Android only.
2. **Module layout in `till/`:** `core`, `sync`, `db`, `security`, `peripherals`, `peripherals-android`, `peripherals-jvm`, `render`, `ui`, `app` (Android), `desktop` (Windows and Linux). Business rules live in `commonMain` only; a platform difference is an interface implemented per platform, never branching inside business code.
3. **Receipts (doc 26):** Sinhala and Tamil are always printed as raster images (ESC/POS `GS v 0`), rendered on the till with the bundled Noto fonts and a shaping engine; printer code pages and text mode are never used for these scripts.
4. **Automatic updates from central, on every OS (doc 26, new section):**
   - Central publishes a release per platform. It is signed with a **release key** kept apart from the snapshot key. It carries a minimum version and rolls out in rings (pilot shops, then regions, then all), which central can pause or roll back.
   - The till learns its target version from the signed snapshot manifest. It downloads in the background with resumable ranges, and verifies the signature and hash before keeping the file.
   - It installs only at a safe point: no open session and no upload in progress.
   - It health-checks on first start and rolls back to the kept previous version on failure. A database migration takes a local backup first.
   - It reports its version on every sync.
   - Below the minimum version, central stops sending new snapshots, but **facts are always accepted**: a sale that happened is a fact.
   - Install per OS:
     - **Android:** a silent `PackageInstaller` install. This requires the device to be provisioned as a dedicated device with the till as device owner, or through an EMM or vendor MDM.
     - **Windows and Linux:** a small launcher, installed once by MSI or DEB/RPM, starts the newest verified app bundle from versioned folders. Each bundle includes its own jlink runtime. Updates need no admin rights and no one at the shop.
5. **Build:** one version number for all targets. CI builds Android and Linux on an Ubuntu runner and Windows on a Windows runner; jpackage cannot cross-build. Each artefact carries its platform signature (Android keystore, Authenticode, GPG) and our release signature, and CI uploads it to the release registry.
6. **Hardware floor:** PCs must be 64-bit with at least 4 GB RAM. Printers are 80 mm ESC/POS with a network or USB connection and raster support, from a supported-hardware list.

## Impact if accepted

- **Doc 30:** re-issued with the new DR-1 and comparison.
- **Doc 26 / 26A:** gain the update flow, the version field in the sync contract and the raster-receipt rule.
- **Doc 17A:** module list updated.
- **Till track, first step:** a desktop spike (sell → print → Z-report on a low-end Windows PC), about 2–3 developer-weeks, before the till screens are built. After it, roughly 20–30% more till effort than Android alone.
- **Backend:** a release registry, a release screen, and the version field in the sync contract. This is a small ticket, placed with M1 devices or kernel sync when it is planned.
- **Research behind this decision:** a comparison of Flutter, .NET MAUI/Avalonia, Tauri/Electron, PWA and separate native apps, with sources. It is kept with the handover notes outside the repository (`.handover/POS-TECH-STACK-RESEARCH.md`).

## Decision

**Accepted by the architect (Chamin), 2026-09-28:** "lets take this direction for pos system".
