# CR-19A-7 — Objects a module owns without a document: ObjectStorage, and job scopes for per-owner work

- **Status:** raised
- **Date raised:** 2026-09-27
- **Raised by:** Claude Code session, ticket M2-06 (branch `feat/m2-06-sku-images`)
- **Documents affected:** 19A §9 (attachments: "PresignService.put(documentId, attachmentId, contentType)"; the verifier "for PENDING rows"), 19A §12 (jobs and their scope); 22A §2 ("19A §9 attachments ... PresignService for image upload; object storage client"), §4 (ThumbnailJob), §6 (AttachImage: "insert PENDING; presign returned; on upload event: verify hash, ThumbnailJob, ACTIVE"); doc 18 (`document_attachment`, `sku_image`)
- **Code affected:** new `kernel.api.ObjectStorage` and `kernel.internal.attachment.ObjectStorageService`; `kernel.internal.attachment.ObjectStore` (read, put) and `S3ObjectStore`; `kernel.api.JobExecution` (two default methods); first user `m2catalogue.internal.image`

## What is wrong or missing

19A §9 gives one owner to an uploaded object: a document. `Attachments.presignUpload(documentId, ...)` writes `kernel.document_attachment`, whose policies, visibility and verifier all go through `document_id`, and `attachment.completed.v1` names the document. 22A §6 asks M2 to attach an image to a SKU through the same presign and "on upload event: verify hash, ThumbnailJob, ACTIVE", and doc 18 gives the image its own row, `catalogue.sku_image` (sku, barcode, owner, object keys, hash, status). A SKU is not a document, so an M2 image has no path through the kernel service as K-09 built it (the K-09 review said so).

Two smaller gaps follow. The thumbnail job must read the upload and write a thumbnail, and the kernel's store exposes neither to a module. And a job that settles rows of many entities (each image in the scope of the entity that attached it, so that the row's own policies admit the update) can obtain only the Federation's OWN scope from `JobExecution`; the kernel's own verifier uses `SystemScope.own(entity)` and `federationView()`, which are internal.

## Why it matters

Without a rule each module that stores a file invents one: a fake document per SKU (a document with no number, type or lifecycle, readable by whoever reads the document instead of by the catalogue's policies), or its own S3 client with its own limits and keys. Both split the one place 19A §9 meant to keep: the size and type limits (`attachment.max_bytes`, `attachment.content_types`), the key layout and the presign window.

## Proposed change

- **19A §9, a second entry point:** "A module that owns the row of an object itself (M2's `sku_image`, whose owner is a SKU) uses `ObjectStorage`: `presignPut(objectKey, contentType, contentLength, ctx)` under the register's attachment limits, `verify(objectKey, expectedHash, ctx)` (MISSING, TOO_LARGE, HASH_MISMATCH, VERIFIED), a bounded `read`, a `write` for what it derives, and `presignGet`. The key is `objects/{module}/{entity}/{objectId}` (`ObjectStorage.keyOf`), a derived object's key that plus one segment; asking again for a key renews its URL. The kernel keeps no row and audits nothing: the module's command handlers do, and the module keeps the K-09 rules on its own row (settle only after the presign window, never change a settled row)."
- **19A §9, the verifier hook:** "For a module-owned object the module's job is the verifier: it asks `ObjectStorage.verify` after the window and settles its row through a command handler."
- **19A §12:** "`JobExecution.ownScopeOf(entity)` is the OWN scope of any entity, without a user, for a job that settles each row in its owner's name; `JobExecution.federationView()` is the read-only view over every entity's rows, for the job's scan."
- **22A §6, AttachImage:** read "presign returned" as `ObjectStorage.presignPut`, and "on upload event" as the ThumbnailJob's verification after the URL has expired.

## Impact if accepted

19A gains the paragraphs above; 22A §6 the reading. The code is already written this way in M2-06 (built to this proposal): the kernel additions are additive (a new interface, two default methods, two methods on an internal interface), `Attachments` and `document_attachment` are unchanged, and no kernel migration was needed. If the architect decides instead that images become document attachments, `document_attachment` needs a non-document owner (nullable `document_id`, an owner subject and entity, policies on the entity), the verifier's scan and `attachment.completed.v1` change with it, and M2's `AttachImageHandler`, `SettleImageHandler` and `ThumbnailJob` move onto them; `sku_image` and its policies stay.
