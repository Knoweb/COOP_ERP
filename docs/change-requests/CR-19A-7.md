# CR-19A-7 — Objects a module owns without a document: ObjectStorage with a kernel upload ledger, and job scopes for per-owner work

- **Status:** accepted as revised (27 September 2026, on the architect's delegation); applied in the repository; 19A and 22A not re-issued yet
- **Date raised:** 2026-09-27
- **Raised by:** Claude Code session, ticket M2-06 (branch `feat/m2-06-sku-images`, #137); revised on branch `fix/cr-19a-7-object-ledger`
- **Decided 27 Sep 2026:** accepted as revised in PR #139, on the architect's delegation.
- **Documents affected:** 19A §9 (attachments: "PresignService.put(documentId, attachmentId, contentType)"; the verifier "for PENDING rows"), 19A §12 (jobs and their scope); 22A §2 ("19A §9 attachments ... PresignService for image upload; object storage client"), §4 (ThumbnailJob), §6 (AttachImage: "insert PENDING; presign returned; on upload event: verify hash, ThumbnailJob, ACTIVE"); doc 18 (`document_attachment`, `sku_image`; a new kernel table `object_upload`)
- **Code affected:** `kernel.api.ObjectStorage`, `kernel.internal.attachment.ObjectStorageService`, `ObjectStore` (read, put) and `S3ObjectStore`; `kernel.internal.job.SystemScope.inOwnTransaction`; `kernel.api.JobExecution` (two default methods); kernel migration `V0060__object_upload.sql`; `ArchitectureTests.onlyScheduledJobsTakeAnEntitysScope`; first user `m2catalogue.internal.image`

## What is wrong or missing

19A §9 gives one owner to an uploaded object: a document. `Attachments.presignUpload(documentId, ...)` writes `kernel.document_attachment`, whose policies, visibility and verifier all go through `document_id`, and `attachment.completed.v1` names the document. 22A §6 asks M2 to attach an image to a SKU through the same presign and "on upload event: verify hash, ThumbnailJob, ACTIVE", and doc 18 gives the image its own row, `catalogue.sku_image` (sku, barcode, owner, object keys, hash, status). A SKU is not a document, so an M2 image has no path through the kernel service as K-09 built it.

Two smaller gaps follow. The thumbnail job must read the upload and write a thumbnail, and the kernel's store exposed neither to a module. And a job that settles rows of many entities (each image in the scope of the entity that attached it, so that the row's own policies admit the update) could obtain only the Federation's OWN scope from `JobExecution`.

The first version of this request (built in #137) answered with a stateless `ObjectStorage`: the kernel kept no row and each module kept the K-09 rules on its own row. A review of #137 found what that leaves open:

- `presignPut` checked no state, so a key whose object had been verified could get a new PUT URL and its bytes be replaced after the hash was checked (overwrite after settle);
- `write` took no scope and no size or type limit, and accepted the base key, so a module could overwrite the verified original itself;
- the module segment of `objects/{module}/{entity}/{id}` was any lower-case word, not tied to the caller, and the entity in the key was never compared with the caller's scope; `read` and `presignGet` took no scope either;
- "settle only after the presign window" was M2's guard alone, so the next module to use `ObjectStorage` would have to remember it;
- `JobExecution.ownScopeOf(any entity)` gives any module's `@ScheduledJob` a user-less OWN scope of any entity.

## Why it matters

Without a rule each module that stores a file invents one: a fake document per SKU (a document with no number, type or lifecycle, readable by whoever reads the document instead of by the catalogue's policies), or its own S3 client with its own limits and keys. And without state in the kernel, the K-09 rules (size and type limits, settle only after the presign window, a settled row never changes, no new URL after settle) hold only where each module remembers to keep them.

## Decision (27 September 2026, on the architect's delegation)

Keep `kernel.api.ObjectStorage` and M2's `catalogue.sku_image` business row, and add a kernel upload ledger so that the K-09 rules are enforced once, in the kernel, for every module.

Rejected: generalising `document_attachment` to a non-document owner (it bends the document policies, and the SHARED visibility of a Federation SKU's image does not fit an owner-or-counterparty table); making images documents (a document with no number, type or lifecycle).

## The change, as applied

- **19A §9, a second entry point:** "A module that owns the business row of an object itself (M2's `sku_image`, whose owner is a SKU) uses `ObjectStorage`. The key is `objects/{module}/{entity}/{objectId}`, built by `ObjectStorage.keyOf(anchor, entity, objectId)`, where the module is the package of the anchor class and the anchor must belong to the calling module; an object derived from it (a thumbnail) takes that key plus one segment. Every method refuses a key of another module than the calling class's. The kernel keeps one row per object in `kernel.object_upload` (owner module, owner entity, type, length, announced hash, PENDING/VERIFIED/FAILED, the failure, `upload_expires_at`, `created_at`, `settled_at`; the RLS template on `owner_entity_id`; only a PENDING row changes, forward only):
  - `presignPut(key, contentType, contentLength, sha256Hex, ctx)`: an OWN scope of the key's entity; the register's `attachment.content_types` and `attachment.max_bytes`; records the row PENDING in the caller's transaction, or renews the window of a PENDING row of the same type; refused with `object.not_pending` once the row is settled.
  - `verify(key, ctx)`: an OWN scope of the key's entity; `PENDING` while the PUT URL is valid; then VERIFIED, or FAILED as TOO_LARGE (before reading), HASH_MISMATCH (against the announced hash) or MISSING (only after the upload window); audited `OBJECT_VERIFIED` or `OBJECT_FAILED`; settled once, and a settled row answers what it settled with.
  - `write(derivedKey, contentType, bytes, ctx)`: only a derived key of a VERIFIED object (`object.not_derived` for the original), an OWN scope of its entity, under the same type and size limits.
  - `read(key, ctx)`: the object or a derivation of it, the base VERIFIED, the key's entity in scope (OWN or PARTY of it, the federation view, an external grant naming it), at most `attachment.max_bytes`.
  - `presignGet(key, contentType, ctx)`: the base VERIFIED; any scope with a class (not NONE). Who may see an image is the module's decision, not the ledger's: a SHARED SKU's image is shown wherever the SKU is visible, which the ledger's entity policies cannot know, so the module passes only a key it has itself read under its own row-level security."
- **19A §9, the verifier hook:** "For a module-owned object the module's job is the verifier: it asks `ObjectStorage.verify` (which settles the kernel's ledger row) and settles its own row through a command handler; `PENDING` means ask again later."
- **19A §12:** "`JobExecution.ownScopeOf(entity)` is the OWN scope of any entity, without a user, for a job that settles each row in its owner's name; `JobExecution.federationView()` is the read-only view over every entity's rows, for the job's scan. Only a `@ScheduledJob` method may call `ownScopeOf` (enforced by ArchUnit), and only with the owner of a row its own module read (a review rule)."
- **22A §6, AttachImage:** read "presign returned" as `ObjectStorage.presignPut` with the announced hash, and "on upload event" as the ThumbnailJob's `ObjectStorage.verify` after the URL has expired.

## Why `ownScopeOf` is kept and not narrowed

Narrowing it to "entities the job's own module reads from its own tables" would need the kernel to know where the job found the entity, which it cannot: the entity is a value the job passes. The alternatives (a kernel-side scan per module, or the kernel settling module rows) move module logic into the kernel. So the method stays, and the risk is written on it: a `@ScheduledJob` could act as any entity. What the build holds is that nothing but a `@ScheduledJob` method calls it (`ArchitectureTests.onlyScheduledJobsTakeAnEntitysScope`, with a fixture in `ArchitectureRulesBiteTest`), so no handler, controller, consumer or helper can borrow another entity's scope through it; that the job passes only the owner of a row its own module read is a review rule, documented on the method. The kernel's own ledger does not rely on it: verify, write and read compare the key's entity with the scope on every call.

## How the anchor is held

`keyOf(Class<?> anchor, ...)` refuses an anchor of another module than the class that calls it, and every `ObjectStorage` method refuses a key whose module is not the calling class's (the kernel walks the stack to the first class outside the service). A key typed by hand for another module is refused as well, so no separate review rule is needed for it.

## Impact

19A gains the paragraphs above and one kernel table; 22A §6 the reading; doc 18 the table `kernel.object_upload`. `Attachments` and `document_attachment` are unchanged. The M2 code changed with it: AttachImage anchors the key on its own class and passes the hash; the ThumbnailJob treats `PENDING` as not yet and fails an image whose upload the kernel settled as missing; SettleImage keeps its own window guard (defence in depth; the ledger enforces it too).
