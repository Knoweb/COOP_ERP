# CR-32-2 — Sync contract: an attachment's upload window is not renewed after it ends; the till attaches a replacement, and a decision waits only on the live attachments

- **Status:** accepted (13 October 2026, on the architect's delegation; wave 4 code review); the document is not re-issued yet
- **Date raised:** 2026-10-13
- **Raised by:** Claude Code session, wave 4 code review decisions (the wave 3 deviation `docs/progress/deviations/2026-10-09-wave3-kernel-small-review-findings.md` item (1), KRN-16), recorded in `docs/progress/deviations/2026-10-13-wave4-kernel-floor-alert-and-config-location.md`
- **Documents affected:** doc 32 §4 (Attachments: "uploads directly to object storage, resumable in byte ranges" and "A write-off approval requires all its attachments COMPLETE"); 19A §9 (Presign) as CR-19A-8 already words it
- **Code affected:** none new. `kernel.internal.attachment.AttachmentService.presignUpload` (renewal refused after the window, `attachment.upload_expired`, since wave 3 KRN-16), `AttachmentVerifier` (a row whose object never came is FAILED), `m5inventory.internal.writeoff.WitnessWriteOffHandler` (a FAILED photograph does not hold the write-off, since wave 2 M5-11); the test `AttachmentsPostgresIntegrationTest.aTillBackAfterTheWindowAttachesAReplacementAndTheOldOneFails` proves the recovery path

## What is wrong or missing

Doc 32 §4 says the till "uploads directly to object storage, resumable in byte ranges", which read as: a till that lost its connection asks again for the same attachment whenever it comes back. Since wave 3 (KRN-16) asking again for the same attachment after its upload window has ended is refused (`attachment.upload_expired`): the verifier settles a row only after its URL has expired, and a renewed URL would let the bytes be replaced after the hash was checked. The document does not say what the till does instead. It also says "A write-off approval requires all its attachments COMPLETE", which, read literally, holds a write-off for ever once one upload has FAILED, since a FAILED row never becomes COMPLETE.

## Why it matters

KRN-16 is a data-integrity rule: a photograph verified as evidence must be the photograph stored. The recovery path for a till that comes back late has to be written down, or the next reader of §4 re-opens the renewal. A decision that waits on an attachment that can never complete blocks a write-off that has other, complete evidence.

## Proposed change

**Doc 32 §4, Path**, replacing "resumable in byte ranges": "uploads directly to object storage with a pre-signed PUT that lasts the register's `attachment.upload_url_minutes` (default 15). Inside that window the till may ask again for the same attachment id and receives a fresh URL. After it the URL is not renewed: the till requests a new attachment (a new attachment id) for the same document and uploads the photograph again. The verifier marks the old attachment FAILED once its object has not arrived (a REVIEW record), and its file, if any, is removed after `attachment.failed_retention_days`."

**Doc 32 §4, Limits**, replacing "A write-off approval requires all its attachments COMPLETE": "A decision that needs the evidence waits only on the live attachments, those not FAILED: a PENDING one holds it, a FAILED one does not, and where a photograph is required at least one must be COMPLETE."

Why the window is kept and not lengthened:

1. **KRN-16** (wave 3): the row settles only after its URL has expired, so the hash the verifier checks is the hash of the bytes that stay; a renewal after the window would reopen the swap.
2. **CR-19A-8** (27 September 2026): the window is configuration (`attachment.upload_url_minutes`, FEDERATION, 1 to 60, default 15) and so is the verifier's schedule; a federation that needs longer sets it, no code change.
3. **Fifteen minutes is ample** for what §4 sends: images downscaled on the device to about 300 KB, which a slow mobile link moves in well under a minute. A till offline for longer than the window simply requests a new attachment on reconnection, which costs one more small upload.

## Impact if accepted

- **Documents**: 32 re-issued (§4, Path and Limits). 19A §9 as CR-19A-8 already words it.
- **Code**: none; the rule is what the code does. The test above proves that a renewal after the window is refused, that a new attachment id on the same document is accepted, and that the verifier fails the old row and completes the replacement. `WriteOffPostgresIntegrationTest.aFailedUploadDoesNotHoldTheWitnessForEverWhileAnotherPhotographIsThere` proves that the write-off is witnessed with one COMPLETE and one FAILED photograph; `ApproveWriteOffHandler` reads no attachment status.
- **Noted, not changed**: a never-arrived object is failed by the verifier only `coop-erp.object-store.upload-window-hours` (24) after it was captured, so a write-off whose old photograph is still PENDING waits that long even with a COMPLETE replacement. M4's claim decision (doc 24 §4.5, `ClaimGuards.requireEvidenceComplete`) still requires every photograph COMPLETE, so a FAILED claim photograph blocks the decision; both are for their own change.
- **Rejected**: renewing an expired upload URL (KRN-16); a longer default window (it delays every decision that waits on evidence, CR-19A-8 point 2).
