## What is wrong or missing

The seller's delivery note names, on each drop, the buyer's location the goods go to (`shipToLocationId`), and the buyer's goods received note can only be captured at that location (M4-05). 24A has the seller choose it and M1 check that it "belongs to the bill-to". Row-level security lets only the owner read its locations (`party.location`, `own_read`; M1 publishes no counterparty read of them), so the seller has no way to list or name the buyer's receiving places, and the delivery note screen could not be filled in. M4-04 already recorded that the ship-to is not checked at the note for the same reason.

## Options considered

1. M1 publishes a counterparty read of an entity's ACTIVE receiving locations (id, code, names) to the entities it trades with, like `party.entity_party_directory` for names. Right in the long run; it is another module's schema and policy, outside this lane.
2. A security-definer function in M4 reading `party.location`: crosses into another module's schema (AGENTS.md), rejected.
3. The buyer, who can read its own locations, names the delivery location on the order; the seller's delivery note takes each drop's ship-to from the order. Additive, M4's own table, and the natural place: the buyer knows where it wants the goods.

## Decision

Decided 27 Sep 2026: accepted, option 3, on the architect's delegation.

- `trading.doc_order.deliver_to_location_id uuid` (nullable; `m4trading/V0002`). `CreateOrderRequest.deliverToLocationId` (optional) and `OrderResponse.deliverToLocationId`.
- CreateOrder guard, after the ETA: a named location must be one of the buyer's own (M1 `getLocation` in the buyer's scope, owner = buyer), else `m4.order.deliver_to_unknown`. It goes into the ORDER_CREATED audit record. The `order.created.v1` payload is unchanged.
- The delivery note screen fills the drop's ship-to and bill-to from the order; the server keeps the existing CreateDeliveryNote contract.

Option 1 remains the better long-term answer for a note with several buyers or a buyer that changes its mind: it is listed in `docs/PLAN_TO_M2.md`, "Deferred after the demo" (M4-11). 24A sections 3, 5, 6 and 8 are to be re-issued with this change.

## Revision, 28 September 2026

Decided 28 Sep 2026: accepted as revised, the order keeps a snapshot of its delivery point (branch `fix/demo-display-polish`), on the architect's delegation.

**What the demo showed.** The seller's order card and delivery note showed the delivery location as a short id ("000111"), and the web client's read of it was refused (404) in the browser console, because the seller still cannot read the buyer's location, which is why this change request exists. An id is no use to a stores clerk loading a lorry.

**Options considered.**

1. M1 exposes a minimal "delivery point" read to the counterparty (code, names, address of an ACTIVE location, through a directory table like `party.entity_party_directory`). It covers every screen at once, but it shows a trading partner every location of the buyer, not only the one the buyer chose, and adds a table, a trigger and a policy to M1 for a display need.
2. The order carries a snapshot of the delivery point: the location's code, its names in the three languages and its address, copied in the buyer's session when the order is drafted (CreateOrder already reads the location there to check it). The seller reads it with the order. A snapshot is what a trading document should hold anyway: the place the order was placed for, which a later rename does not rewrite.

**Decision: option 2.** It reveals only what the buyer named, on a document both parties already read; it lives in M4's own table (additive columns on `trading.doc_order`, insert-only as before); and it is cheap to reverse, or to complete with option 1 later. Built:

- `m4trading/V0004__order_deliver_to_snapshot.sql`: `deliver_to_code`, `deliver_to_name_en`, `deliver_to_name_si`, `deliver_to_name_ta`, `deliver_to_address`, written once by `CreateOrderHandler`. An order drafted before has none, and shows a dash to the seller.
- `OrderView.deliverTo` (`OrderView.DeliveryPoint`) and `OrderResponse.deliverTo` (`DeliveryPointResponse`: `code` and `nameEn` required; `nameSi`, `nameTa`, `address`), additive.
- The web client names a counterparty's location only from that snapshot (the order card; a delivery note's drop, through the drop's order; the seller's view of a GRN, through its drop's order) and never asks M1 for it.

Option 1 stays in `docs/PLAN_TO_M2.md` ("Deferred after the demo", M4-11); the buyer still does not see the seller's dispatch warehouse by name (a dash on the delivery note).
