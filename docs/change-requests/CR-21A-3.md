# CR-21A-3 — Which security rows M1 may delete: `user_role` alone, or `role_permission` and `sod_pair` as well

- **Status:** raised
- **Date raised:** 2026-09-26
- **Raised by:** Claude Code session, from the code review of 25 September of the M1-08 pull request (roles, assignments and separation-of-duties pairs), finding on `m1security/V0010` line 25
- **Documents affected:** 21A §6 (the handler table: RevokeRole, AmendRole, RemoveSodPair), 17A §6.2 (the grants of `app_rw`), 18 Part F (the security schema register: which tables are current facts and which are history)
- **Code affected:** `db/migration/m1security/V0010__roles_assignments_and_sod_pairs.sql` (`GRANT DELETE ON security.user_role, security.role_permission, security.sod_pair TO app_rw` and the three `own_delete` policies); `AmendRoleHandler` (deletes `role_permission` rows the amendment drops); `RemoveSodPairHandler` (deletes the entity's own `sod_pair` row); `SchemaRulesIntegrationTest` (`DELETE_BY_DESIGN` names the three tables)

## What is wrong or missing

21A §6 calls RevokeRole "insert / delete user_role (the one DELETE M1 performs; audited)": one table. 17A says `app_rw` has no DELETE on any table (AGENTS.md repeats it: "Never `UPDATE` or `DELETE` a document, line, stock movement, account posting, outbox or audit row. The `app_rw` role has no such grant; do not add one"). M1-08 needed two more removals, "insert / replace role_permission set" (AmendRole) and an entity taking back a pair it added itself (RemoveSodPair, which 21A does not list), and settled them locally: V0010 grants DELETE on three tables and the schema test's list of tables that may be deleted from was widened to match, with the reasoning written in the migration's header ("none of the three is a document, a ledger or an audit row; each is a current fact whose history is the audit trail").

The reasoning may well be right. It is not the developer's to decide alone: 21A names one table, 17A names none, and the next module will point at the precedent ("M1 deletes three, so we may delete ours").

## Why it matters

- The removed rows' only record is the JSON in the audit log. An amended role's earlier permission set, or a pair an entity once had, can be reconstructed only by reading audit records, which no query of 21A §7 does.
- Doc 18's rule "ledgers are insert-only, documents immutable, current facts may change" needs a stated home for `role_permission` and `sod_pair`: are they current facts (a status column or a replace is fine) or history (a row per version)? Until it is stated, each module answers for itself.
- `SchemaRulesIntegrationTest.DELETE_BY_DESIGN` is the build's enforcement of 17A's rule; each table added to it weakens the rule by one table with no document saying so.

## Proposed change

One of two, for the architect to choose:

1. **Keep the three deletes and say so.** 21A §6 re-issued: AmendRole "replaces the permission set (delete and insert `role_permission`, audited with before and after)"; RemoveSodPair added to the table ("an entity removes a pair it added itself; a federation default is never removed"); RevokeRole's "the one DELETE" becomes "one of the three DELETEs M1 performs". 17A §6.2 states the rule as "no DELETE on documents, lines, ledgers, outbox or audit; a current-fact table may be granted DELETE when its implementation guide names the command that performs it, audited with the row's state". 18 Part F marks `user_role`, `role_permission` and `sod_pair` as current facts.

2. **Keep DELETE on `user_role` alone and model the other two as status changes.** AmendRole marks a dropped `role_permission` row `removed_at` (or writes a new `role_permission_set` row per version and the resolver reads the latest); RemoveSodPair sets `sod_pair.status = 'REMOVED'` and every reader of pairs filters on ACTIVE. 21A §3.2 gains the columns; V0010's grant is narrowed by a new migration (`REVOKE DELETE ON security.role_permission, security.sod_pair FROM app_rw`) and the two `own_delete` policies dropped.

Option 1 is the smaller change and matches what is on `main`; option 2 matches 17A as written and keeps a row per fact that ever was.

## Impact if accepted

- Option 1: 21A re-issued (§6), 17A re-issued (§6.2), 18 re-issued (Part F); no code change; `SchemaRulesIntegrationTest` stays as it is.
- Option 2: 21A re-issued (§3.2, §6); a new m1security migration (columns, revoke, policies); `AmendRoleHandler`, `RemoveSodPairHandler`, `SecurityRecords` (readers filter on status), `JdbcPermissionResolver` (reads only live permission rows) change; `SchemaRulesIntegrationTest.DELETE_BY_DESIGN` narrows to `user_role`; the M1-08 tests that count `role_permission` and `sod_pair` rows change.

Nothing is applied until the status is **accepted**; V0010 stays as merged meanwhile (a merged migration is never edited).
