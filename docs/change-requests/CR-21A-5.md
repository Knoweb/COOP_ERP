# CR-21A-5 — Two M1 rules the documents state otherwise or not at all: BulkRegister is all or none, and a till position may be registered at a shop in any status

- **Status:** accepted
- **Date raised:** 2026-09-27
- **Raised by:** Claude Code session, the M1 decisions of 27 September 2026 (branch `feat/decisions-m1-rules`), from PR #90 (M1-11) and the review fixes of PR #128
- **Documents affected:** 21A §6 (the handler table: BulkRegister, RegisterTillPosition); doc 21 §5.1 (BulkRegister: "Validated staging; commit per row; validation report") and §6.1 (the failure path of the onboarding flow)
- **Code affected:** none changed; `m1party/internal/bulk/BulkRegisterEntitiesHandler` and `m1party/internal/location/RegisterTillPositionHandler` are confirmed as built and their documentation cites this file; `LocationsPostgresIntegrationTest.aPositionIsRegisteredAtAShopInAnyStatus` is new

Decided 27 Sep 2026: both rules are kept as built (PR #143), on the architect's delegation.

## What is wrong or missing

1. **BulkRegister.** Doc 21 §5.1 gives BulkRegister "Validated staging; commit per row; validation report", and 21A §6 "each valid row through its command handler in its own transaction; report collects outcomes": the valid rows of a file are registered and the invalid ones reported. M1-11 (#90) built all or none: every row is validated first, and when any row fails nothing is registered and the report names every failing row by line and column; when all pass, all are registered in one transaction, each with its audit record and its `entity.registered.v1`.
2. **RegisterTillPosition.** 21A §6 gives the guard "location SHOP; position_no unique" and says nothing of the shop's status (PLANNED, ONBOARDING, ACTIVE, DORMANT). The handler registers a position at a shop in any status; the review of 26 September (#128) asked whether PLANNED and DORMANT should be refused.

## Why it matters

1. A partial commit of a file of legal entities cannot be taken back (an entity is never deleted, only suspended), and the operator must then work out which rows went in and send a file of the others; a whole file sent again would report every registered row as a duplicate. And "each row in its own transaction" is not buildable within the rules the build enforces: a command handler is one `@Transactional` method and never calls another (the kernel's interceptor claims the request's idempotency key around each), so per-row transactions would need an orchestrator outside the handler model, for one screen.
2. Refusing PLANNED would break onboarding: doc 21 flow 6.1 registers "locations PLANNED, positions, staged devices", and ActivateLocation needs a primary till, which is a position. Refusing DORMANT would force a shop to reactivate before the lane it needs to reopen with exists.

## Decision

1. **BulkRegister stays all or none.** Doc 21 §6.1's failure path is met ("Validation report lists rejected rows (duplicate codes, missing VAT no, invalid district); nothing partial commits per row"): the report lists every rejected row before anything is written, and no row, nor any part of a failing file, commits. The corrected file is sent again whole. 21A §6 and doc 21 §5.1 are re-issued with: "validate every row first; if any row fails, register none and answer the report; otherwise register every row in one transaction, one audit record and one event per row". The row limit stays the configuration item `m1.bulk.max_rows`. Reasons: reversible (nothing to undo after a bad file), simpler for the operator and for the team (one transaction, one handler), and within the handler rules the build enforces; the performance target of 21A §11 (40 shops in 60 s) is met in one transaction.
2. **A till position may be registered at a shop in any status.** 21A §6's guard is complete as written ("location SHOP"); the handler gains no status guard. Reasons: PLANNED and ONBOARDING are required by the onboarding flow; DORMANT is harmless (a position only gets its series, and no device trades at a dormant shop until it reactivates through the connectivity gate) and useful; a future CLOSED status, if doc 21 ever adds one, will need its own rule. 21A §6 is re-issued with "at a SHOP in any status".

## Impact

21A re-issued (§6, two rows) and doc 21 (§5.1, one cell). No code change; the handlers' documentation cites this file, and a test proves a position registers at a shop in each of the four statuses.
