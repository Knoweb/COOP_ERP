# DEMO_SETUP.md — setting up and releasing the demo on a server

For whoever installs the cooperative-staff demo on a server that other people reach over the network: not a developer's own laptop. Assumes you know Linux and Docker, not this project. `docs/DEMO.md` is the demo's storyline and screens; this document is the server side: sizing, secrets, the sign-in server, install and reset, and a release checklist.

There is no ready-made deployment definition yet: `infra/deploy/` is empty (only `.gitkeep`). Doc 14 and doc 35 are where a real production deployment is designed; until then, the closest thing to a demo-server setup is `infra/compose/` (the local development stack) run with the changes this document lists. Everything here is "to confirm" against doc 35 once it exists.

## 1. What the demo is

`docs/DEMO.md` is authoritative; read it first. In short: Sri Lankan cooperative retail data (the Federation, two distributors, three multi-purpose cooperative societies, four shops, forty everyday goods in English, Sinhala and Tamil), loaded by `make demo-data` through the real command handlers (so every row carries its audit record, event, document number and stock movement, as if a person had clicked it). Phase 1 of the storyline is steps 1–3 (catalogue, price list, opening stock — already loaded) followed live by steps 4–9 (the Federation sells to a distributor: order, accept, delivery note, dispatch, GRN, invoice). A named demo user signs in for each step; the full cast and their jobs are in `docs/DEMO.md`, "Who is who".

M4 (trading documents) is on `main` as of this writing (PRs #156, #157, #161, #163, #164, #165), but `DemoDataLoader` itself does not create trading documents — steps 4–9 are still done live, not pre-loaded. **To confirm:** check `docs/DEMO.md`'s "Still to come" section against the branch you release from; if trading documents have since been added to the loader, the storyline in section 1 of this document may be stale.

## 2. Server requirements

Sizing is a sum of the compose services in `infra/compose/compose.yml`, not a measured figure — **to confirm** with a real run before a production-sized commitment.

**CPU.** At least 4 vCPUs. PostgreSQL, Keycloak (a JVM), the backend/worker (a JVM that also runs headless Chromium for PDF rendering), RabbitMQ and MinIO are all running at once; the backend and Keycloak are the two that matter for latency once the demo is up. 2 vCPUs will start the stack but PDF rendering (invoices, delivery notes) and Keycloak's first token issuance will be slow.

**Memory.** At least 8 GB, 12 GB more comfortable. Rough per-service floors: PostgreSQL ~512 MB–1 GB, Keycloak (JVM) ~512 MB–1 GB, the backend+worker JVM ~1–2 GB heap plus a Chromium process per PDF render (headless Chromium alone is commonly 200–400 MB resident), RabbitMQ ~256 MB, MinIO ~256 MB, Mailpit and PgBouncer negligible. **To confirm** with `docker stats` under load; nothing in the repository sets JVM heap limits explicitly (`-Xmx` is not set in the Jib image config found), so the JVMs use the container's memory as their default heap ceiling — give Docker enough that a default heap does not starve PostgreSQL and Keycloak.

**Disk.** The worker image is Debian trixie-slim plus the JRE plus `chromium` and `ca-certificates` (`infra/worker-image/Dockerfile`); the ticket brief cites it at about 1.6 GB (K-06b, PR #161). Add the plain backend image, `postgres:16`, `quay.io/keycloak/keycloak:26.8.0`, `rabbitmq:3.13-management`, the two Bitnami legacy MinIO images, `axllent/mailpit`, `edoburu/pgbouncer` and (if you keep the containerised Vite dev server) `node:24-alpine` with its installed `node_modules`. Budget at least 10–15 GB for images alone, plus room to grow for the PostgreSQL data volume, RabbitMQ's volume and MinIO's object store (the demo's data itself is small — forty SKUs, a handful of documents — but leave headroom for repeated `make reset && make up && make demo-data` cycles during a release, and for backups taken locally before they are moved off-box). 30 GB free is a reasonable floor for a small demo server; more if you plan to keep multiple backups on the box.

**Ports.** From `infra/compose/compose.yml`, the published host ports are: PostgreSQL 5434 (and PgBouncer 6432), RabbitMQ 5672/15672, MinIO 9000/9001, Keycloak 8085, Mailpit 1025/8025, the backend 8080, the web client 5173. **None of these should be reachable from the public internet directly.** Only two need to be reachable by the demo's users at all: the web client's origin (what a browser loads) and the backend API origin (what the browser's browser JS calls) — and in a real server setup you put a reverse proxy (nginx, Caddy, Traefik) in front of both and expose only the proxy's 443. Everything else (PostgreSQL, PgBouncer, RabbitMQ, MinIO, Keycloak's own 8085, Mailpit) stays bound to the Docker network or to `127.0.0.1`, reachable only over SSH tunnel for administration. Keycloak in particular must sit behind the same TLS-terminating proxy as the web/API origins, because the browser and the backend must agree on one public issuer URL (section 4 below) — Keycloak cannot be left on a bare `http://host:8085`.

**Domain and TLS.** You need at least one DNS name pointed at the server (a wildcard or two subdomains works well: e.g. `demo.example.org` for the web client and API, `auth.demo.example.org` for Keycloak, or path-based routing through one nginx if you prefer one hostname). Terminate TLS at the reverse proxy in front of everything — compose's own services speak plain HTTP to each other inside the Docker network, which is fine, but nothing in this repository terminates TLS for you, and a production sign-in issuer must be `https://`, not `http://` (see section 4: the code refuses a non-development issuer to run without its secrets set, and Keycloak realm configuration expects a real HTTPS front for browser redirects). Nginx or Caddy in front of the web port and the backend port, with a certificate from Let's Encrypt or your own CA, is the straightforward option; `infra/compose/compose.two.yml`'s `nginx-two.conf` is a *load-balancing* nginx between two backend instances behind the app's own port — it is not TLS termination and is a separate concern from the internet-facing proxy.

## 3. Settings that have no development default

The application code is deliberately strict: several settings default to an **empty string** in `application.yml`, and the code that reads them checks the sign-in issuer (`coop-erp.security.oidc.issuer`) with `JwtClaimsMapper.isDevelopmentIssuer` (`backend/app/src/main/java/lk/coopfed/knoweb/kernel/internal/security/JwtClaimsMapper.java`) — an issuer whose host is `localhost`, `127.0.0.1`, `[::1]`, or ends in `.localhost` or `.test`. Against a development issuer, an unset secret is filled in with a fixed, published development value and a warning is logged. Against any other issuer (which a demo server's issuer must be, once it has a real domain — see section 4), the same code **refuses to start** and throws `IllegalStateException` naming the property. This is your checklist of what must be set before the demo goes on a server; it is enforced, not a suggestion.

For every item below: put it in an **env file outside the repository** (e.g. `/etc/coop-erp/demo.env`, owned by root or the deploy user, mode 600) and reference it from your compose invocation with `--env-file`, or export the variables in the systemd unit / process supervisor that starts compose. **Never commit it** — `infra/compose/.env` is already git-ignored for the same reason, but a demo server should keep its real secrets entirely outside the repository checkout, in case the checkout itself is ever copied or shared.

Two more settings are **not** required for the demo but are worth knowing about if the same box is later used for anything beyond the current storyline:

- `SYNC_SIGNING_PRIVATE_KEY` / `SYNC_SIGNING_PUBLIC_KEY` (K-08, till sync signing, Ed25519 PKCS#8/X.509 base64): empty on a developer machine, each instance then generates its own key pair and logs that it did so (`TillSigner`). The demo's storyline has no enrolled till device (`docs/DEMO.md`: "The till is not part of phase 1"), so this is not on the checklist above — but if you ever demo the till, generate and fix these the same way as the other keys, because a self-generated per-instance key would make a restarted backend unable to verify what it signed before.
- `COOP_ERP_ENFORCE_PERMISSIONS` defaults to `false` in `application.yml` but is set to `true` in `infra/compose/compose.yml`'s backend service already — keep it `true` on the demo server; it is what makes the narrow "Demo: ..." roles in `docs/DEMO.md` actually bite.

## 4. The sign-in server for a demo

`infra/compose/realm-dev.json` is written for laptops, not for a server other people reach. Two things in it must change:

1. **`directAccessGrantsEnabled: true`** on the `coop-erp-web` client (`realm-dev.json`, the client whose `redirectUris` is `["http://localhost:5173/*"]`) — this is the OAuth2 **password grant**, which lets a caller trade a username and password directly for a token with no browser redirect at all. It exists so `tools/smoke.mjs` and the identity integration tests can sign in without driving a browser. It has nothing to do with how the demo's own users sign in (they go through the browser's redirect flow) but it is a live way to obtain a token for *any* demo user with nothing but their password, from any host that can reach Keycloak's token endpoint. **Turn it off** for the server realm: set `"directAccessGrantsEnabled": false` on `coop-erp-web`, matching the admin client (`realm-dev.json` line ~116) which already has it `false`. Code and PKCE only, as `tools/smoke.mjs`'s own comment says a production realm should do.
2. **The redirect URIs.** `"redirectUris": ["http://localhost:5173/*"]` must become your real web client origin(s), e.g. `["https://demo.example.org/*"]` — and, since Keycloak matches these literally, make sure it is `https://` once TLS is terminated in front of the web client, and that it matches exactly what the browser will be redirected back to.
3. **`COOP_ERP_MFA_PASSWORD_REAUTH_COUNTS`** (backend env var; realm-side there is no separate flag — it is read by the backend, `coop-erp.security.mfa.password-reauth-counts` in `application.yml`, and by the web client as `VITE_OIDC_STEP_UP_ACR_VALUES` in `infra/compose/compose.yml`'s `web` service). This makes a fresh **password** sign-in count as the second factor for a step-up (publishing a price list, signing a stock balance) — acceptable only because the dev realm has no OTP configured at all. Since wave 2 (decision D-5, `docs/progress/deviations/2026-10-06-wave2-deploy-kit.md` (5)), `JwtClaimsMapper`'s constructor **refuses to start** when this is `true` against a non-development issuer, unless the second opt-in `COOP_ERP_MFA_PASSWORD_REAUTH_PUBLIC_ACK` (`coop-erp.security.mfa.password-reauth-public-issuer-ack`) is the literal `demo-data-only`; it then logs a `WARN`. Only the demo server's `infra/deploy/compose.yml` sets both. For any other server: configure a real second factor (OTP) in the realm and set the flag `false`.

None of this needs a new realm export tool: edit `realm-dev.json` (or keep a separate `realm-demo.json` if you want the two realms to diverge further — Keycloak just needs whichever file `KC_HOSTNAME`/the import path names), and point `KC_HOSTNAME` in the Keycloak service's environment at the real public issuer host instead of `http://localhost:8085`, matching whatever you set `OIDC_ISSUER` to on the backend.

## 5. Install, first start, demo data, reset, checks, backup

**Install.** `git clone` the repository (or deploy a tagged release checkout — see the release checklist below), install Docker with the compose plugin (2.24+), JDK 21 and Node with pnpm on the server if you intend to run `make image`/`make build` there rather than push pre-built images (README's fifteen-minute start covers the exact requirements; they apply on a server the same as a laptop). Put the env file from section 3 somewhere outside the checkout and reference it from every `make`/`docker compose` invocation, e.g. by exporting the variables in the shell profile of the deploy user, or via `docker compose --env-file /etc/coop-erp/demo.env ...` if you script around the Makefile.

**First start.**
```sh
make up            # builds/pulls images, starts the stack, migrates, seeds the development rows
make demo-data      # loads the demo (docs/DEMO.md); safe to repeat
```
`make up` alone gives you the development seed (`fed-admin`/`fed-officer`/`mpcs-admin`/`cashier`, password `dev`) and a healthy stack; `make demo-data` adds the demo's parties, users and the phase-1 story data. Follow section 4 above (realm edits) **before** the first `make up` on the server, since Keycloak imports `realm-dev.json` only "when the volume is first created" (`compose.yml`'s comment on the Keycloak service) — importing it again needs `make reset`'s Keycloak wipe, described next.

**Reset.** `make reset` (`docker compose ... down --volumes --remove-orphans`) deletes every data volume, PostgreSQL and Keycloak both — the next `make up` starts from nothing and re-imports whatever realm file you point it at. A clean demo from nothing is `make reset && make up && make demo-data`, exactly as `docs/DEMO.md` documents. **This is destructive**: it takes down RabbitMQ's and MinIO's volumes too, so any attachment uploaded through the demo (there are none by default in the loader, but a live click-through might add one) is gone. Never run it on a server without the release checklist below telling you to.

**Checking it works.**
- Health endpoints: `curl http://localhost:8080/actuator/health` (or through your reverse proxy) should answer `{"status":"UP", ...}`; `/actuator/health/liveness` and `/actuator/health/readiness` are the orchestrator-style probes (`application.yml`'s comment on `management.health`), and they need no token. The Keycloak health check inside compose reads `/health/ready` on its internal management port 9000, which is not published to the host by default — check it from inside the Docker network (`docker compose exec keycloak bash -c '...'`, or add a temporary port mapping) if you need to probe Keycloak's own health from outside.
- The smoke test: `make smoke` (add `TWO=1` only if you are running `make up-2`). It signs in as several dev-realm users with the password grant and checks scope isolation, idempotency and translated errors end to end. **Caveat:** `tools/smoke.mjs` itself signs in with the password grant against `coop-erp-web`, which section 4 says to disable on the server realm — so `make smoke` either needs `directAccessGrantsEnabled` temporarily re-enabled (do this only against a throwaway/staging copy of the realm, never the live demo realm with real users watching) or is a check you run once against the fresh stack **before** you lock the realm down for real users, not a check you can run continuously against the locked-down server. **To confirm:** whether the team wants a variant of the smoke test that does not depend on the password grant, for ongoing checks against the hardened demo realm.
- `make e2e` needs a real browser (Playwright/Chromium) driving the sign-in pages; it is a heavier check, meant for CI or a workstation, not something to run routinely on the server itself.

**Backing up and restoring the database.** Nothing in the repository automates this yet (**to confirm** against doc 35/14 for what a real production backup policy should be — RPO/RTO targets are referenced as an open item in `docs/DECISIONS_PENDING.md`, F-14). For a demo server, the pragmatic approach:
- Back up: `docker compose --project-directory infra/compose -f infra/compose/compose.yml exec -T postgres pg_dump -U "$POSTGRES_USER" -Fc -d "$POSTGRES_DB" > coop_erp_$(date +%Y%m%d_%H%M).dump` (custom format, so you can restore selectively if needed) — run this against a quiet moment, not mid-demo, since it is a logical dump rather than a point-in-time snapshot. Copy the dump file off the box immediately (it is your only copy otherwise).
- Restore: bring up an *empty* database (`make reset && make up` gets you a freshly migrated, empty schema — or point at a fresh volume) then `docker compose ... exec -T postgres pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists < coop_erp_YYYYMMDD_HHMM.dump`. Restoring into a database that Flyway has already migrated to a *different* version than the dump's is not something this project's tooling checks for you — restore against a checkout at the same commit the dump was taken from, or expect Flyway to complain about the mismatch on the backend's next start.
- The MinIO object store (attachments) and RabbitMQ (in-flight messages only, nothing durable you need across a restore) are not covered by the PostgreSQL dump; for a demo with no real attachments in play this is usually fine to ignore, but note it if the demo starts uploading images or documents to the object store.

## 6. Release checklist

Before pointing the demo's public URL at a new release:

- [ ] **Which commit.** Know the exact commit SHA (or tag) you are deploying; record it somewhere (a deploy log, a git tag `demo-YYYY-MM-DD`) so a rollback is "redeploy the previous SHA", not guesswork.
- [ ] **CI green.** `gh pr checks <n>` (or the `main` branch's own workflow run) is green for that commit — build, unit and integration tests, web lint/tests, the generated-client and module-diagram check, the scaffolder proof, stack smoke, secret scan. Do not deploy a commit CI has not finished checking.
- [ ] **Images built.** `make image` on the release commit builds both `coop-erp/backend:dev` and `coop-erp/backend-worker:dev` (Jib, `-PjibFromDaemon=true` and `-PjibWorker=true`) — rename/tag them for the server (e.g. push to a registry, or `docker save`/`docker load` onto the server) rather than relying on the `:dev` tag compose defaults to; decide and document your own tagging scheme (this repository's compose files assume a local Jib build, not a registry pull — `pull_policy: never` on the backend service). The worker image specifically (`infra/worker-image/Dockerfile`, Debian trixie-slim + JRE + Chromium) needs its base rebuilt (`docker build ... infra/worker-image`) whenever that Dockerfile changes, which `make image` already does for you — just do not skip straight to the Jib step by hand.
- [ ] **Migrations.** Flyway runs automatically when the backend container starts (`FlywayConfig`); there is no separate migration step to remember, but do check `git diff` on `backend/app/src/main/resources/db/migration/**` between the currently-deployed commit and the new one, so a migration that needs `MIGRATION_OUT_OF_ORDER` or manual attention on a database that already has real (demo) rows in it does not surprise you. The local stack sets `MIGRATION_OUT_OF_ORDER=true` for developer convenience (compose's comment on why); **do not carry that onto the demo server** unless a specific PR tells you to — the strict, in-order default (`false`) is what a server holding data across releases should keep, same reasoning as `application.yml`'s comment: "what a deployed database needs (its schema must be reproducible from the files in order)".
- [ ] **`make reset` only when a PR says so.** Never reset the demo database as a matter of routine between releases — Flyway migrations are additive and forward-only by design; reset destroys every demo document, audit record and user session. Only run it when a merged PR's body explicitly calls for it (the ticket brief's own PR template has a "make reset" section for exactly this — "Needed only for a renamed or removed migration or a changed queue argument; else 'Not needed'"). If a PR does call for it, treat that release as "the demo restarts from nothing" and re-run `make demo-data` and the password changes below as part of the same release, not as an afterthought.
- [ ] **Demo users' passwords changed from `demo`.** Every user in `docs/DEMO.md`'s "Who is who" table signs in with the password **`demo`** by default (`seed/m1security/demo-users.demo.sql`), and the leftover development users (`fed-admin`, `fed-officer`, `mpcs-admin`, `cashier`) sign in with **`dev`**. Both are published, well-known passwords the moment this repository is public or shared — **change every one of them** in Keycloak (or in a `realm-demo.json` you control, applied at import) before the demo is reachable by anyone outside the team. Decide whether the server-facing demo keeps the *same* password for every demo user (simplest to hand out to an audience, but means one leaked password reads/writes as that one user only, not as everyone) or per-user passwords communicated separately; either way, `demo` and `dev` themselves must not survive onto a server other people reach.
