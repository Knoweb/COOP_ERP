22 ­ M2 Catalogue & Batch

Module design for the shared product truth: stock keeping units in one global namespace
with local and shared status, units and pack conversions, barcodes many-to-one with
optional batch resolution, tags, tax categories, product images, and physical batches
carrying expiry and the printed maximum retail price. The module the data steward
operates, and the largest reference set distributed to tills.

Why this module decides whether the programme lands. The requirements baseline names the assembly of a
trusted catalogue as the critical path (T-03) and the data steward as the single largest open action. M2's screens are
the steward's tools; if bulk import, duplicate detection across three scripts and translation completeness are
afterthoughts, the catalogue will be assembled in spreadsheets and imported badly. They are first-class here.

1. Purpose and scope

M2 defines what can be counted and sold: the SKU as the smallest distinctly tracked item (B-01), its units and
pack conversions, the barcodes that identify it at a scanner, the tags that group it, the tax category that prices it,
the images that help a cashier recognise it, and the batch as the physical identity that carries expiry and printed
MRP. It owns identity, not holding: where stock is and what it cost belong to M5 (doc 17 change C4).

3. Domain model

Tables are those of doc 18 v0.2 part B owned by M2 (schema catalogue): uom, sku, sku_uom_conversion,
sku_barcode, sku_alias, sku_image, tag, sku_tag, tax_category, tax_rate, batch; plus one table introduced here.

    3.1 SKU             Design

Aspect                  sku with its conversions, barcodes, images, tags and attributes. Root of identity for everything sold or counted.
Aggregate
Invariants              sku_code system-generated, opaque, unique, never reused. short_name_en non-null in every status; _si and
                        _ta non-null for SHARED (B-I1). Owner is the Federation for SHARED; the creating entity for DRAFT and
Visibility              LOCAL. base_uom_code is KG when sold_by_weight. attributes under 4 KB, no behaviour, not
                        searchable.
Flags that drive other
modules                 SHARED SKUs are readable by every scope (the reference exception to OWN: a policy shared_read on status
                        = SHARED). LOCAL and DRAFT SKUs are OWN only, and Federation view-only (M-03).

                        batch_tracked, expiry_tracked, has_printed_mrp (new; false for loose produce and unpriced goods so
                        a null batch MRP is legitimate rather than missing), sold_by_weight, multi_mrp_policy (default from M3's
                        policy; stored here because it is a SKU property).

3.2 Units and conversions

Aspect                  Design
Vocabulary
                        uom is Federation-governed: EA, KG, G, L, ML, CASE, PKT, BAG, BOX, DOZ. An entity cannot add units; it can
Conversion              define conversions for its own SKUs.

                        sku_uom_conversion(sku, uom, factor_to_base, effective_from/to): CASE = 24 × EA. A
                        supplier's case-size change is a new effective-dated row, not an edit (P5). Weighed goods: base KG; retail packs
                        of a bulk SKU are a different SKU produced by an M5 recipe, never a conversion (ADR-07).

    3.3 Barcodes        Design

Aspect                  sku_barcode(barcode, symbology, sku, uom, batch_id?, owner_entity, status). Unique per
Registry                (barcode, symbology) across the federation for factory symbologies; INTERNAL codes unique within the owner
                        entity (B-I2).
In-store codes
                        GS1 prefixes 20­29 for weigh labels and stickers. The label encodes SKU code and weight (or SKU code and
Batch link              batch), never a price, so the till resolves the price through the shared engine and the control-price ceiling still
                        applies (multi-MRP study; doc 18 §4.9).
2D readiness
                        batch_id set when the code identifies one batch: an MPCS batch sticker (option C of the study), a manufacturer
                        code that changed with the MRP (option B), or a 2D code carrying application identifier 10. The till's scan layer
                        passes the parsed GTIN, lot and expiry; M2's lookup returns the SKU and, when it can, the batch.

                        LookupByBarcode accepts (gtin, lot?, expiry?, symbology); when lot is present and a batch with
                        that number exists for the SKU, the batch is returned even without a registered batch barcode ­ this is what
                        makes GS1 2027 marking pay off without any catalogue work.

    3.4 Images          Design

Aspect                  sku_image(sku, barcode?, owner, object_key_full, object_key_thumb, hash, status)
Model                   (doc 18 v0.2). One ACTIVE image per (sku, barcode-or-null).

Thumbnails              An M2 job (ImageThumbnailJob) produces the 128 px WebP thumbnail on attach; the snapshot carries only
                        thumbnail keys; the till fetches lazily and caches (doc 20 M2; doc 32 §5.1).
Ownership
                        Federation attaches for SHARED SKUs; an entity may attach for its LOCAL SKUs; an entity may also attach a
                        local override for a SHARED SKU (different pack in that region), scoped to its own locations.

    3.5 Tags            Design

Aspect                  tag(tag_code, names, governed, owner_entity). Governed tags are Federation-owned and used for
Vocabulary              federation-wide comparison and for policy attachment (expiry windows, loss tolerances, variance thresholds,
                        control-price scope, multi-MRP policy). Local tags belong to an entity for its own merchandising.

    3.6 Tax          Design

Aspect               tax_category(code, names) and tax_rate(category, rate_percent, effective_from/to).
Model                Standard VAT only (J-03); exempt and zero-rated as categories with a 0% rate row. Publication of a new rate is a

    3.7 Batch        Design

Aspect               batch(sku, batch_no, supplier, manufacture_date, expiry_date, printed_mrp,
Identity             origin_document, is_synthetic). Global, not owned: one physical batch is held successively by the
                     Federation, a distributor and an MPCS; each holding is an M5 stock lot with its own cost (doc 17 change C4,
Uniqueness           ADR-38).
Synthetic batches
MRP                  (sku_id, supplier_id, batch_no) unique. A receiver who keys a batch that already exists gets the
Who creates batches  existing row (the GRN cites it); a receiver who keys a new number for the same physical batch creates a
                     duplicate identity ­ accepted, flagged as a duplicate suspect for the steward (Section 6.2).

                     For SKUs with batch_tracked = false each receipt line creates a synthetic batch (is_synthetic =
                     true, batch_no = 'S-' + document number + line) so that MRP and cost always have a home and
                     price resolution has one code path (doc 18 DR-5).

                     printed_mrp mandatory when the SKU has has_printed_mrp; immutable. A mis-keyed MRP is corrected by
                     CorrectBatchMrp: a new batch row, an audited link corrects_batch_id, and M5 re-points the lots (B-I8).
                     Two concurrent batches may legally carry different MRPs (ADR-08).

                     M4's GRN confirmation (supplier goods at a Federation warehouse; distributor and MPCS receipts cite the
                     incoming batch or create a local-supply batch) and M5's repack execution (output batch for the produced SKU).
                     M2 exposes RegisterBatch as an internal command those modules call in their own transaction.

3.8 Assortment (new concept, for the snapshot)

Aspect               Design
Definition
                     The set of SKUs a location's till must know: SKUs on the owning MPCS's retail price list (M3 query)  SKUs with
Materialisation      a lot at the location (M5 query)  LOCAL SKUs of the owning entity  SKUs tagged core-range (a governed
                     tag the Federation uses for goods every shop should be able to sell).

                     location_assortment(location_id, sku_id, reason, since) maintained by an M2 consumer of
                     price-list, lot and SKU events; the snapshot contributor reads it; a change to it writes the change-log row for that
                     location (doc 32 §5.1). Change request CR-22-2 adds the table to doc 18 part B.

Aspect               Design
Model
                     supplier(supplier_id, owner_entity, name, status) ­ enough for batch attribution (B-03) and
                     Federation receipts. Change request CR-22-1 adds it to doc 18 with the note that M10 absorbs it in phase 2 (doc
                     20 M10 seams).
