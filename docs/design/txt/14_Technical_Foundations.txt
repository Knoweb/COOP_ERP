1.1 Modular monolith, enforced

The application is one Spring Boot deployable organised as modules with build-time boundary enforcement
(Spring Modulith): a module's tables, services and events are its own; other modules use its published
commands and queries or react to its events through the transactional outbox. The enforcement is what keeps a
monolith from rotting into a tangle; it also keeps extraction into a separate service possible later, which is the
answer to “what if one module needs to scale alone” (doc 20 Appendix A).

1.2 Portability as the hedge

Because hosting is undecided and may change at the pilot gate, every infrastructure dependency is chosen for
portability: PostgreSQL, an AMQP or NATS broker, S3-compatible object storage, OCI containers, OpenID
Connect. Moving between a cloud provider and local hosting is then a deployment exercise (doc 35), not a
redesign.

1.3 Stateless scale-out: any request to any instance

moment and the load balancer needs no sticky sessions. A request from a user or a till that last spoke to
instance A is served identically by instance B. The rules that make this true:

3. Till platform

Direction confirmed: ARM-based Android terminals, all new, centrally specified (H-08, T-07). In practice this is
the class of integrated Android POS terminals with built-in printer and battery. The consequences for design are
already absorbed: the internal battery turns the power-cut requirement into a device property (Q-07); the
integrated 80 mm printer takes raster output, which solves trilingual receipts; the peripheral abstraction is the
platform's own interface over two or three vendor SDKs, with UnifiedPOS used only as vocabulary; updates are
self-managed through a device-owner agent (doc 31).

Recommendation for the decision. Choose the cloud provider with managed Postgres unless the government IT
policy check (Q-08, still open) requires in-country hosting. If local hosting is chosen for cost or policy, adopt a hybrid:
primary in-country, backups and a warm standby in a cloud region, so the RTO/RPO commitment survives a site loss
and the operating model stays close to single-DevOps. Decide at the pilot gate at the latest; nothing before pilot
depends on the answer except doc 35.
