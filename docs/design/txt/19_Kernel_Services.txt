Why these five are designed together. A permission is meaningless without an identity to hold it; an audit event is
meaningless without both; every audit event and every screen string must render in three languages; and all of it
moves through one event model. Designing them apart produces five inconsistent notions of "who", "where" and
"when". Designing them together lets one set of claims (user, device, entity scope, location scope, correlation) flow
unchanged from login to audit row to report.

4. Audit service

Doc 18 defined the audit tables; this section defines the service that fills and reads them. The design goal is that
an auditor can trust the log without trusting the application: structure, not procedure, guarantees completeness
and immutability.

4.1 Emission

Rule                      Design
Same transaction
Facade, not free text     The audit row is inserted in the same database transaction as the business change it records, through one audit
Correlation               facade. There is no separate audit queue at central; a business change without its audit row cannot commit. On the
Minimal diff              till the same holds against the local database.
Never logged
Reason capture            Code calls `audit.record(eventType, subject, before, after, reason, witness)`. Event types are the catalogue of doc 18
                          (audit_event_type); a code path cannot invent a type, and every REVIEW/ALERT type must have a reviewer
                          template before deployment (D-I3).

                          The first request in a user action creates `corr`; it propagates through service calls, the outbox and the till sync so
                          that a refund appears as one action (REFUND, DRAWER_OPEN, state transition) rather than three unrelated rows.

                          before_state` / `after_state` carry only changed columns. For immutable subjects
                          (documents) `before_state` is null and the event points at the document; the document is
                          its own record.

                          Credential material (passwords, PIN hashes, TOTP secrets, tokens), full card references, and personal data values.
                          A customer phone change logs the customer id and the fact; the values live under PDPA rules in the customer table

                          Where the type demands a reason (voids, refunds, write-offs, credit-limit changes, negative-stock

5. Internationalisation on ICU

Trilingual is a phase-1 requirement across interface, printed output and search (P-01, P-04). The design
separates four concerns that are often conflated: interface strings (a translation catalogue owned by the
product team), master data (three columns per name, owned by the catalogue steward), rendering (fonts,
shaping, formatting), and collation and search (how Sinhala and Tamil sort and match).

10. Service invariants

The contract that code, configuration and tests must all honour.

· X-I1. No request executes without a resolved principal and scope; anonymous access exists only for the login
   endpoints.

· X-I2. Permissions are checked at the service layer by code, never inferred from the user interface; every
   service method carries a permission annotation (build-time test).

· X-I3. No user can grant a permission they do not hold; no entity can lose its last user-management holder.
· X-I4. A requires_mfa permission is exercised only with `mfa_at` inside the freshness window.
· X-I5. A till exercises only permissions present in its signed snapshot; offline, only those flagged

   offline_allowed.
· X-I6. Every business change commits with its audit row and its domain event in the same transaction, or not

   at all.
· X-I7. Every event and audit row carries the correlation id of the user action that caused it.
· X-I8. Events from one source are applied in `source_seq` order, exactly once in effect (idempotent by

   `event_id`).
· X-I9. Every string shown to a user resolves through the message catalogue or a three-column name with

   English fallback; a raw message id or a blank is a defect.
· X-I10. All stored text is NFC-normalised; all list ordering uses the display language's ICU collation.
· X-I11. No module calls a notification, SMS or e-mail gateway directly; every notification originates from a

   domain event through a registered rule.
· X-I12. No module holds private settings; every configurable value resolves through the configuration register

   with a registered key and schema.
· X-I13. Every scheduled job runs under the kernel lock; two instances never execute one job concurrently.
