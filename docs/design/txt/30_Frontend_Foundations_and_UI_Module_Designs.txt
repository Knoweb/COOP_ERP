The one rule that shapes every screen. Shop staff have generally low computer familiarity (S-02) and already know
the paper: the requisition book, the delivery note, the GRN, the khata, the day-end sheet. Every screen mirrors a paper
document they already understand, laid out the way the paper is laid out, with the same words in their language.
Software vocabulary (dashboard, entity, sync, transaction) never appears on a shop screen.

2.3 Usability rules for shop screens

· Three taps to sell. Scan, scan, tender. Nothing on the sales screen requires reading more than one word to
   act.

· No modal chains. A screen never opens a dialog that opens another; confirmations are inline in the
   ApprovalBar.

· Destructive actions need a reason, never a second click. A void asks why (coded), not "are you sure?".
· The keypad is the primary input. Quantity, weight, PIN and price look-ups all work without a keyboard;

   search by name is the fallback.
· Same place every time. Basket left, item card right, totals bottom-right, actions bottom bar; the layout never

   reflows by mode.
· Show what the system knows, honestly. Offline state, pending uploads, stale ceilings and missing

   translations are visible, never hidden.
· Training mode is loud. Sandbox transactions look different enough that a real receipt can never be

   mistaken for practice (T-04).
· Validate with real cashiers twice (Stage 3 usability rounds) before any screen is frozen.

                       MPCS administrators of several shops).

Data access            A typed client generated from each module's OpenAPI slice (the contract file of doc 20 section 5); server-state

                       modules.

Forms                  Validation schema generated from the contract; inline errors in the shop language; drafts autosave; issued
                       documents render read-only through the same components.

Permissions in the UI  Visibility from the resolved permission set; every action button also handles the server's permission denial
                       gracefully (the server is the authority, doc 19 X-I2).

Internationalisation   Message catalogue loaded per language; ICU MessageFormat; dates and money formatted centrally; language
                       follows the user's location (doc 19 5.1).

Printing and export    A4 output is server-rendered PDF (doc 19 5.3) opened in a viewer; spreadsheet export is a server job with a
                       download link.

Responsiveness         Document pages collapse to a single column; line tables become stacked cards on phones; approval bars stay
                       fixed at the bottom.

Accessibility          Keyboard operable throughout; focus order follows the paper reading order; WCAG 2.2 AA targets.

Error and degraded states Loss of connectivity shows a banner and keeps read views; write actions are disabled with the reason; a version
                                      banner appears when the deployed backend is newer than the loaded client (doc 31).

Module packaging       Each module contributes a route group, its screens, and its generated client; the shell owns layout, auth, i18n,
                       navigation and the component library. A module developer adds screens without touching the shell.

4. Till application shell

4.1 Technology decision

Three stacks were weighed for the till: native Android (Kotlin, Jetpack Compose), Flutter, and React Native. The
till needs device-owner and lock-task control, direct peripheral access, a durable local database with safe
shutdown, raster printing, background sync and a two-day offline life on modest ARM hardware. Native Android
is the only stack where all of these are first-class; the others reach them through bridges that become the
project's risk.
