Cooperative Retail and Distribution System (Knoweb)
Start Here  -  System Design Documentation
The entry point to the system design folder. Section 1 says what the system is; sections 2 - 3 explain the three ideas behind it and which document is which; the rest is a working guide for developers taking a module: what to read, how the code is organised, the first steps, the rules that are not negotiable, and how to get unstuck. Non-developers need only sections 1, 3 and 12. Version 1.1, 10 September 2026.
If you read nothing else: your module's implementation guide (the document numbered nA  -  21A, 22A, ...) is written so that you can start from it alone. Read it first, end to end, before you open the design document or the architecture. Everything below explains why it is shaped that way and what to do in what order.
1. What you are building, in five sentences
The system runs the supply chain and shops of Sri Lanka's cooperative federation: the Federation sells to about 75 distributors, who sell to about 800 societies (MPCS), who run about 4,000 shops growing to 10,000. Goods are ordered, delivered, received, sold at the till, and paid for; stock is counted, written off and repacked; customers buy on credit; everything is reported to the federation. Shops must keep selling for two days with no connectivity, in Sinhala, Tamil or English. The backend is one Java application divided into nine modules with strict boundaries; the till is a native Android application; the two talk through a sync contract that never merges data. You will own one module, from its database tables to its screens.
2. Three ideas you must understand before writing code
Almost every design choice in this system comes from one of these. When something looks odd, check which one explains it.
Idea
What it means for your code
A shop is a location, not a legal entity
Every row carries owner_entity_id (the MPCS, distributor or Federation that owns it). A shop never owns anything. Row-level security in the database filters rows by the caller's entity and location; your code never filters by tenant itself.
Ownership of goods transfers when the receiver confirms the goods received note (GRN)
Before confirmation the goods are the seller's; after it, the buyer's. Batches are registered, stock lots are created, invoicing becomes possible  -  all from that one event. Nothing about a GRN is ever edited afterwards.
No record is ever written by two parties
The till writes its own receipts, sessions, counts and receiving; central writes everything else and pushes it to tills read-only. Because nothing has two writers, there is no merge logic anywhere. Never write code that 'reconciles' two versions of a record.
Two more rules follow from these and are enforced by the build: documents are immutable once issued (corrections are new, linked documents), and ledgers  -  stock movements, account postings, the audit log  -  are insert-only (balances are sums, never edited).

4. What to read, in what order
Read in this order. Each step is a prerequisite for the next; how long each takes depends on you and your module.
 This document, end to end  -  orientation.
 Your module's implementation guide (nA), sections 1 - 4 and 10  -  what you build, what you inherit, the schema, the package layout, the tickets.

 Your module's design document (n), sections 3 - 6  -  the reasoning behind the tables and state machines, and the flows you must make work.
 Your nA guide again, sections 5 - 9, slowly, then 30 Frontend Foundations sections 2 - 3  -  the API slice, the handler specifications, the screens, the tests.

Do not start with 17 Solution Architecture or 14 Technical Foundations. They explain the whole system and are useful after your first module; before it they will slow you down.
5. How the code is organised
One repository. The backend is a Spring Boot application with one package per module; the build fails if a module reaches into another module's internals.
 backend/app/src/main/java/lk/coopfed/knoweb/
   kernel/          layer 0: scope, identity, permissions, audit, events, documents, sync
                    (you call it; you never change it)
   m1party/ m2catalogue/ m3pricing/ m4trading/ m5inventory/
   m6pos/ m7customers/ m8reporting/ m9integration/
   hello/           the template module  -  copy it, do not invent your own shape
  
 lk/coopfed/knoweb/m2catalogue/            (example)
   api/        what other modules may call: commands, queries, events   <- your contract
   query/      read-only query interfaces other modules may call
   internal/   everything else: entities, repositories, handlers, services  <- private
   web/        REST controllers implementing the generated OpenAPI interfaces
  
 backend/app/src/main/resources/
   db/migration/m2catalogue/V0001__catalogue.sql   your schema (nA guide section 3)
   openapi/m2catalogue.yaml                        your API slice (nA guide section 5)
   seed/m2/*.yaml                                  your seed data
   i18n/en.json si.json ta.json                    message ids; a missing translation fails the build
 web/src/modules/m2catalogue/                      your screens, on the shell's components

The database has one schema per module (party, security, catalogue, pricing, trading, inventory, pos, customers, reporting, integration). You write only to your own schema. To use another module's data you call its query interface; to change another module's state you publish an event it handles.
6. The shape of every command handler
Every write in the system looks the same. The kernel interceptor has already checked the permission, the multi-factor step-up and the idempotency key before your code runs. Your handler does four things in one transaction, in this order:
 @CommandHandler(permission = "cat.sku.create_local")
 class CreateSkuHandler implements Handles<CreateSku, SkuId> {
   @Transactional
   public SkuId handle(CreateSku cmd, ScopeContext ctx) {
     // 1. guards   business rules in the order the nA guide lists them;
     //              throw ProblemException("sku.name_required")
     // 2. mutation create or change your entities; save through your repository
     // 3. audit    audit.record(SKU_CREATED, Subject.of(sku), null, sku.snapshot(), ctx)
     // 4. events   events.publish(new SkuCreated(sku.id(), ctx.entityId()))
     //              (written to the outbox in the same transaction)
     return sku.id();
   }
 }

If a handler needs a fifth thing, stop and ask. Handlers that skip the audit call, publish events outside the transaction, or call another module's command directly are the three most common mistakes in review.

8. Rules that are not negotiable
Rule
Because
Never UPDATE or DELETE a document, a line, a stock movement, a posting or an audit row. The database role does not allow it; do not ask for the grant.
The audit trail and the gapless numbering depend on it
Never store a balance you do not recompute from the same events that change it.
Balances are sums; a cached balance is a convenience, not a truth
Never write to another module's schema; never import another module's internal package.
The build enforces it; the modules must stay independently deployable later
Never put a phone number, NIC, password, PIN or token in an event payload, a log line or an audit row.
Personal data and credentials have exactly one home each
Never reject a till's uploaded fact for a business reason. Flag it.
The sale already happened in the real world
Never hard-code a price, threshold, window or limit. It is a configuration item or a data table.
876 societies need different values; law-like values (control prices) are data with their own tables
Every user-visible string is a message id with three translations.
Sinhala, Tamil and English are all first-class; a missing one fails the build
Every mutating API operation carries an idempotency key and a permission annotation that matches the OpenAPI slice.
Stateless instances; the build compares them
9. Testing: what 'done' means
Your nA guide section 9 lists the layers. The minimum before a ticket is closed:
 Every guard in the handler specification has a failing-case unit test with its message id.
 Every operation in your slice has a contract test through the generated client, including the idempotent resend.
 Your tables have rows in the row-level security matrix: a user from another entity sees nothing; a shop-scoped user sees only its shop; the Federation reads but cannot write.
 If your module has a ledger or a balance, the property-based test 'balance equals the sum of movements under random interleavings' is green.
 The scenario in your guide's section 9 that your ticket completes runs end to end against the composed stack with two backend instances (`make up-2`).
10. When you are stuck
Situation
Do this
The guide does not say what should happen in a case you hit
Check the design document's section 4 (state machines) and section 6 (flows). If it is still not there, ask the module designer and record the answer in your module README. Do not decide silently.
The answer depends on a decision nobody has taken
It is probably in 10 Open Items Register with an assumption already written. Build to the assumption; note the item number in your code comment.
You need something from another module that does not exist yet
Your guide's section 11 names the stub to use. Code against the interface in the other module's api package; the stub returns fixture data.
You think the design is wrong
You may well be right. Write it as a change request (what, why, what changes) and send it to the design lead. Do not fix it locally  -  the same problem exists in the documents and in other modules.
A kernel service does not do what 19A says
That is a Sprint 0 defect. Report it with a failing test; the platform pair fixes the kernel, you do not.
The build fails on a boundary or ownership rule
The rule is right and your code is wrong. Move the code to the correct package or schema; do not loosen the rule.
11. Words you will see everywhere
Term
Meaning
Entity
A legal party: the Federation, a distributor or an MPCS. Owns everything.
Location
A warehouse, shop or office belonging to an entity. A shop is a location.
SKU
Stock keeping unit: the smallest thing counted and sold. Global namespace.
Batch
A physical supply identity with expiry and the printed maximum retail price (MRP). Global, not owned.
Lot
An entity's holding of a batch at a location, in a condition, at that entity's cost.
GRN
Goods received note. Confirming it transfers ownership.
Control price
A government-gazetted maximum price; a hard ceiling by date, whatever is printed on the pack.
Snapshot
The read-only reference data a till receives (catalogue, prices, lots, operators). Applied whole or not at all.
Bundle
A complete document a till uploads (header, lines, movements, state) as one event.
Kernel
Layer 0: scope, identity, permissions, audit, events, documents, sync. You use it; you never change it.
Contract
Your module's api and query packages plus its OpenAPI slice. Frozen once another module depends on it.
nA guide
The implementation guide for design document n. Self-contained; start there.
