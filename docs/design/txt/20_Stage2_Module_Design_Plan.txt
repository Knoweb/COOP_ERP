Design stance: enterprise-grade, not enterprise-complicated. The system must carry 10,000 shops, 3 million
receipts a day, multi-entity legal ownership, offline trading and an immutable audit trail. That demands rigour in a small
number of places: ownership, numbering, immutability, sequencing and permissions. Everywhere else the plan
chooses the plainest mechanism that meets the requirement, and Section 4 lists the mechanisms that were
considered and deliberately left out. A module design that adds one of them back must justify it against that list.

   2.1 Boundary rules (the modular monolith contract)

   · A module owns its tables (doc 18 assigns them) in its own schema namespace; no other module reads or
      writes those tables directly. Cross-module access is by in-process query interface (synchronous, read-only)
      or command interface (synchronous, transactional, permission-checked), or by reacting to domain events
      (asynchronous, via the outbox of doc 19).

   · One database, one transaction: a command that spans modules runs in one transaction because it is one
      process against one database. No sagas, no compensation logic across modules in phase 1; compensation

   20 - Stage 2 Module Design Plan and Blueprints | v0.3 draft | Cooperative Retail and Distribution System                      Page 2
   exists only for documents, as the typed links of doc 18.
· Events are notifications of committed facts, not the source of truth. Module state lives in tables; the outbox

   lets other modules and tills react. No module is event-sourced.
· Each module publishes a contract file (commands, queries, events with versions). A dependent module

   designs against the contract, never against the tables. Contracts are the artefact that lets modules be
   designed in parallel.
· Module boundaries are also team boundaries for design ownership, but not deployment boundaries: one
   deployable, per doc 17, until measured load says otherwise.

and marked restated from doc X §Y, so one document is read and provenance survives when a source
changes. DDL, seed data and the OpenAPI slice are committed to the repository; the guide is their reviewed
specification, never a second copy maintained by hand.
